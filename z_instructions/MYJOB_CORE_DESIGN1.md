## 推奨方式と比較

| 案 | 利点 | 問題/採否 |
| --- | --- | --- |
| 全簡易記録をPJA/eventsへコピー | 旧画面を使いやすい | 分類/仮名だけでも登録できる簡易と、具体ProjectJob中心の旧方式の差がある。旧ID/日報/数量単位/集計の移行と二重計上リスク。**初回不採用案** |
| 新しい仕事マスタへ全件移行 | 将来の共通基盤を作りやすい | 全既存経路の参照変更が大きい。**初回不採用案** |
| 保存元を保持して共通操作を追加 | 既存ID/予定/分析の分類を維持。段階配備できる | 旧新を区別する内部参照と混在系列/認可が必要。**推奨** |

共通のWorkJob参照は `{type: entry|assignment, id: 正整数}`。異なる保存元の同数字ID/同名を混同しない。これはサービス内の参照であり、一般画面にテーブル名/生キーを見せない。GETで仕事や予定を新規作成しない。

## 保存項目案（指定migrationのみ）

| テーブル | 新項目案 | 意味 |
| --- | --- | --- |
| personal_work_entries | completed_at nullable datetime | 独立した簡易仕事の明示完了。NULLは未完了、時刻経過で埋めない |
| personal_work_entries | source_entry_id nullable FK | 続き元が独立簡易の場合の元ID |
| personal_work_entries | source_assignment_id nullable FK | 続き元が旧マイジョブの場合の元ID |
| project_job_assignments | source_personal_work_entry_id nullable FK | 旧詳細形式で作った続きの元が独立簡易の場合の元ID |

既存PJA.source_assignment_idは旧→旧の継続のまま使う。各仕事の続き元は一つ: entryのsource_entry/source_assignmentは排他、PJAの既存source_assignment/新source_personal_work_entryは排他。実FK型は既存migrationのPK型に合わせ、parent削除はRESTRICT相当、cascade削除/NULLへ黙って切断しない。DB版で排他CHECKが使えなくてもサーバvalidation/transactionで必ず検証し、対応するDB制約も設ける。

**流用しない列:** entry.source_event_idは既存予定の結果補足、entry.project_job_assignment_idは既存割当との関係、PJA.supersedes_assignment_idは依頼置換、coordinator_assignment_idは校正関係。続き元の代用にしない。

初回migrationは新nullable項目/索引/FKのみ、既存行はNULLのまま。業務レコードの一括コピー/タイトルによる既存系列の推測はしない。補足entry(source_event_idあり)は独立したWorkJobとして操作せず、参照先assignment/eventの既存扱いを保つ。

## 共通サービスと画面

- `WorkJobService`（仮名）: resolve/authorize/read/edit/continue/complete/series/deleteの共通入口。entryは本人+会社部署の独立記録、assignmentは本人の自己割当を基本とし、受信/校正の専用操作は旧認可へ戻す。既存のNULL会社案件の許可と別会社拒否を保つ。
- 全公開入口は実所属INFO・非一般会社・SuperAdmin、実会社と異なるcontext拒否。系列の元/子/各予定も本人・会社部署を検証。初期ノードだけの認可では済ませない。深さ/件数に上限を設け、循環/欠損/不正参照は明示エラーとして安全に停止。
- 独立entryの詳細GETはBOXとカレンダーから同じページへ。AppLayout/青のUserナビを使用し、作業概要・予定枠/時間内訳・数量/単位・結果・完了状態・系列をカード化。編集は既存QuickWorkEntryModalを開き、同じentryを更新。既存の通常入力の軽さと分類/仮名だけの登録を保つ。
- 旧assignmentの詳細は既存URLを保持。混在系列の場合に共通の系列読み取りを利用し、旧新の前後への移動が切れない。旧だけの系列の応答を勝手に別形式へ変えて既存UIを壊さない。
- 新API案: strict trial配下にentry detail、complete、continue、series。旧から簡易の続きを作る入口も同じ共通continueにsourceの型とIDを渡す。新から旧詳細の続きは、元参照を検証して旧フォームへ初期値を渡し、既存保存処理に許可された継続項目だけ追加する。任意のIDや送信者を信用しない。
- 既存Calendar/DepartmentWorkの編集/削除POST/PUT/DELETEからも、新しい系列や完了の整合を壊さないよう共通検証を呼ぶ。リンクを隠すだけで代替しない。新関連のない一般Userの旧処理を広く変更しない。

## 続きの仕様案

1. 元の詳細から「続きのマイジョブを作成」。分類/案件または仮名、作業名、作業区分/種類、単位/公開範囲を初期値として引継ぐ。次の作業日と開始/終了を入力する。
2. 新しい数量、結果、完了、時刻はコピーしない。単位が同じでも元の数量を出来高として再登録しない。元仕事の実時間や数量は保存時に変更しない。親が休止分類を使っていた場合、新規候補の既存activePath規則を検証し、別の有効分類への変更を案内。
3. 同日午前/午後、翌日、旧→簡易/簡易→旧の全組合せを扱う。同名仕事の自動系列化や、別人の仕事を元とすることは禁止。元と続きの案件/分類変更を許す範囲は通常の新規作成権限で検証し、別会社への変更は不可。
4. 保存はtransaction内で行う。本人のロックを取得し元/子を再検証するなど、同時更新で循環や削除済み参照を作らない。二重クリック/通信再送はrequest token等で冪等化し、意図的な別の続きは別操作として許す。
5. 系列は作業日順を基本に、親子関係も分かる表示。時系列並びと親子が一致しなくても明示IDを優先。各ノードの予定が複数ある場合は全部を表示し、件数上限で無言で切り捨てない。
6. 昼専用自動分割は初回案に含めない。9〜12の仕事から13〜15の続きを作り、同じ系列・予定計5時間を確認する。昼休憩をまたぐ9〜15の1予定の控除とは別。

## 完了仕様案（承認対象の業務ルール）

- 旧の操作に合わせ、**選択した仕事と、その継続元の祖先を完了**にする案。確認画面に対象を示す。兄弟や子は勝手に完了にしない。
- 系列全体の完了表示は全ノードの状態から判断する。元が完了でも、未完の別の続きがあれば「系列全体が完了」とは表示しない。完了した元から再開の続きを作ることは許し、新しい続きは未完から始める。
- entryの完了はcompleted_at、旧はPJA.completed/statusを唯一の状態とする。表示用の別マスタに旧の状態を複製しない。作業時刻・数量・日報本文・評価点を完了操作で変えない。
- 旧ノードで表/校正等の連動が必要な場合は、既存の副作用を認可と対象条件を検証して呼ぶ。entryにproject_job_idがあるだけでは、案件全体や他人の割当を完了にしない。通知の二重送信も防ぐ。本番でテスト完了を実行して通知を試さない。
- 再完了は冪等。関係をロックしてから全対象の権限を検証し、途中だけ成功しないようにする。副作用のtransaction/通知タイミングも整理する。
- **完了解除は初回の追加対象外という案。** 解除を入れる場合は祖先/表/校正へどう戻すかを別に決める。旧動作を根拠に未完の兄弟まで閉じる仕様にはしない。

## 時間の共通仕様案

既存実装には、詳細の休憩/中断計算、保存plannedMinutes、分析minuteLedgerという別の処理がある。旧詳細の系列集計には直接Carbon::parseやユーザー設定休憩の独自計算が残るため、旧画面の数値を無条件の正解値にしない。

| 表示 | 意味/計算 |
| --- | --- |
| 予定時間 | 保存された予定枠の長さ。未来の予定も表示。旧の複数eventsはすべてJSTへ解決 |
| 休憩/重複を除く予定内訳 | 当日の設定休憩と重複条件を明示。別の業務/会議が重なる場合の扱いも既存の優先・配分規則へ合わせる。昼控除と重複控除を同じ分に二回適用しない |
| 記録時間 | 当日現在まで/対象日/勤務・会議根拠等、既存分析の対象判定を満たす時間。未来は未算入。完了したから未来分を認定しない |
| 系列合計 | 上記のどの値の合計か明記。所属各ノードの予定を一意に扱い、重なる時間を仕事の数だけ増やさない。予定計と記録計を混同しない |

- `WorkMinuteLedger`等へ既存分析minuteLedgerの休憩除外・優先イベント・同優先時の均等配分を挙動保持で抽出する案。分析の期間/対象/公開判定/係数/勤怠根拠を勝手に変更しない。記録別の配分も返せるようにして、詳細で同じ対象条件の値を照合する。
- 計算前の対象集めも、本人の当日全体から行う。系列の仕事だけを集めて別仕事との重複がなかったことにしない。非公開の他者タイトルを漏らさず、表示権限と時間の算入を区別。
- proof UTCはCalculatesEventTime、日付はJST。旧source_event付き補足やmaterialized copyを新しい仕事として重複算入しない。
- 分配で小数分が出る場合は内部精度を保持し、表示丸めと系列合計の丸め方を統一。丸めた各行の単純和で合計を変えない。
- 日報の予定表、予定内訳、評価用記録時間は意味が異なる。常に全画面で同じ数字になるとは要求せず、**同じ意味/対象日/対象条件で一致**することをM07の判定とする。評価点の方式/過去の再採点は変更しない。
- 共通化前後の既存分析出力（時間・点・日数・内訳）は合成fixturesで比較し、既存値が変わる場合は原因と仕様差を分離して、別の承認なしに配備しない。

## 編集・削除の案

- 編集しても同じIDと継続関係を保持。本人/会社部署をクライアントから変更させない。日付/時刻修正は既存日報の移動制約を守り、系列合計は読取時に再計算。
- **子のある元/途中仕事の削除は初回は拒否する案。** 「続きがあるため削除できない」と表示。子を自動削除したり黙って系列をつなぎ替えない。
- 末尾/独立entryは既存制約内で確認して削除可。ただし日報/旧仕事/添付等の関連がある場合は参照を確認し、安全な旧経路や明示エラーへ。既存仕事やファイルを巻き添え削除しない。
- 旧経路の削除でも新しい参照を壊せないようサーバ/FKで保護。詳細画面だけで削除を隠す方法は不可。

## 旧方式の維持とM11の扱い

添付/依頼/表・校正の専用画面は旧のまま残す。新規でその機能が必要な場合に旧詳細入力を選ぶ経路は維持する。**既に作った簡易記録を、同じ仕事として旧形式へ引き渡す方法は別の設計が必要**で、旧BOXトップのリンクでM11完了とはしない。
