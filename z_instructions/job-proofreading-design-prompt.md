あなたは既存ウェブシステムの改善設計を担当するソフトウェアアーキテクト兼要件整理担当です。
このタスクでは、既存実装を尊重しながら、組版ジョブと校正ジョブの連携設計を見直し、進行管理表との紐づけも含めて、実装可能な設計図に落とし込んでください。

# 最重要方針
- まず最初に、ワークスペース内の関連ファイル群を読んで現状把握してください。
- 現状把握が終わるまで、設計を断定しないでください。
- ファイルを読んだあと、私に質問してください。質問数は多くてかまいません。細かい部分まで確認してください。
- 疑問点が解消したら、設計図を作成し、`z_instructions` 配下に保存してください。
- 他の Claude でも続きの作業ができるように、設計図は「背景」「現状」「課題」「設計方針」「データ構造」「画面/操作フロー」「移行方針」「未確定事項」まで含めて、引き継ぎ可能な形で書いてください。
- 既存システムをなるべく活かし、必要な箇所だけを変更する方針で検討してください。

# この改善で扱いたいテーマ
通常のジョブ（主にオペレーターによる組版作業）と、校正ジョブ（校正者による校正作業）の連携を、情報欠落や運用ミスが起きにくい形で確立したいです。

## 前提の業務像
- プロジェクト内のジョブは、オペレーターによる組版作業と、校正者による校正作業がセットになることが多い。
- ジョブは、Coordinator から依頼された場合でも、自分で作成した場合でも、カレンダー連携された event として保存される。
- このジョブ情報をしっかり保持したまま、漏れなく校正へ受け渡し、校正作業を進めたい。
- オペレーターは必ず PC を使う。
- 校正者は PC を持たず、紙ベースで作業する。
- そのため、校正管理者にジョブを集約し、校正管理者が専用ページから校正ジョブの配分を行う運用になっている。
- 校正管理者は、オペレーター側のジョブ詳細をそのまま活用して校正ジョブを登録・管理したい。
- その際、ジョブ登録時に必要情報を「カプセル化」し、そのカプセルを保ったまま校正へ渡し、締切内に作業日を記録し、最終的にオペレーター側へ戻すことが重要。

## 既にある実装
- 校正管理の各機能
- ユーザーのジョブ画面
- 進行管理の project 管理画面のジョブ詳細
これらから、「まだ校正が終わっていないジョブを校正へ渡す機能」はすでに開発済み。

まずは、この「オペレーターのジョブ」と「校正ジョブ」の連携の現状を把握してください。

## 進行管理表について
Coordinator には「進行管理表」という機能があり、Excel の表のように、誰がどの作業に着手しているか、完了したかを把握できる。

- この進行管理表は、進行表からジョブを登録することでジョブと紐づけられる。
- ただし、現状ではオペレーターのジョブと校正のジョブは別々に扱われている。
- 理想としては、進行管理表とジョブ詳細をより強く紐づけたい。
- オペレーターのセルと校正のセルを連携させたい。
- 同一案件・同一作業セットであることが分かるなら、オペレーターセルと校正セルの位置関係を把握したい。
- そうすることで、オペレーター側から進行表に関連するジョブを校正へ渡した際に、校正管理者が進行表を細かく探さなくても、半自動で該当する校正セルの座標を見つけられる仕組みが欲しい。
- 現在の進行管理表はバラバラに作られているが、将来的には「組版と校正を1セットのブロックとして管理する」ような構造も考えている。

## 一緒に考えてほしいこと
- ジョブを中心に据えた、組版と校正の連携の仕組み
- 進行管理表とジョブをどう紐づけるか
- 既存システムを残しながら、どこを変更すべきか
- 「ジョブの情報カプセル化」とは、実装上どう表現すべきか
- ジョブ→校正配布→作業記録→オペレーター返却の流れを、データ構造と UI の両面でどう設計すべきか
- 進行管理表のセル座標やブロック構造と、ジョブ・校正ジョブの関係をどう扱うべきか

# あなたに最初にやってほしいこと
以下の順で進めてください。

## Step 1: 関連ファイルの探索と読解
まず、ワークスペース内から関連ファイルを探して読んでください。
優先的に確認したい対象:
- job / jobs
- proofreading / proof / 校正
- operator / typesetting / 組版
- coordinator
- calendar / event
- project 管理
- 進行管理表 / progress table / schedule sheet 的な機能
- job detail
- assignment / distribution / allocation
- status / deadline / work date
- モデル定義
- DB schema / migration
- API route / server action / service / repository
- 関連 UI コンポーネント

必要なら grep / ripgrep 等で探索し、関連箇所を洗い出してください。

## Step 2: 現状把握の要約
ファイルを読んだら、まず私に以下を要約して示してください。
1. 現在のジョブ構造の理解
2. オペレーター側ジョブと校正側ジョブの現在の関係
3. すでに実装済みの「校正へ渡す機能」の実装箇所
4. 進行管理表とジョブの現在の紐づき方
5. 今の設計の弱い点、情報断絶の起点になりそうな箇所
6. 変更影響が大きそうな領域
7. 設計を進める前に確認すべき論点一覧

## Step 3: 私への質問
要約のあと、私に質問してください。
質問は多くて構いません。むしろ細かく聞いてください。
最低でも以下の観点は質問に含めてください。

### 業務ルール
- 組版ジョブと校正ジョブは常に1対1か
- 1つの組版ジョブに複数回の校正があり得るか
- 再校、再々校の概念があるか
- 校正者個人と校正管理者の役割分担
- 校正完了の定義
- オペレーターへ戻す条件
- 締切、作業日、受け渡し日、完了日の区別

### データ
- 「カプセル化」したい必須情報は何か
- 校正へ渡したあとに、元ジョブと同期されるべき情報 / されるべきでない情報
- スナップショットとして固定したい項目
- 元ジョブ変更時の校正ジョブへの反映ルール
- イベント / カレンダーとの関係
- 識別子の持ち方（operatorJobId, proofreadingJobId, sharedJobGroupId などが必要か）

### 進行管理表
- セルの意味
- 行列の意味
- 組版セルと校正セルの対応ルール
- 現状のセル座標の保存有無
- ブロック化したい場合の表示・操作イメージ
- 同一案件内で複数の組版/校正ペアがある場合の扱い
- セル検索の半自動化に必要な条件

### UI / UX
- 校正管理者の専用ページで何を一覧表示したいか
- どのタイミングで校正ジョブを生成するか
- 自動生成 / 手動確認の境界
- エラー防止のために必要な確認画面やロック
- 紙ベース運用を前提とした表示要件

### 技術 / 既存資産
- 既存DBをどこまで変えられるか
- 既存APIや画面との互換性要件
- マイグレーション可能性
- 段階導入の必要性
- 監査ログや履歴の必要性

質問は、回答しやすいように整理して提示してください。
曖昧さが残る場合は、追加質問を続けてください。
無理に一度で設計に進まないでください。

## Step 4: 設計図の作成
疑問が解消したら、設計図を作成してください。
設計図には少なくとも以下を含めてください。

1. 背景と目的
2. 現状整理
3. 課題定義
4. 目標と非目標
5. 用語定義
6. ドメインモデル案
7. エンティティ関係
8. ジョブのカプセル化方針
9. 組版ジョブ → 校正ジョブ受け渡しフロー
10. 校正管理者による配分フロー
11. 校正結果の記録とオペレーター返却フロー
12. 進行管理表との紐づけ方針
13. セル座標 / ブロック管理の設計案
14. UI変更案
15. API / サーバー処理変更案
16. DB変更案
17. 既存機能を活かす方針
18. 段階的リリース案
19. リスクと対策
20. 未確定事項 / 要追加確認事項
21. 実装タスクの分解
22. Claude が次に実装着手しやすい順序

## Step 5: 保存
設計図を `z_instructions` 配下に保存してください。
ファイル名は内容が分かる名前にしてください。
例:
- `z_instructions/job-proofreading-linkage-design.md`
- `z_instructions/typesetting-proofreading-progress-table-design.md`

保存する設計書は、他の Claude が読んでもすぐ作業再開できる品質にしてください。
