# Clerk予定の複製・予定日設定 設計図

作成・更新: 2026-09-15 / Codex / 状態: 実装・自動検証完了、ユーザー画面確認待ち

## 1. 目的

ユーザーが既存の連続カレンダー・祝日設定をローカル確認済み。
追加依頼は、予定の複製と、交通費申請・外注費提出などの予定を指定条件で自動登録する「予定日設定」。

## 2. 調査結果

- `ClerkScheduleCalendar.vue`は予定詳細をeventFormへ変換し、既存store APIで新規作成できる。複製は新規フォームへ切り替える方式で実現可能。
- `ClerkEventController`は会社単位で全予定を返す。終日予定のDB終了日は包含、FullCalendarのendは翌日の排他。この変換を維持する。
- スケジュール一覧編集、モーダル編集、ドラッグ、リサイズは同じupdate APIを通る。削除も同じdestroy API。自動生成予定の個別変更は全経路で記録する必要がある。
- `Clerk/Calendar/Settings.vue`は祝日設定メニューを持つ。ここへ予定日設定を追加する。
- 参考: `Leader/MeetingDefinitions/Create.vue`、`Leader/MeetingDefinitionController.php`、`MeetingDefinition.php`、`Schedule/EventModal.vue`。
- 会議フォームのラジオ・曜日選択・複数日付追加を参考にする。会議選択処理は次回日付をフォームへ入力する方式であり、継続的なClerk予定生成エンジンとしては流用しない。
- 会社別祝日DBとClerkの色設定は既存。予定と祝日は別種の情報として扱う。
- `routes/console.php`に定期実行の既存構成がある。新たな生成コマンドを登録可能。本番スケジューラの稼働は本タスクでは未確認。
- 既存Tests\TestCaseにはsales DBを削除する処理がある。この機能のテストは前回同様、独立インメモリSQLiteを使用する。

## 3. 予定の複製

- 予定詳細に「複製」ボタンを設ける。押した時点では保存せず、「予定を複製」の入力状態に切り替える。
- タイトル、内容、色、終日属性、開始・終了日を引き継ぐ。元予定は更新しない。
- 複製元が完了済みでも新しい予定は未完了。自動登録ルールとの紐づけも引き継がず、独立予定とする。
- 複製画面で開始日を変えると、元の期間日数を保って終了日を同じ日数移動する。終了日は別途変更可能。
- 保存時のみ既存store APIで作成。キャンセルは作成しない。二重クリックを防ぐ。
- タイトルへ「コピー」等を自動付加しない（同じ項目で複製する要望に合わせる）。
- 既存UIは日付中心。時間付きの既存予定を複製する際は時刻を失わないよう保持し、終日へ暗黙変換しない。必要なら複製時のみ時刻入力を表示する。

## 4. 予定日設定の画面

導線: カレンダー設定 → 予定日設定 → 一覧 / 新規作成 / 編集。
AppLayout、headerの戻るリンク、白カード、Clerkの紫を踏襲。会議設定の入力パターンを参考にし、重複するmain/幅制限ラッパーは作らない。

共通項目:

- タイトル（必須、255文字まで）、内容（任意、2000文字まで）
- 色（既存11色と会社の色ラベルを利用）
- 指定方法（下表）
- 適用開始日（初期値はJSTの今日）、適用終了日（任意）
- 有効/停止
- 登録前の予定日プレビュー（直近12回、該当日なしの場合も明示）

| 指定方法 | 入力例 | 日付の意味 |
| --- | --- | --- |
| 毎月の日付 | 毎月25日 | 1〜31日 |
| 月末 | 毎月末日 | 2月は28/29日、その他は30/31日 |
| 毎月の曜日 | 第2火曜日 / 最終火曜日 | その月の2回目 / 最後の火曜日 |
| 日付を指定 | 2026/10/15、2026/11/20 | 日付入力から複数追加・個別削除 |

初回範囲は上の4種類。毎週・隔週は会議画面に存在するが今回の追加要望には必須でないため対象外。
生成する予定は1日単位の終日予定。参加メンバーや会議室は不要。
一覧は名称・色・条件・適用期間・有効状態・編集/停止/削除を表示する。

### 日付の境界（確認対象の推奨案）

- 「第2火曜日」は月間カレンダーの2行目ではなく、月の2回目の火曜日。入力ラベルにこの意味を明示する。
- 31日が存在しない月・第5曜日が存在しない月は生成しない。月末が必要な場合は「月末」を選ぶ。
- 土日・祝日でも指定日に登録する。前営業日/翌営業日への自動移動は今回は行わない。
- 適用期間の両端を含む。終了日が開始日より前、個別日付の重複や期間外、無効な日付は拒否する。
- 年をまたいでもルールは継続する。春分など祝日データの変更に予定を連動させない。

## 5. 自動登録・個別操作の扱い

予定は実際の`clerk_events`として保存する。既存の予定一覧、週間プランナー、CSVにも同じ予定を表示する。

### 生成のタイミング

1. ルール保存後に、開始日以降の当面18か月分を生成。開始日が未来の場合はその開始日を基準にする。終了日があればそこで止める。
2. 日次コマンドで有効ルールの今日〜18か月先を補充する。Asia/Tokyo、withoutOverlappingを使用。
3. カレンダー表示年の読み込み時にも、その年と前後の余白を補充する。Cron未設定でも画面を開けば表示範囲が埋まる。
4. プレビューは保存・生成を行わない。過去の予定を無条件に全期間生成しない。

ClerkEventController::indexに表示年の任意パラメータを追加。useClerkCalendarStripの年変更時にもイベント再取得する。既存の全件スケジュール一覧を月フィルターで削らない。
CSV出力・週間プランナーのみを開く場合も少なくとも当面の生成を保証する共通サービスを使う。

### 二重生成を防ぐ

ルール＋元の予定日を一意に記録し、同じ日に同じルールの予定を二重作成しない。手動の同名予定や別ルールには影響しない。
並行した画面読込・Cron実行でも、ルール行ロックとDB一意制約で重複を防ぐ。

### 個別の予定を変更した場合

- 自動予定を移動・内容編集したら「個別変更済み」と記録し、その回をルールの再生成で元へ戻さない。
- 完了状態は再生成でリセットしない。
- 自動予定を削除したら「この回を取り消し」と記録し、再表示・Cronで復活させない。
- 一覧編集の無変更保存を個別変更と誤判定しないよう、保存前後の実際の差分を見る。
- 複製した予定はルールから独立する。

### ルールの変更・停止・削除

- 確認文に「今後の未完了・個別変更していない予定に反映。過去・完了済み・個別変更済みは残る」と明示。
- タイトル・色・日付条件の変更は、今日以降で未完了かつ個別変更のない生成予定だけに反映する。
- 停止・ルール削除は、その条件に当たる将来分をカレンダーから除き、以後の生成を止める。過去・完了済み・個別変更分は保持。
- 停止の解除で未取消の対象日を再生成可能にする。
- ユーザーが個別削除した取消記録と、ルール変更に伴う自動整理を区別し、再開時に必要な予定まで永久に欠落させない。
- ルールの日付条件を変えた場合、残した個別変更分と新条件の予定は併存しうる。プレビュー/変更確認で保持分を案内する。

## 6. DB設計案

### clerk_schedule_rules（新規）

id / company_id / created_by / title / description / color_key / recurrence /
day_of_month(nullable) / ordinal(nullable:1〜5、最終用の値) / day_of_week(nullable:0〜6) /
custom_dates(JSON nullable) / starts_on(date) / ends_on(date nullable) / is_active /
created_at / updated_at / deleted_at。

会社ごとの管理。ルール削除は論理削除し、残した過去の予定の由来を失わない。
日付キャストはdate:Y-m-d。種類に使わない入力はサーバーで除去する。

### clerk_schedule_occurrences（新規）

id / rule_id / nominal_date(date) / clerk_event_id(nullable) /
state(generated, customized, cancelled, retired) / timestamps。
UNIQUE(rule_id, nominal_date)、clerk_event_idも重複紐づけ禁止。

- nominal_dateは移動前の生成基準日で固定する。
- cancelledは利用者が個別削除、retiredはルール変更等で整理したもの。再開時はretiredのみ再生成可能。
- generated/customizedの判定と完了済み予定の扱いはサービスへ集約。
- 手動予定に紐づきはなく、既存データのバックフィルは不要。
- ルール/occurrenceのロック順序を統一し、生成・ルール更新・個別更新/削除をトランザクションで扱う。

## 8. 検証

- 複製で元予定不変、色/内容一致、期間保持、完了解除、キャンセル時作成なし、複数日・年末・時間付き予定。
- 月末（2/28・うるう年2/29・4/30・12/31）、第1/第5/最終火曜、存在しない日、年跨ぎ、指定日複数。
- 保存直後・画面読込・Cronを繰り返しても二重作成なし。並行実行は専用テストDBが確認できる場合のみ追加検証。
- 個別移動/編集/削除/完了と設定変更・停止・再開・削除の組合せで保存内容を保護。
- CSV、スケジュール一覧編集、週間プランナー、祝日設定、会社間アクセス制御の回帰確認。
- PHPテストは独立インメモリSQLite。Tests\TestCaseやRefreshDatabaseは使わない。
- Vue/JS変更後npm run build。ローカルの追加migrationのみ適用。実画面はユーザーに確認してもらう。
- 本番配備は別途指示。新規migrationとスケジューラ確認をDEPLOY_SAKURA.mdに従って行う。SSHはコマンド提示・承認後。
