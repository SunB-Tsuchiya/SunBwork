# 部署の作業予定：非公開表示の調査

調査日: 2026-10-13。対象日: 2026-10-09。対象画面: 「予定表」→「部署の作業」→「部署の作業予定」。横断管理は `JOB_EVALUATION_CONTROL1.md` の P16。

## 方法と範囲

さくら本番のアプリで、試用権限を持つ情報出版の Super Admin 1名の視点から、`DepartmentWorkController::index()` を対象日で読み取り専用実行した。画面 API が返す `source` / `kind` / `private` と、該当レコードの公開フラグだけを件数集計した。後続の所属照合では、利用者の依頼を受けて3名の氏名・所属会社名を一時出力したが、管理資料には個人名を保存しない。予定名、本文、案件名、sales DB は出力・保存していない。既存データや権限は変更していない。

## 2026-10-09 の結果（修正前）

対象者37人の予定表示99件のうち、53件は件名が表示され、46件は「非公開の予定」。内訳は次のとおり。

| 経路 | 表示 | 非公開 | 非公開の直接条件 |
| --- | ---: | ---: | --- |
| マイジョブに紐づく `events` | 44 | 42 | 42件とも案件の `show_on_department_schedule` は有効だが、案件の `company_id` が **NULL**。閲覧者は本人・案件担当・共同管理者ではないため伏せられる。12人の予定に発生。 |
| その他の `events` | 9 | 4 | 会社共有予定で `visibility=private` が2件（2人）、従来の個人予定で `is_company_event=false`・`visibility=private` が2件（1人）。個人予定2件には予定種別があり、案件の直接リンクはない。 |
| 簡易予定 `personal_work_entries` | 0 | 0 | この日には該当表示がなかった。 |

**非公開46件のうち42件（約91%）は、極秘フラグを立てた案件ではなく、案件の所属会社IDが空欄のため自動的に伏せられたマイジョブ。** 利用者が意図する「ごく一部の極秘だけを非公開」と現在の表示は一致していない。後続の読み取り専用照合で、影響を受けた12人の所属会社・部署は全員閲覧者と同じと確認した。別会社所属の人や別会社登録の案件は、この42件にはなかった。

## 調査時点のコード上の経路

- 修正前の `PersonalWorkSchedule::eventForViewer()` はジョブ予定について、閲覧者が本人・案件担当・共同管理者でなければ、案件の会社IDと閲覧者の会社IDが一致し、かつ `show_on_department_schedule=true` の場合だけ件名を返した。NULL は一致しなかった。Super Admin であること自体は件名公開の条件に含まれない。`DepartmentWorkController::index()` の対象者は、閲覧者と同じ会社・部署に限定される。
- 簡易予定は `entryForViewer()` で行単位の `entry_visibility` と案件公開フラグを判定する。今回の対象日では簡易予定の非公開例はなかった。
- 会社共有予定は `visibility`、従来の個人予定は所有者・招待と `is_company_event` で判定する。従来の個人・社内・取引先予定は保存時に `visibility` を指定せず、DB 初期値 `private` となる経路がある。対象日の個人予定2件がどのコントローラで作成されたかは、保存データだけからは確定できない。
- `WorkloadTrialAnalysis` も同じ `private` 判定で予定を除外する。この42件のジョブ予定自体は、閲覧者の試用分析で計上されない経路に入る。別の記録による同時間の計上まではこの調査で判定していない。

## 利用者の判断と修正

利用者の意図は、TOEIC 本番データの校正のような極秘案件だけを限定的に伏せ、社内で周知の作業を管理層が把握できること。2026-10-13、案件の `company_id` が NULL でも `show_on_department_schedule=true` なら同部署の試用予定表で件名・案件名を表示すると決めた。別会社IDの案件と `show_on_department_schedule=false` の極秘案件は引き続き伏せる。明示的 `private` の会社共有予定2件・個人予定2件は非公開のままにすることも利用者が選んだ。コードでは `eventForViewer()` と `entryForViewer()` の判定を揃え、試用分析にも同じ判定を使う。帯の「【完了】」は表示時だけ取り、保存済みのタイトルと完了状態は変えない。案件の会社IDが NULL になった作成・移行経路と、既存案件をどう補完するかは後続調査とする。

訂正履歴: 最初の集計では `NULL` と「別会社のID」をまとめて不一致と数え、「別会社の案件が主因」と誤記した。2026-10-13 の追加照合で42件すべて `project_jobs.company_id=NULL` と確認し、上記のとおり訂正した。会社IDが空欄になった理由は未調査。
