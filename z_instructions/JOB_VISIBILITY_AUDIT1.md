調査日: 2026-10-13。対象日: 2026-10-09。対象画面: 「予定表」→「部署の作業」→「部署の作業予定」。横断管理は `JOB_EVALUATION_CONTROL1.md` の P16。

## 方法と範囲

さくら本番のアプリで、試用権限を持つ情報出版の Super Admin 1名の視点から、`DepartmentWorkController::index()` を対象日で読み取り専用実行した。画面 API が返す `source` / `kind` / `private` と、該当レコードの公開フラグだけを件数集計した。後続の所属照合では、利用者の依頼を受けて3名の氏名・所属会社名を一時出力したが、管理資料には個人名を保存しない。予定名、本文、案件名、sales DB は出力・保存していない。既存データや権限は変更していない。

## 調査時点のコード上の経路

- 修正前の `PersonalWorkSchedule::eventForViewer()` はジョブ予定について、閲覧者が本人・案件担当・共同管理者でなければ、案件の会社IDと閲覧者の会社IDが一致し、かつ `show_on_department_schedule=true` の場合だけ件名を返した。NULL は一致しなかった。Super Admin であること自体は件名公開の条件に含まれない。`DepartmentWorkController::index()` の対象者は、閲覧者と同じ会社・部署に限定される。
- 簡易予定は `entryForViewer()` で行単位の `entry_visibility` と案件公開フラグを判定する。今回の対象日では簡易予定の非公開例はなかった。
- 会社共有予定は `visibility`、従来の個人予定は所有者・招待と `is_company_event` で判定する。従来の個人・社内・取引先予定は保存時に `visibility` を指定せず、DB 初期値 `private` となる経路がある。対象日の個人予定2件がどのコントローラで作成されたかは、保存データだけからは確定できない。
- `WorkloadTrialAnalysis` も同じ `private` 判定で予定を除外する。この42件のジョブ予定自体は、閲覧者の試用分析で計上されない経路に入る。別の記録による同時間の計上まではこの調査で判定していない。

## 会社ID空欄の案件についての追加集計（2026-10-13）

利用者が承認した読み取り専用 SSH 集計で、同じ10/09の部署一覧にある、案件会社IDが NULL のマイジョブ予定を再抽出した。現在の抽出は**非公開だったものだけに限定しない**ため45予定であり、修正前の「非公開42件」とは母集団が異なる。この差を新規予定3件の増加とは解釈しない。45予定が紐づく案件は2件。両案件に取引先IDがあり、取引先そのものは未登録ではない。取引先の会社IDは、一方が NULL、もう一方が閲覧者の会社と一致した。案件の `creation_method` は `legacy` が1件、NULL が1件。両案件の `created_at` は会社ID追加 migration ファイルの日付（2026-05-30）以降だが、migration の実行日や個々の案件の作成経路までは確定しない。氏名・案件名・予定本文・sales DB は出力していない。

コード上、現在の通常登録・一括登録は案件へ会社IDを設定する。2026-05-30 の migration は、当時の取引先の会社IDを案件へ補完するため、取引先側が空欄なら案件側も空欄のままになり得る。案件複製は元案件の会社IDを引き継ぐ。一方、取引先に現在会社IDがあるもう1件については、後から取引先だけ補完された可能性などがあり、NULL が残った直接経路をこの集計だけでは断定できない。**「クライアント未登録が原因」との説明は支持されない。** 既存案件の会社IDは更新していない。

## 会社IDの作成経路を再点検（2026-10-18、コードのみ）

現行の Coordinator 案件通常登録・テンプレート登録・一括登録・共有登録と MGinbon 専用登録は、案件へ会社IDを明示する。複製は元案件の会社IDをそのまま引き継ぐため、元が空欄なら複製先も空欄になり得る。

登録ルートのある `Coordinator/ProjectJobCsvController::importCsv()` は `ProjectJob::insert()` の行に `company_id` を入れておらず、**今後もCSV登録で会社ID空欄の案件を作り得る**。現行コードは `creation_method=csv` を保存するが、この代入が加わったのは2026-10-10。対象案件はそれ以前の作成なので、`legacy` と記録されていても当時のCSV経由を除外できない。以前の「現行CSVは `csv` と保存するため、対象2案件の直接原因とは言えない」という説明は、過去のコードに当てはめられないため訂正する。`EventController` の「その他」共通案件も会社IDを空欄で作るが、共有の既定案件であり、この2案件と同一とは確認していない。`MyProjectJobController::store()` にも会社ID設定がないが、現在の `routes/web.php` にはこの `store()` への登録ルートが見当たらず、現行の有効な作成経路とは断定しない。

`creation_method=legacy` は作成画面・取込経路の名称ではない。2026-10-10 の作成者列追加 migration が、以前の案件の現リーダーを作成者の代理として `creator_source=legacy_leader` に設定し、その後の方式列追加 migration がその行を `legacy` にした。したがって対象の1案件は作成者追跡開始前から存在したことは分かるが、当初の登録経路まではこのラベルから分からない。NULL のもう1案件も、この値だけでは経路を判定できない。

この再点検はリポジトリのコードだけを読んだ結果で、本番データの再調査・更新はしていない。2案件の直接の作成経路は未確定。次に対象候補の作成日・作成元・会社IDと取引先の現在の会社IDを、件名・本文なしのメタデータで照合する。取引先の `updated_at` は最終更新時刻で、会社IDを設定した日時の証拠とは限らない。その後、CSV新規登録の会社ID欠落防止と既存案件の補完を別々に判断する。会社共有の「その他」案件へ安易に会社IDを一括設定しない。
