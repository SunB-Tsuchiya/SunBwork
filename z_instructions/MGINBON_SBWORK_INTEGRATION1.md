# MGinbonとSBWork既存機能の接続調査

## 1. 結論

銀本制作進行管理は、既存の`progress_sheets / progress_rows / progress_cells`だけを拡張して
構築せず、MGinbon専用の正規化データを正本とする。そのうえで、担当作業を既存の
`project_job_assignments`へ、実作業時間を`events`へ接続する。

MGinbon正本はSBWork本体DBではなく、専用MySQL接続`mginbon`に置く。年度は専用DB内の
年度プロジェクトで分離する。本体DBのユーザー、外注先、Assignment、Event、NSystem学校・試験との
関連IDは保持するが、接続をまたぐ外部キー制約は作らず、アプリケーションサービスで整合性を検証する。

既存進行管理表は表示・操作の実績があるため、セルUI、担当者選択、外注先選択、ジョブ登録、
完了、工数表示等をMGinbon専用画面で再利用する。ただし、汎用セルをMGinbonの正本にはしない。

```text
専用DB: MGinbon年度プロジェクト／制作単位／媒体／科目／工程（正本）
                    │
                    ├─ 担当作業ID ─ 本体DB: project_job_assignments
                    │                  └─ events（予定・実績時間）
                    │
                    ├─ 実施先ID ─ 本体DB: users / departments / subcontractors
                    ├─ 学校・試験ID ─ 本体DB: NSystem
                    │
                    └─ 日次作業実績 ─ 日報表示用集計・候補
```

## 2. 既存進行管理表で再利用できる機能

- `progress_sheets.column_config`は階層化した可変列を持てる。
- `progress_rows`は親子行と並び順を持てる。
- `progress_cells`は文字、日付、真偽値、社員、外注先を保持できる。
- `worker`セルは社員または外注先を選び、担当ジョブを作成できる。
- `proof_user`／`proof_v2`は校正担当と校正ジョブに対応する。
- セル単位で期限、メモ、完了日時を持てる。
- 担当ジョブに紐づく`events`から作業時間を集計して進行表へ表示している。

これらの操作パターンとUI部品はMGinbonでも再利用価値が高い。

`project_job_assignments`はJobBoxとMyJobBoxの共通正本で、社員、外注先、工程、状態、数量、
期限、継続関係を保持する。`events.project_job_assignment_id`により、MGinbonのOP・校正担当も
担当件数と作業時間を集計できる。

既存`subcontractors`は会社、担当Coordinator、対応部門、JobBox割当を持つ。MGinbonの文字入力・
作図・スキャンを社外へ依頼する場合はこのマスターを参照し、重複マスターを作らない。

## 3. 既存テーブルだけでは不足する理由

汎用進行表の行・列・セルには、次の恒久的な業務識別情報がない。

- 年度と販売形態（書店向け印刷物／α版デジタル）
- 学校または冊子共通部品、問題冊子／解答冊子
- 媒体と科目
- `初校校正`、`校正①`、`再校出`、`校正②`等の工程ID
- FileMaker原列、原値、取込回、補正履歴
- 流用元年度・流用元制作物
- 科目別の図版数（scan／drawing×社内／外注）と将来の外注費算出根拠

これらを`col_key`や表示ラベルだけで判定すると、列名変更、年度複製、集計、再取込時に
意味が壊れる。MGinbon専用テーブルを正本とし、表示列は工程定義から生成する。

## 4. 推奨する接続方式

### 4.0 既存NSystemとの接続

SBWork内にはすでに、恒久学校`n_schools`、年度別学校`n_school_years`、入試回系列
`n_exam_series`、年度別試験`n_exams`、年度版掲載行`n_publication_entries`がある。
新規作業管理はこの学校・試験体系を共用し、学校マスターを重複作成しない。

- FileMakerの日能研コード → 年度と合わせて`n_exams.n_code`
- FileMakerのみくにコード → 年度版と合わせて`n_publication_entries.mikuni_code`
- 学校名 → `n_school_years.school_name`を照合補助に使用
- 入試回別制作単位 → `n_exams.id`を参照
- 傾向と対策等の学校共通制作単位 → `n_schools.id`を参照し、第二回等へ複製しない

NSystem側からSunBWork業務テーブルへの外部キーは追加しない。銀本作業管理側の接続テーブルから、
NSystemの試験IDとSBWorkの担当ジョブIDを参照し、既存の検索・公開機能を分離したまま連携する。

### 4.1 年度プロジェクト

- 1年度の中学入試全体をMGinbon年度プロジェクトとして作成する。
- 必要に応じて既存`project_jobs`へ1対1で接続し、権限、Coordinator、チーム、JobBox、
  カレンダーの入口を利用する。
- 535件をそれぞれ独立した`project_jobs`にはしない。既存画面と集計を過密にするためである。

### 4.2 MGinbon工程作業と担当ジョブ

- MGinbon工程作業を正本とし、担当や予定作業が必要になった時だけ
  `project_job_assignments`を作る。
- MGinbon工程作業側に`project_job_assignment_id`を持たせる。
- 同一担当が4科目をまとめて行う場合は、複数工程作業をMGinbon作業パッケージへまとめ、
  パッケージから1件の`project_job_assignment_id`を参照する。
- OP、初チェック、初校校正、校正①、校正②、赤字照合等は社員担当ジョブへ接続できる。
- 文字入力・作図・スキャンの外注は`subcontractor_id`付き担当ジョブへ接続できる。
- 社内製版のように個人管理しない作業は部門・実施区分・状態だけでも完了可能にし、
  架空ユーザーへ割り当てない。
- 前年度流用は担当ジョブを必須にせず、流用元を記録して完了できる。

### 4.3 再校工程順

```text
初校出稿
→ 初校校正（初校出稿後の文字突き合わせ）
→ 初校戻り・初校修正
→ スキャン画像反映
→ 校正①（スキャン図照合）
→ 再校出稿
→ 校正②（再校出稿後の文字突き合わせ）
→ 再校戻り・再校修正
→ 校正（赤字照合）
→ 三校出稿
```

前後関係は警告や表示順に用いるが、例外案件の入力を完全にはブロックしない。

## 5. 日報・日々の作業レポートとの接続

現行`diaries`は日付と自由記述本文が中心であり、MGinbon工程別集計の正本には適さない。
`work_records`は1人1日単位の勤務開始・終了等を管理し、案件別作業明細ではない。

初期接続は次の構成とする。

1. ユーザーが銀本担当ジョブをカレンダーへ登録する。
2. `events`に開始・終了・中断時間が記録される。
3. MGinbon画面では担当者、学校、媒体、科目、工程別に実績時間を集計する。
4. 日報画面には、その日の銀本実績を構造化された作業候補として表示する。
5. ユーザーが確認して日報本文へ反映する。自由記述を自動で上書きしない。

MGinbon進行表から学校・媒体・科目・工程を選んで既存の依頼ジョブを作成し、作業者は
JobBox／MyJobBoxからカレンダーへ登録する。作業時間は`events`だけを正本とし、MGinbon専用の
分数直接入力は設けない。

現物を手渡された作業者本人が、作業用進行表から該当する学校・媒体・科目・工程を選び、
自己割当Assignmentを作成する。自己割当とカレンダー作業登録は分離し、現物受領・担当確保だけでは
`校正入り`を記録しない。最初にカレンダーへ登録したEventの作業日を`校正入り`、カレンダーの
既存完了操作の対象EventのJST作業日を`校正UP`として管理台帳へ自動反映する。

複数日にまたがる場合は既存の「続き作業」を使い、`source_assignment_id`でAssignment系列を接続する。
最後の続き作業を完了した際の祖先完了カスケードを利用してMGinbon工程を完了し、系列のEvent時間を
合算する。`supersedes_assignment_id`は依頼ジョブ置換用であり、続き作業には使わない。

既存進行表はセル↔Assignmentを`progress_cell_id`／`assignment_id`、カレンダーを
`events.project_job_assignment_id`で接続している。カレンダー完了はAssignment、続き系列の祖先、
進行表の完了表示へ戻る。MGinbonではこの連動経路を再利用し、完了処理からMGinbon作業パッケージと
工程タスクを同期する。既存`progress_cells`をMGinbonの正本にしたり、画面側だけで完了扱いにしたりしない。

問題・解答のように4科目セットで動く作業は4科目を既定選択し、α版の解説解答・傾向と対策等は
選択科目のみを既定とする。どちらも登録前の科目チェックで変更できる。4科目一括時もAssignmentと
Eventは1組とし、4つの工程タスクへ担当・状態・節目を反映する。実績時間はパッケージ全体として
集計し、科目別へ機械的に等分しない。

## 6. MGinbon専用画面

同じMGinbonデータから、責務を分けた二つの表と既存ジョブ画面を生成する。

- 管理台帳: FileMakerのLIST型横方向表。入稿チェック等は保存ビューとして切り替える
- 作業用進行表: Coordinator進行表型。必要な作業セルを選びAssignmentを作成する
- JobBox／MyJobBox: 自分の担当作業、期限、状態、カレンダー実績登録

本番進行表ID 5では531行のうち入力済みセル52、Assignment 51、Event接続50であり、
必要なセルだけを作業化する運用が成立している。MGinbonも疎な作業表を採用する一方、
全日付・点数・工程を管理するFileMaker型台帳は別表示にする。両者は同じ正規データを使い、
管理者による再入力を発生させない。旧進行表の保存形式上の互換仕様は模倣しない。

担当者、外注先、媒体、科目、工程、状態は検索可能なドロップダウンとする。候補外の旧値は
取込警告として残し、人が対応候補を選ぶ。

## 7. 権限の基本方針

- SuperAdmin／Admin／Leader／Clerk／Coordinator: 年度設定、取込、全体閲覧・編集、担当割当、
  外注設定、集計、共有URL管理を同じ権限で行う
- Proof Admin（`proof_coordinator`）: 全体閲覧、校正担当・校正入り・校正UP・校正状態等の
  校正関連項目だけを編集
- User: 全対象行・空き作業の検索、該当セルへの自己登録、自分の担当作業・状態・実績時間の入力
- 外注先: 直接ログインさせず、社内担当者が状態・日付・点数を管理
- みくに出版: 読み取り専用のトークンURLで公開対象の進捗のみ閲覧

上記5つの管理ロールはMGinbon内では上下差・部署スコープ差を設けず、既存`CoordinatorMiddleware`の
許可ロールに合わせる。Proof Adminは別枠の認可で校正関連フィールドだけを更新可能にし、
フロントで隠すだけでなく更新API側でも許可フィールドを制限する。

既存進行表の共有URLは、ランダムトークン、認証不要、読み取り専用、印刷、即時無効化に対応する。
MGinbonはこの操作パターンを再利用する。ただし既存共有レスポンスは担当者名・外注先名・セルメモも
含むため、そのまま流用せず、専用公開コントローラでallowlist項目だけを返す。
