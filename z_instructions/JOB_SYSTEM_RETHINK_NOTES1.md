# ジョブ・作業記録・評価の見直しメモ

更新: 2026-10-13。利用者の途中の発言を落とさないための履歴表。横断の現在位置、置き換わった方針、保留案は `JOB_EVALUATION_CONTROL1.md` に記す。この表の「独立試用」「確認印」「本番未反映」は当時の状態を含み、現在の実装状況として単独で引用しない。

## まず読む概要

- 依頼されたジョブをマイジョブへ取り込み、本人作成のジョブもマイジョブに統一する。
- 進行管理は伝票・個々のテストを細かく管理する。オペレーターと校正は「カリキュラムテスト」「教材」「テキスト」など大枠から仕事を探せればよい。
- 作業の記録はその都度でも一日の終わりでも同じ入力を使う。作業の切替やファイル返却時にも短く残せるようにする。
- 進行管理の必須作業は、作業者が選べる「本筋」の案件作成とメンバー登録に絞る。支流の伝票・個別案件、依頼・予定は必要な場合に扱い、本人のマイジョブ登録を止めない。
- 上長と実際のデータ・作業例を確認するまで、Super Admin だけの試用にとどめる。カレンダー簡易予定は試用分析と日報タイムテーブルには現れるが、旧作業量分析の点数や日報本文へ自動で混ぜない。

- 2026年8月〜10月11日は、同条件の新規割当・送信が0件。同期間も本人作成マイジョブは3,552件ある。4月〜10月11日の本人作成マイジョブは計7,808件。
- 割当作成数には未送信のものが含まれる。転換4件は明示的な参照による確認数で、古い紐付け方まで含む総数とは限らない。実態は「依頼を必須にしなくても本人登録が続いている」。

## 当時の設計案と継続検討事項

以下には現在置き換わった案も含む。実装順序と採否は `JOB_EVALUATION_CONTROL1.md` の D01〜D07、W01〜W07 を優先する。

- 画面は「届いた依頼」→「マイジョブに入れる」→「自分のジョブ」→「その日の作業記録」という順にする。
- **旧案（置換済み）:** 短い必須項目・日報時の一日確認・途中の入力を独立試用で検証し、正式導入時に既存マイジョブの入力画面を置き換える。現在はカレンダー簡易入力の実例確認を先に行い、後でマイジョブ、依頼ジョブの順に整理する。依頼からの転換経路と履歴は保持する。
- 現行コードでは本人のジョブ登録先は `ProjectJob` で、登録画面はチーム所属の案件を候補に出す。したがって、本筋を選択可能な `ProjectJob` として作り、メンバーを紐付ける案を先に検証する。支流の `ProjectJob` が未登録でも、本筋へのマイジョブ登録ができることを必須条件にする。
- 作業者には通常、本筋の名前と短い作業内容だけを選ばせる。伝票・個別テスト・細かなジョブ名は、本人が必要とする場合か、進行管理が既存の依頼を出した場合に使う。本筋の記録を後から特定の支流へ自動で振り分けない。
- 大枠と伝票の紐付け方は実例を見て決める。同じ名称の本筋は取引先・年度で分ける。現行 `ProjectJob` に大枠の親子関係はなく、`shared_from_id` は部署間共有のため流用しない。
- 大枠だけの作業記録から、どのテスト・伝票の成果かを推測して点数化しない。集計では一つの作業を一度だけ数える。
- 現行マイジョブは翌日に自動完了する場合があるため、その `completed` を本人が仕事を終えた証拠として使わない。

## 最終確認の進め方

1. 新しい発言が出るたびに ID を追加し、確定した方針か検討案かを明記する。
2. Super Admin 試用で、短期大量案件、長期案件、別テストを行き来する日、ファイル返却、校正を実例照合する。
3. 各 ID に実装画面・保存先・権限・上長との確認結果を追記する。未対応の ID がある間は全員向け公開を完了扱いにしない。
