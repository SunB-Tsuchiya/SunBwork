# 年末調整Web入力フォーム 設計図(Claude Code / Codex 用ブリーフ)

## 0. この文書の読み方

- 目的: **自社ポータル上で従業員に年末調整の控除申告をWeb入力させ、国税庁のXML定義書形式でデータ保存・エクスポートする**フォームを作る。PDF印字は本年度やらない。計算(e-Tax提出・年調計算)は税理士側が行う。
- 一次情報はすべて国税庁が公開している仕様書。**この文書の項目リストより、必ず一次資料の記載を優先**すること。本書は「何をどの資料から読み取るか」の地図である。
- 画面レイアウト・デザインは指定しない。**実装先サイトの既存デザインシステム(コンポーネント・トークン・ナビゲーション)に合わせる**こと。新規のUI設計をしない。

## 2. スコープ

**今回作るもの(Phase 1: 今年の年末調整)**
1. 従業員向け入力フォーム(申告内容のWeb入力)
2. 控除証明書XML(保険会社からダウンロードしたファイル)のアップロード受入 → 項目自動入力
3. 入力データのDB保存(年度版管理・前年引継ぎ)
4. 申告書XML定義書準拠のXMLエクスポート(税理士へ渡すファイル)
5. 管理画面(回収状況一覧・差戻しコメント・エクスポート)

**今回やらないこと(Non-goals)**
- **年調計算ロジック(税額計算)を実装しない** — 税理士側の担当。毎年の税制改正追従コストが常態化するため意図的に外す(FAQ 問5-21:税制改正で計算ロジックは毎年変わり得ると明記)
- PDF帳票への印字出力 — 後回し(決定済み)。ただし後で追加するため、帳票用レンダラを入れずともデータ構造から破綻しない設計にする
- e-Tax / 光ディスク提出、法定調書作成 — 税理士側
- マイナポータル連携(仕様公開申請・連動テストが必要) — Phase 2
- 国税庁「年調ソフト」への取り込み前提にしないこと(FAQ:年調ソフトは年調ソフト自身が作成したデータしかインポート不可。自作XMLの受け手は税理士側ソフト)

## 3. フォームが扱う申告書(8種)

XML定義書の NTAAPP001〜008 に対応。フォームは1画面1申告書ではなく、年調ソフトの帳票設計書のフローに倣い**質問形式で一貫入力**させ、該当する申告書データを裏で分岐生成する。

- 給与所得者の扶養控除等(異動)申告書
- 給与所得者の配偶者控除等申告書
- 給与所得者の基礎控除申告書
- 所得金額調整控除申告書
- 給与所得者の特定親族特別控除申告書
- 給与所得者の保険料控除申告書
- 住宅借入金等特別控除申告書
- 従たる給与についての扶養控除等(異動)申告書

## 4. 入力項目の構成(上位グループ。正確な項目・桁数・コード値は帳票設計書とXML定義書から抽出)

1. **従業員基本情報** — 氏名、住所、マイナンバー、中途就労/退職の有無、障害者の区分、 本人が特定親族特別控除対象か 等
2. **会社側が事前投入する情報(従業員に入力させない)** — 支払金額、社会保険料等、源泉徴収税額、勤務開始日等。人事データまたはCSV取込で管理者が投入し、フォームでは参照のみ
3. **扶養親族(繰り返し行)** — 氏名、続柄、生年月日、マイナンバー、住所、障害区分、所得の見積り、16歳未満/23歳未満判定フラグ(令和8年改正で扶養親族の所得要件が58万→62万に変わる点に注意。判定は固定値を埋め込まず**設定ファイル化**して年度ごとに差し替え可能に)
4. **配偶者** — 氏名、マイナンバー、住所、合計所得の見積り、学生以外の特定対象者該当 等
5. **保険料控除(繰り返し行)** — 生命保険:旧契約/新契約×一般/介護医療/個人年金の区分、保険会社名、契約者・受取人。地震保険:保険会社、契約者、保険期間、保険料(長期損害保険料を含む)。**控除証明書XMLアップロードで自動入力できた場合は手入力欄を閉じる/上書き確認にする**
6. **寄附金** — 受付団体名・金額(ふるさと納税を含む特定寄附金の区分)
7. **住宅借入金等特別控除(繰り返し行)** — 居住開始年ごとの借入金年末残高、住宅の種別、(特定増改築等)該当、住民税の住宅ローン控除に関する事前申告の要否
8. **添付・確認** — 控除証明書XMLのアップロード(複数可)、最終確認画面、送信

バリデーションは必須/型/桁数/コード値を**XML定義書の制約から自動生成**する(Excel→JSON→バリデーションスキーマ)。帳票設計書の質問フローも併読して、XMLだけでは分からない依存関係(例:「保険料控除を申告しないなら保険の行は不要」)を補う。

## 5. データモデル・XMLエクスポート

- DB: `employee`(社員マスタ) / `nencho_submission`(年度+社員ID+ステータス: 下書き/提出済/差戻し) / `nencho_answer`(申告書種別×項目) / `nencho_file`(アップロード証明書) / `nencho_audit`(差戻し・承認履歴)
- 年度を**必ずスキーマに持たせる**(様式・コード値が年度ごとに変わるため)。前年引継ぎは「前年度 submission の回答を初期値コピー + 変更点だけ修正」で実装
- 保存義務:データで受領した年末調整関係書類は**提出期限の年の翌年1月10日から7年間**(FAQ 問2-16)。削除は7年経過後に行う設計
- マイナンバーはフォーム上で入力必須だが、一覧表示はマスク、DBは暗号化、閲覧権限は管理者のみ(社内規定・税理士との共有方法は別途確認)
- XMLエクスポート: 申告書XML定義書(令和8年10月版)のタグ構造に厳密準拠。サンプルデータ(ダミー従業員1名分)を生成し、定義書の制約に対する**自動検証テスト**を作る。文字コード・1従業員1ファイルか一括か・拡張子/圧縮/署名の要否は**税理士側ソフトの受入仕様を確認してから確定**(税理士のソフトが年調ソフト形式XML/CSVのどれを受け付けるかで実装が変わる。現時点は定義書準拠のXMLを出す仮実装+仕様差替え可能な作り)

## 6. 実装前に把握しておく制約(出典: 開発者FAQ nencho_faq.pdf)

- 年調ソフトへの自作データのインポートは不可(§2 の通り)。受け手は税理士側
- XML定義書・様式は**毎年10月頃に更新**される。定義書のパース→JSON生成をスクリプト化し、来年は差分確認だけで済む運用にする
- 適用する控除によっては証明書類の保存が別途必要(FAQ 問1-11 等)——税理士と確認
- 税制改正による入力項目・判定値の変更(令和8年分は基礎控除引上げ・扶養親族所得要件62万円・23歳未満扶養ありの生命保険料控除特例)が令和8年10月版定義書に反映済み。**必ず令和8年10月以降公開の版を使う**(古い版で作ると計算誤り。FAQ 問5-37 付近の警告参照)

## 7. エージェントへの作業指示(実行順)

1. `docs/nta/` に上記資料をダウンロードし、XML定義書(NTAAPP001〜008)と帳票設計書、hosoku.xlsx を openpyxl で読み、定義JSONとバリデーションスキーマを生成 → **その時点で人間に概要を報告してから先へ進む**
2. データモデル(§5)を実装先フレームワークで定義し、マイグレーションを作成
3. フォーム実装:既存サイトのデザインシステム/コンポーネントのみを使用。レイアウトを新規設計しない。質問フローは帳票設計書の順序に従う
4. 控除証明書XMLアップロード機能(hosoku.xlsx 準拠のパース・取込)
5. XMLエクスポートモジュール + ダミーデータでの検証テスト
6. 管理画面(回収状況・差戻し・エクスポート・CSV概算一覧)
7. 全体を `make verify`(バリデーション→エクスポート→検証)で通ること
