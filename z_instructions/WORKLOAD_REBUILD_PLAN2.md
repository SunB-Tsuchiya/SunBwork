# WORKLOAD_REBUILD_PLAN2 — 簡易順位と詳細分析の分離

作成日: 2026-10-11。`WORKLOAD_REBUILD_PLAN1.md` の本番試用結果を受けた次段階の設計。実装前の確認用。

## 目的

- 予定表の「作業実績の内訳」は、日・週・月の状況と暫定順位をひと目で見る簡易画面とする。
- メニューの「作業量分析」は、点数の根拠と欠測を確認できる詳細画面へ作り直す。旧分析のページ数・サイズ・難易度による順位を新方式へ流用しない。
- 旧分析のコード・表示は「旧方式アーカイブ」として読み取り専用の別入口に残す。再計算結果であって過去時点の固定スナップショットではないことを明示し、新方式の点数と混同しない。
- 最初は情報出版の Super Admin 試用で検証し、利用者向け公開と旧メニューの切替は実データ照合後に行う。他部署の既存分析と権限は試用中に変えない。

## 実データから分かったこと

- 情報出版の7〜9月では、記録時間、記録件数、管理案件数のいずれか一つだけでは職種間の仕事を比べられない。入力を求めていないアカウントも混在する。
- 現行試験点は記録時間由来の基本点が順位を大きく左右する。管理案件加点を一律に下げても、実作業者とのずれは残る。
- 旧総合点はページ数を複数カテゴリへ重ね、各カテゴリの相対順位を合計する。自己登録ジョブの二重経路もある。旧画面の上位作業者は校正の手がかりにはなるが、旧点数を正解値として使わない。
- 管理案件数が多いことは進行管理の職務上自然。継続して作業を記録する校正・オペレーターの実務を比較の基準にし、進行管理の記録した作業と補助点を分けて照合する。個人名と個別の本番値は文書・Seeder に保存しない。

## 二つの画面

| 画面 | 主な表示 | 判断に使う粒度 |
| --- | --- | --- |
| 予定表の簡易順位 | 日・週・月、作業区分の色、暫定点、順位、未入力の注意 | その日の状況と推移を素早く見る |
| 新しい作業量分析 | 月別と複数月の比較、個人・担当・作業種類・入力元ごとの実績、記録率、重複除去後の時間、工程候補数、案件管理、登録、残業、暫定点の内訳 | 点数が実態からずれる理由を調べる |
| 旧方式アーカイブ | 旧6カテゴリと旧順位・旧ガイド。旧式と明記し編集操作を置かない | 過去方式との照合に限る |

## 新しい分析の集計原則

1. マイジョブ、依頼ジョブ、結果入力済み簡易作業、仕事の会議を入力元別に示す。簡易実績が既存イベントから作られた場合は同一作業として扱う。案件の非公開設定と部署・会社の閲覧境界は `PersonalWorkSchedule` / `WorkloadTrialAnalysis` の既存判定を共有する。
2. `project_job_assignments.completed` は自動完了を含むため、完了工程の直接の証拠にしない。記録件数は当面「入力件数」と明示し、工程候補数は案件・作業種類・日付・元イベントの関係で重複を整理した試算として別表示する。工程の分割登録で無制限に点が増えないようにする。
3. 数量は同じ作業種類・同じ単位の内訳に限って表示する。案件全体のページ数が含まれるため、ページ数を総合点や職種横断順位の直接係数にしない。
4. 記録時間は昼休憩・重複を除いた補助指標とし、勤務枠の未記録時間を別表示する。残業は勤務記録と作業記録が重なる分だけ別枠で示す。時間だけで能力・成果を決めない。
5. 案件管理は活動案件数、活動日、チーム人数、登録件数をそれぞれ表示する。進行管理の点数は作業実績の点と管理・登録の補助点に分け、補助点オン／オフで順位変化を見せる。管理案件数そのものを基準値にしない。
6. 入力を求めていない人は順位・人別一覧から除外する。既存 `user_employment_settings.ranking_included` と `workload_tracked` を明示的に利用し、未設定時の暫定既定値は正社員・契約社員を対象、派遣・業務委託を対象外とする。個別設定で例外を許す。対象外人数は匿名の集計値として表示する。
7. 職種の登録名と実際の作業種類を別々に示す。兼務者を登録名だけで校正・オペレーター・進行管理へ固定しない。

## 係数の校正方法

- 最初に6か月分を月別で再計算し、入力対象者の記録率と作業種類の偏りを見る。旧方式との一致率を成功指標にはしない。
- 継続入力者の実作業を比較の基準として、基本点のみ・管理点追加・登録点追加・残業点追加の各順位を並べる。基準となる個人名をコードやDB設定へ固定しない。
- 総合点の係数変更は、校正・オペレーター・進行管理の実務と管理者の観察を複数月で照合してから行う。現行10点/時や0.5点/管理活動日の値は試験値として保持し、新方式を確定値と表示しない。
- 0点は「未入力・対象外・対象期間外」を区別して表示し、仕事をしていないという断定を避ける。

## 実装段階と主なファイル

1. 旧方式を分離: `routes/web.php`、`app/Http/Controllers/Leader/WorkloadAnalyzerController.php`、`resources/js/Pages/WorkloadAnalyzer/*`。現行の旧コードを参照用クラス・ページへ保全し、新しいメニューから通常操作で到達しないようにする。旧設定の編集はアーカイブ入口に置かない。
2. 共通集計: `app/Services/WorkloadTrialAnalysis.php` の既存の時間・公開判定を再利用し、入力元・工程候補・記録率・対象判定を別サービスへ分ける。月別の同一入力を二重に数えない。
3. 詳細APIと画面: 新しい管理者用コントローラーと `resources/js/Pages/WorkloadAnalyzer/` の新ページ。月／複数月、担当・作業種類・入力元フィルタ、人別根拠を表示。`AppLayout` の `fluid` を使う。
4. 予定表簡易画面: `DepartmentWorkController` と `Schedule/WorkAnalysis.vue`。詳細分析と同じ集計バージョンを参照し、現在の表示密度は維持する。詳細画面への導線は Super Admin 試用中だけ見せる。
5. 検証・切替: `CONSOLIDATED_07_workload_and_handover.md`、ガイド、変更履歴。旧 URL は切替段階で新画面へ向け、アーカイブ URL は権限保護する。一般向け更新ログへの掲載は公開時に行う。

## 検証・移行の条件

- 権限: 他社、他部署、非公開案件、入力対象外、旧アーカイブのアクセスを確認する。情報出版以外の画面は新方式を公開するまで変えない。
- 集計: 簡易実績と元イベント、自己登録・依頼ジョブ、共有会議出席者、重複時間、昼休憩、校正イベントのUTC保存、A/B/C勤務、月境界を確認する。
- 実データ: 個人名や案件名を保存せず、月別の集計傾向を管理者の観察と照合する。新しい総合点の単独順位を評価査定へ直結させない。
- Vue/JSの変更後は本番用のビルド設定で生成物を検証する。既存の汚れた `public/build` と `storage` を上書きしない。通常の PHPUnit はローカル `sales` 接続に影響するため、安全なテスト経路を確認してから実行する。
