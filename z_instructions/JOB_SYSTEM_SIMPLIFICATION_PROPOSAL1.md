# ジョブ・作業記録の簡素化案 1

作成: 2026-10-11。検討用。現行画面・本番DB・採点式の変更を指示するものではない。

2026-10-13 利用者が方針を再確認: 大枠のテストを「本筋」として先に登録し、細かな案件は必要な場合だけその下に作る。作業は本筋・細かな案件のどちらにも登録できるようにする。10/09の非公開予定42件に紐づく案件では所属会社IDが空欄と分かった。利用者はこれを細かな案件入力の負担を示す材料と捉えたが、クライアント未登録が空欄の直接原因かは未確認。親子関係の実装と既存データの整理は別工程。

## まず読む概要

1. **記録を止めない。** 進行管理が「本筋」の案件とメンバーを用意すれば、支流の伝票・個別案件・ジョブ依頼を待たずに作業者が記録できるようにする。本筋も未登録なら、当日の簡易記録は仮の案件名で残せるようにする。
2. **入力を一度にする。** 作業者は同じ画面で、随時の短い記録と日報時のまとめ入力を行う。マイジョブの本人登録と依頼取り込みは同じ一覧へ寄せる。既存の依頼→マイジョブ転換は再実装しない。
3. **連動は必要な時だけ。** 伝票、取引先、進行表、予約、カレンダーとの紐付けは明示されたものだけ使う。未登録や推測による自動振り分けを、記録・日報の保存条件にしない。
4. **評価は記録の質を確かめてから。** 暫定点や件数を直ちに人事評価へ転用せず、入力状況、作業内容、上長が確認できる成果を分けて見る。Super Admin 試用と上長照合を続ける。

## 今の仕組みから確認したこと

| 領域 | 確認結果 | 改善案への意味 |
| --- | --- | --- |
| 案件とマイジョブ | `project_jobs` が本人のジョブ登録先。登録画面は主に本人がチーム所属する案件を候補に出し、保存ルートは `ProjectJob` を要求する | 本筋の案件とメンバーを先に用意すれば、支流なしで現行マイジョブを使える。案件自体がない場合は別の短い入口が必要 |
| 依頼と本人登録 | `project_job_assignments` が共通の保存先。依頼の取り込みには `supersedes_assignment_id` がある。依頼一覧は送信メッセージに依存する | 成立している依頼経路は残す。依頼を本人登録の前提にしない |
| 実際の利用 | さくら本番の読み取り専用集計では、2026年8月〜10月11日の新規依頼送信は0件でも、本人作成マイジョブは3,552件 | 自己登録を主導線にする根拠。ただし職種別の使い方は試用で確認する |
| 簡易作業と日報 | `personal_work_entries` は案件IDなし・自由入力の案件名を保持できる。日報の作業行は作業種類、実績時間、結果文を要求する。現在は試用権限に限る | 仮記録の土台がある。必須入力と日報時の操作数は現場例で減らす余地がある |
| 伝票・予約 | `PrepressTicket` はCSV/OCR由来の独立レコードで、案件・取引先IDは任意。オペレーター仮予約も本人の実績予定とは分離している | すでに緩い接続の実例がある。全機能の強制同期を目標にしない |
| 評価 | 旧分析には自己登録ジョブの重複集計経路があり、新しい試験点も記録時間の影響が大きい。マイジョブの自動完了は成果の証拠にならない | 入力件数・予定時間・自動完了をそのまま能力や成果へ置き換えない |

## 提案する日常の流れ

### 進行管理

- 本筋の案件を作り、関係する作業者をメンバー登録する。普段の必須操作はここまでとする。現行の手動案件作成は伝票番号と取引先IDを空欄にできるが、画面文言や他の作成経路は確認する。
- 支流の伝票付き案件、期限、進行表、仮予約、ジョブ依頼は、その案件で必要な時に登録する。支流の作成が遅れても本筋の作業記録を止めない。
- 同じ本筋に支流が増える場合、まずは画面上の任意の関連付けを検討する。親子IDを新設するかは、実際の検索・集計・権限で必要になってから決める。既存の `shared_from_id` は部署間共有用なので使い回さない。

### 作業者・校正者

- 最近使った本筋を最初に表示する。大枠が分かれば選択を終えられ、個別テスト名・伝票番号・取引先の再入力を要求しない。
- 最小入力は「作業日」「作業種類」「おおよその実作業時間」「結果の状態」。日付は初期値を入れ、時間は候補から素早く選べるようにする。結果の状態は例として「作業中・提出・返却・完了」、説明文と数量は任意とする。最小項目の確定は現場の数日分の例で行う。
- 作業の切替やファイル返却時にも1件追加できる。日報時にはその日の候補をまとめて確認・修正し、未記録の作業だけ追加する。同じ内容を日報本文、カレンダー、マイジョブへ繰り返し書かせない。
- 本筋も未登録なら、簡易作業記録は仮の案件名または「案件未登録」で保存できるようにする。その後の紐付けは本人または権限のある管理者が明示的に選ぶ。現在のマイジョブ登録ルートでは案件が必要なので、この例外を現行マイジョブにどう統合するかは別途設計する。
- 依頼が届いた場合は、既存の「マイジョブとして登録」で引き継ぐ。本人が同じ仕事を手入力済みなら、二重の作業として加算しないよう確認する。

## データの役割を分ける

| 記録 | 当面の役割 | 無理に行わない連動 |
| --- | --- | --- |
| Excel等の伝票・`PrepressTicket` | 受注番号、納期、取引先、制作・製版の管理 | 作業者の毎日の記録を、伝票入力完了まで待たせない |
| 本筋の `ProjectJob` | チームと作業の大枠。本人が選ぶ入口 | 支流が全部登録されていると仮定しない |
| `ProjectJobAssignment`・マイジョブ | 依頼、本人の担当、続き作業の履歴 | 1件を1日の実作業時間や完了成果とみなさない |
| 日々の作業行 | その日に何をどのくらい行い、どうなったか | 案件名の一致だけで伝票へ自動接続しない |
| `work_records` と日報 | 勤務時間の記録と、本人による一日の報告 | 勤務時間を案件別作業時間へ自動配分しない |

画面は一つに寄せても、保存先を一つのテーブルへ無理に統合する必要はない。本人が入力した同じ作業には参照IDを持たせ、日報への反映と分析で一度だけ数える。伝票番号・取引先コードが分かる場合の紐付けは残し、未確定の一致を確定扱いしない。会社・部署・非公開案件の閲覧制限は維持する。

## 試す順番

1. Super Admin 試用で「本筋だけある日」「支流だけ遅れる日」「本筋もない日」「1時間ごとの切替」「ファイル返却」を再現し、記録が止まらないか確認する。
2. 簡易入力の画面と日報を、現場の実例で操作回数・入力時間・重複を確認する。入力の多い項目より、空欄になりがちな項目を先に減らす。
3. 既存の依頼・マイジョブ・校正・銀本専用工程と衝突しないことを確認する。特に依頼取り込み、続き作業、二重計上、権限、JSTを検証する。
4. 上長と、実際の記録の具体性・未記録の理由・成果の確認方法を照合する。試用の点数式の変更と全員向け公開は、その後に別判断とする。
