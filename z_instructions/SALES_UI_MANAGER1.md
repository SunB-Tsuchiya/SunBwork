### 7. 経費比較: 科目セレクタをボタン式に、エラーハンドリング追加

ユーザーから2点の指摘。**①** 科目の選択が`<select>`ドロップダウンだと面倒なので、部署タブと
同じボタン横並び方式にしてほしい。**②** 「消耗品」等、主材料費以外の科目を選ぶとグラフ・表が
何も表示されない（主材料費だけは表示される）。

**①**: `ExpenseComparison.vue`の科目セレクタを`<select>`から`<button>`の横並び（部署タブと同じ
`flex flex-wrap gap-1`スタイル）に変更。

**②の調査**: `消耗品`カテゴリについて、(a) `SalesExpenseQueryService::categoryMultiYearTrend()`/
`vendorComparison()`をtinkerで直接呼び出し、(b) 実HTTPカーネル経由で`/superadmin/sales-analysis/
api/expense-comparison/trend?...category=消耗品`を実際にdispatchして確認、の両方で**正常に
6年分のデータ・支払先内訳が返ることを確認**（バックエンドは問題なし）。`ExpenseComparison.vue`の
リアクティブフロー（`watch(selectedCategory, ...)`等）もコードレビューで問題を発見できず。
過去2回、似た症状（ブラウザの古いキャッシュ）があったため、同様の可能性が高いと判断。ただし
今後同種の問題が再発した際に原因を切り分けやすくするため、`fetchTrend()`/`fetchVendors()`に
`catch`を追加し、取得失敗時は画面にエラーメッセージを表示するようにした（従来はエラーが
握りつぶされ、何も表示されない状態と「読み込み中」の区別がつかなかった）。npm run build・
SalesAnalysis配下テスト355件成功。ユーザーへハード更新を依頼し、再発する場合はブラウザの
コンソールエラー・Networkタブの実際のレスポンスを確認してもらうよう伝える。

### 8. 経費比較グラフ不具合の根本原因特定・修正

ユーザーが②の再現画面を再度提示。今回は表（6年分の数値・支払先内訳）は正しく表示されており、
**グラフ（canvas）だけが空白**であること、コンソールエラーも無いことが判明し、タスク7での
「ブラウザキャッシュの可能性」という見立てが誤りだったと判明（データ取得自体は正しく動いており
真の原因はフロントエンドのレンダリングロジックにあった）。

**根本原因**: `ExpenseComparison.vue`では`<canvas>`を`<template v-else-if="trendData">`の中に
置いており、科目を切り替えるたびに`trendLoading=true`→「読み込み中」表示（canvas破棄）→
`trendLoading=false`→canvas再生成、という形でcanvasをDOMごと作り直していた。既存の他画面
（期別分析の複数年推移グラフ等）はcanvasを常時マウントしたままにし中身だけ再描画する設計で、
今回の経費比較だけがこの「切替のたびにcanvasを作り直す」という未検証のパターンを採用していた。
さらに、`trendData.value = response.data`をセットした直後（`trendLoading`をまだfalseにする前）に
`renderTrendChart()`を呼んでいたため、**chart.js がまだ`display:none`で隠れているcanvasに対して
描画しており、0サイズで測定されてグラフが見えなくなっていた**（初回表示だけ、ページ読込み直後に
canvasが元々表示状態だったため偶然動作していた）。

**修正**: canvasを`v-show`（CSS表示切替のみ、DOM常駐）へ変更し他画面と同じ「常時マウント・
中身だけ再描画」方式に統一。あわせて`fetchTrend()`/`fetchVendors()`内の描画呼び出し順序を、
`finally`で`trendLoading`/`vendorLoading`をfalseにした**後**に`nextTick()`→描画、という順序に
変更し、描画時点でcanvasが確実に表示状態になっているようにした。npm run build・SalesAnalysis
配下テスト355件成功。この教訓（「loading用のv-ifでcanvasをアンマウントしない」「loading解除後に
描画する」）は今後chart.jsを使う画面を作る際に注意する。

### 9. 支払先別グラフ: 項目が多い場合の縦スクロール化

グラフ表示自体は復旧したが、ユーザーから「支払先が多い科目（外注加工費等）だと表と棒グラフが
ずれて見える。上位5〜7件を表示し、残りは縦スクロールで見る形にしてほしい」との指摘。
`vendorChartRef`のcanvas自体は全件分の高さ（`vendors.length * 24px`）を確保したまま、
`max-h-44`（176px、約7本分）＋`overflow-y-auto`の親divで囲み、見える範囲を上位5〜7件程度に
固定して縦スクロールで残りを見る形にした。npm run build・SalesAnalysis配下テスト355件成功。

### 10. 科目切替が反映されない（外注加工費から変わらない）不具合の修正

ユーザーから「外注加工費から他の科目に変えようとしても変わらない」との報告。`fetchTrend()`/
`fetchVendors()`にリクエストの先着・追い越しガードが無く、科目ごとに支払先数が大きく異なる
（外注加工費は30社超、他は数社程度）ためレスポンス時間の差で**古い（外注加工費の）リクエストの
応答が、新しく選び直した科目のリクエストより後に届いて表示を上書きしてしまう**競合状態が
原因と判断（典型的なrace condition。外注加工費はデータ量が最大でレスポンスが遅くなりやすく、
そこから別科目へ切り替えた直後に発生しやすい）。`trendRequestSeq`/`vendorRequestSeq`という
リクエスト連番をそれぞれに導入し、応答が返ってきた時点で「自分が最新のリクエストか」を
確認し、古ければ反映せず破棄するよう修正した。npm run build・SalesAnalysis配下テスト355件成功。

### 11. 「外注加工費だけダメ」の正体（タスク10の対応は誤診断だった）

ユーザーへの再確認（見出しの科目名は正しく切り替わっているか）で「変わっています。外注加工費
だけダメです」との回答を得て、さらに「グラフ・表とも空/数字がおかしい/エラー」の選択式で
確認したところ、**データ更新自体は問題なく動いており、実際の症状は「支払先が多い科目
（外注加工費=34社）だけ、横棒グラフの帯とラベルの行がずれて見える」という表示崩れ**だったと
判明。タスク10で実施した「古いリクエストの上書きを防ぐ連番ガード」は誤診断に基づく対応で、
実害は無かったが根本原因ではなかった（ガード自体は副作用も無いため残置）。

**根本原因**: タスク9で追加した「外側を`max-h-44 overflow-y-auto`の固定高さにし、内側の
canvasに`:height="件数*24px"`属性を設定する」方式は、chart.jsの`responsive: true`が
**canvasの直接の親要素の実サイズ**を基準にcanvasを再計算してしまうため、親である外側の
固定高さ（176px）に合わせて棒を圧縮してしまっていた（`height`属性は初期値止まりで、
chart.js起動直後に上書きされる）。支払先が少ない科目（5〜7件以下）はたまたま176pxに
収まるため問題が表面化せず、外注加工費のような大量件数の科目だけ症状が出ていた。

**修正**: 外側の固定高さ`overflow-y-auto`コンテナの**内側にもう1枚、全件分の実高さ
（`件数*24px`）を持つラッパーdiv**を追加し、canvasはそちらを基準に伸縮させる二重ラッパー
構成に変更。あわせてchart.jsオプションに`maintainAspectRatio: false`を追加（trueのままだと
既定のアスペクト比が優先され、縦長の親要素でも横幅基準で潰れた高さに描画されてしまうため）。
これで内側ラッパーが本来の高さ（例: 34件なら816px）を持ち、外側コンテナがそれより小さい
176pxに固定されることで正しくスクロールバーが機能する。npm run build・SalesAnalysis配下
テスト355件成功。

**教訓**: chart.jsを`overflow`制御されたスクロール領域に入れる場合、`responsive: true`は
canvasの**直接の親**のサイズを見るため、固定高さにしたい外枠と、canvasの実サイズを決める
内枠は必ず別の要素に分離すること。

### 12. 期番号（第◯期）の表記追加

ユーザーから「期別の表記に第何期かを入れたい。2026年度=56期、2025年度=55期で、ちょうど30
ずれている（＝開始暦年-1970=期数）。56期（2026年度）のように直してほしい」との指示。

**会社スコープの判断**: 期番号の計算式（開始暦年-1970）はサン・ブレーンの創業年に基づく固有の
値で、他社（サンエー印刷等）には適用できない。期別分析画面（`FiscalYearAnalysis.vue`）自体は
全社共通画面のため、`supportsExpenses`（既存のSUNBRAIN限定判定、Phase21から流用）で
表示を分岐し、**サン・ブレーンのときだけ「56期（2026年度）」表記、他社は従来どおり
「2026年度」のまま**にした。経費取込・経費比較（`ExpenseImport.vue`/`ExpenseComparison.vue`）は
元々SUNBRAIN限定画面のため無条件で新表記を適用。

**実装**: `useSalesChart.js`に`fiscalPeriodNumber(fiscalYear) = fiscalYear - 1970`と
`fiscalPeriodLabel(fiscalYear) = "${期}期（${fiscalYear}年度）"`を追加（新規API不要、
フロントのみの計算）。`PeriodNavigator.vue`に`showFiscalPeriod`propを追加し、期別分析の
期間送り表示（中央の「2026年度」表示）を条件付きで新表記に変更。`FiscalYearAnalysis.vue`の
残り4箇所（品名検索見出し・欠落月警告・前期参考値・月別推移グラフ見出し/凡例）、
`ExpenseComparison.vue`の5箇所（複数年推移グラフ凡例・表・会計年度セレクタ・支払先別表
見出し・前年比較不可メッセージ）、`ExpenseImport.vue`の2箇所（対象会計年度表示・取込完了
メッセージ）を順次更新。npm run build・SalesAnalysis配下テスト355件成功。
