# WORK_RECORD_PLAN1 — 作業記録を日報と随時入力で共用する設計案

作成日: 2026-10-11。目的は作業の見える化を主、人事評価の参考を従とする。ここでいう「6:4」は利用目的の比重であり、採点係数ではない。利用者の確認後、入力と日報の試用実装を開始する。上長と実データを確認するまで、利用権限は情報出版の Super Admin のみに据え置く。

## まず読む概要

- 試用する Super Admin は、作業の切り替えやファイルの返却時に、同じ案件・作業を候補から選んで短く記録できる。記録した時刻は自動で残し、後から日付・時刻・内容を直せる。オペレーターへの公開は上長との評価後に判断する。
- 試用画面に「日報で一日を振り返る」確認欄を置き、その日に残した記録を一覧で見る。既存日報への正式な取込は、上長との検証後に接続する。
- プロジェクトや依頼ジョブへの結び付きがあれば活用するが、作業記録の必須条件にしない。短期大量案件、長期案件、案件外業務のいずれも記録できる。
- マイジョブの通常の自己記録を、将来的に同じ短い入力へ統合する。依頼ジョブ・進行表など既存の連動は引き続き参照可能にする。
- 入力件数・入力時刻・予定枠・残業から「まじめさ」を自動判定しない。作業記録は何に取り組んだかを確認する材料とする。

## 現行実装で確認したこと

- `personal_work_entries` はカレンダー簡易入力と日報で共用され、案件ID・依頼ジョブID・予定元イベントIDを任意で持てる。試用記録をここへ書くと現行分析へ混入するため、初期試用は別テーブルに保存する。
- 簡易入力は予定枠から `actual_minutes` を計算し、作業種類と結果文がある場合だけ現行暫定点に算入する。日報の取込画面では結果文・作業種類・分数を必須にしている。
- 日報の未記録時間案内は、勤務枠との差を暫定点と結び付けて促す。今回の目的では、記録のない時間を埋める圧力になるため文言と計算の扱いを見直す。
- `PersonalWorkSchedule::available()` は情報出版所属 SuperAdmin だけを許す。実際のオペレーターが使うには、対象者と閲覧権限を別途拡げる必要がある。
- マイジョブの難易度・サイズ・工程・数量・見積時間は任意だが、入力画面は多項目。自己割当の `completed` には翌日の自動完了が混じり、成果の証拠として直接使えない。

## 使い方

### 途中で記録する

1. Super Admin 専用の試用画面で「作業を記録」を開く。日報での使用感は同画面の一日確認欄で試す。正式な日報画面への接続は評価後に行う。
2. 最近の案件・作業と本人の担当案件を候補に出す。案件は任意。「続き」と「別の作業・ファイル」を明示して選べるようにし、誤って同一成果へまとめない。
3. 選ぶ項目は作業種類と進み具合を中心にする。進み具合の例は「進めた」「返却・引き渡した」「確認待ち」。返却は引き渡しの記録で、品質上の差し戻しとは区別する。自由記述と数量は必要な時だけ。
4. 保存時刻を自動で付ける。正確な時間配分を求めない。作業時間を任意で記録する場合は、予定時間と実績時間を明確に分け、後から修正可能にする。

### 日報を想定してまとめる（試用画面内）

- その日の随時記録を時系列で見せる。複数件をまとめたり、不足する作業を同じ操作で追加できる。
- 一日分の記録を並べ、作業を追加・修正・削除できる。試用データだけを操作し、既存日報・簡易予定・分析は更新しない。
- 現行日報へ接続する際は、本人が取込を確認し、非公開記録の公開範囲を示す。同じ作業を複製しない設計を先に検証する。
- 試用画面では、未記録時間を点数や勤怠時間との差として示さない。現行日報の案内は本試用では変更せず、統合時の見直し対象にする。

## データと連動の方針

- 初期試用では専用の `work_record_trials` テーブルを正とする。既存の `personal_work_entries`、`diaries`、`project_job_assignments` は読み取り参照のみとし、集計へ混入させない。
- 試用記録には日付・記録時刻・作業種類・進み具合・続きの識別子を保存する。将来 `personal_work_entries` へ統合するときは、試用レコードを区別して二重計上を防ぐ。
- 案件選択時は現行の会社・案件公開設定を守る。本人の入力・編集と管理者の閲覧を別に認可し、案件なしの記録も扱えるようにする。
- 既存マイジョブと依頼ジョブの履歴・通知・進行表連動は当面維持する。新規の本人作業記録から不要な自己割当を自動生成して重複させない。必要な進行表リンクだけ明示的につなぐ。
- 旧記録を新しい「本人が完了を押した」実績へ変換しない。自動完了と親子ジョブへの完了伝播を確認済み成果へ算入しない。

## 評価表示の方針

- 当面は「記録がある勤務日」「どの作業を進めたか」「本人が返却・提出した節目」「実績時間が本人入力された範囲」を別々に表示する。欠測は欠測と示す。
- 作業成果の点数は、記録の定着と実際の提出・完了の照合後に決める。候補式は `確認済みの工程 × 仕事の種類ごとの標準作業量`。標準量は現場のサンプルから校正し、本人に難易度・サイズの入力を強いない。
- 品質、納期、協力、担当機会の差は上長の確認項目として分離する。旧6カテゴリ順位と現行の時間由来暫定点を新成果点へ変換しない。

### 上長との照合手順

1. 現行の7〜9月の匿名集計を、記録の揃い具合と時間点の偏りを知る材料として示す。個人の旧順位を新方式の正解とみなさない。
2. Super Admin 試用で、短期案件、長期案件、返却が多い日、会議・差配が多い日を各数例選ぶ。実際の仕事の流れと、試用記録から読み取れる流れを上長と照合する。
3. 1件の入力にかかる操作、記録漏れ、案件候補の探しやすさ、ファイル返却の意味が伝わるかを確認する。記録時刻を監視や作業時間の確定値として扱わない。
4. 仕事の種類ごとの標準量と品質確認の基準は、この照合で合意できたものから採用する。単一の人事点数と全員への公開は別判断にする。

## 実装フェーズと主な対象

1. **独立試用入力**: 新規マイグレーション、`WorkRecordTrial` モデル、専用 Controller・ルート・Vue 画面。既存カレンダーと日報の保存処理には手を入れない。
2. **一日の確認**: 同じ試用画面に、途中記録を時系列で確認・修正する欄を設ける。既存日報との取込は実際の使用感と権限設計を確認後に実装する。
3. **Super Admin 限定試用**: `PersonalWorkSchedule::available()` の制限を維持する。分離した Git worktree とブランチで作り、既存の未コミット変更・ビルド出力から隔離する。Sakura 反映は設計と画面の確認後にコマンド全文を提示して別途確認する。
4. **マイジョブ統合**: 新入力が使われることを確認後、本人の新規マイジョブ入口を共通入力へ寄せる。依頼ジョブ・進行表など連動が必要な入口は維持し、リンク方法を個別に検証する。
5. **評価表示**: 記録の定着を見て、旧方式・暫定点・新しい成果の画面を整理する。点数式は実データと現場確認後に別計画で決定する。

## 検証

- 同じ日に1時間前後で作業を切り替え、返却を複数回記録しても消失・二重登録しない。
- 途中で保存した作業が試用の一日確認欄に現れ、修正・削除後の表示が一致する。現行日報と現行分析に試用記録が混入しない。
- 案件あり・案件なし、続き・別ファイル、既存ジョブ予定、非公開記録をそれぞれ確認する。
- 旧マイジョブ、依頼ジョブ、進行表、カレンダー、既存日報の動作を壊さない。PHP の対象テスト、権限テスト、Vue ビルドで確認する。

## 公開前に確認する一点

Super Admin 試用の後、上長と実際の記録・集計の妥当性を確認し、どのユーザーへ公開するかを決めてから権限を変更する。「ファイルを戻す」は、原則として作業したファイルを返却・引き渡す意味として扱う。本番 DB の丸ごとのローカル複製は行わず、必要な場合は Sakura の読み取り専用集計を個人・案件を識別しない形式で確認する。
