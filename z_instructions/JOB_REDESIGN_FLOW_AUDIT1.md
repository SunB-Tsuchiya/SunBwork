# 既存のジョブ・簡易入力・日報の再点検

2026-10-12。改修前のコードと既存設計を読み取って確認した結果。以下の「現行コード」は調査時点の状態を指す。後続の簡易入力改修と使用率調査は `JOB_INPUT_REVIEW_PLAN1.md` と `JOB_INPUT_REVIEW_MANAGER1.md` に記録した。全員向け公開や査定方法の決定ではない。

## 利用者との再すり合わせ（2026-10-12、以下の旧提案より優先）

利用者は日報と予定表を一体化することを求めていない。提示された画面のように、本人が書いた日報本文と当日のタイムテーブルを同じページに表示する現行機能を維持する。予定を本文へ自動挿入する新機能も現時点では不要。以下の旧提案にある「日報で作業行を必須確認・追加し、その行を評価データとする」という連動は、新しい作業記録の前提にしない。

利用者確認済み: 評価の参考にする案件別の作業時間は、日報本文ではなくカレンダーの時刻表で選んだ開始・終了から読み、必要ならそこで訂正する。独立した作業時間欄や分数のみの入力は作らない。その日になった予定は基本的に活動記録として扱い、各予定に「実施確認」を押す操作は求めない。未来の予定は活動記録に含めない。実際と違った予定は、既存の編集・削除などで直せるようにする。日報作成時はカレンダーの記録を見返すのに適した時点なので、不備があれば保存を妨げない注意を出す。日報本文との統合や自動転記は行わない。

注意は、勤務時間に対して記録が大きく不足する日や、時間が判断できない古い記録など、本人が直せる点を中心にする。結果文・進みの文章が空欄という理由だけで警告したり採点対象から除いたりしない。現行の `DiaryWorkReminder` は表示位置とカレンダーへの導線を再利用できるが、`WorkloadTrialAnalysis` による記録時間の計算と「結果または作業種類が未入力」「暫定ポイントに反映されません」という文言は新方針に合わせて修正が必要。

現行コードは本文 `diaries.content` と別に Super Admin 用の `work_entries` も持ち、`DiaryWorkEntries::sync()` で `personal_work_entries` に日報ID・時間・結果文を保存している。この追加欄をどう扱うかは別途検討する。画面から外す場合は、編集保存時に空配列を送って既存の関連作業行を解除・削除しないよう、既存レコードの保護が必要。分析も `result_note` の有無を認定条件にしている。カレンダー・マイジョブの時間記録は、日報本文とタイムテーブル表示に手を入れずに検討する。

## まず読む結論

独立した「作業記録の試用」を日常の新しい入口として育てるのは重複が大きい。既存の「マイジョブ作成」と「カレンダーの簡単な作業予定」を手直しする方が筋がよい。日報の自由記述とタイムテーブル表示は現状どおり残す。試用画面は安全に比較するため当面残し、追加開発を止める。

マイジョブは仕事の担当・依頼・続き・ファイルを保持する。日々の作業行は「その日に何を何分行ったか」を保持する。役割が異なるため保存テーブルを無理に一つにせず、必要ならIDで結び、一度の入力と二重計上防止を画面と集計で実現する。

## 現在の流れ

| 入口 | 保存と次の画面 | 既に使えるもの |
| --- | --- | --- |
| MyJobBox の「マイジョブ作成」、またはカレンダーの「マイジョブ」 | 通常 `Events/Create_Job.vue` → 共通 `AssignmentForm.vue` → `project_job_assignments` と予定。依頼元からは `MyJobBox/Create_user.vue` も使用 | 過去データ流用、依頼の取り込み、案件とジョブ名、開始・終了時刻、カレンダー選択 |
| カレンダーの「簡単な作業予定を追加」 | `QuickWorkEntryModal.vue` → `personal_work_entries` → カレンダーに再表示 | 選んだ時間枠の引き継ぎ、案件検索、仮の案件名、作業名、後から修正 |
| 日報の「今日の作業結果」 | `DiaryWorkEntries.vue` → `DiaryWorkEntries::sync()` → 同じ `personal_work_entries` に日報IDと結果を保存 | 簡易予定や既存ジョブ予定を選択、予定外作業を追加、時間と種類を入力 |
| Super Admin の「作業記録の試用」 | `WorkRecordTrial.vue` → `work_record_trials` | 1件ずつ保存・続き・一日確認。既存日報・マイジョブ・採点へは未接続 |

## 重要なずれと未確認点

1. **時間の意味:** 簡単な作業予定は午前・午後・終日・時間指定を保存し、`DepartmentWorkController::validatedEntry()` が予定枠から `actual_minutes` を計算する。日報画面では簡易予定の分数を編集できず、`DiaryWorkEntries::sync()` も予定枠の分数を採用する。`WorkloadTrialAnalysis` は時間配分に `slotInterval()` を使う。今後の簡易入力はカレンダーの開始・終了を必須にし、その時刻を基本の活動時間とする。予定と実際が違う場合だけ本人が時刻を訂正する。独立した分数欄は作らず、未来の予定を活動記録として集計しない。
2. **文章の必須条件:** 日報の選択した作業行は `result_note` が必須で、`WorkloadTrialAnalysis` も結果文がある行だけを実績として扱う。利用者の新方針は進み・文章を任意、時間を必須。日報の保存検証、注意文言、集計の対象条件を一緒に見直す必要がある。日報本文の自由記述は維持する。
3. **案件選択:** MyJob の共通フォームは本人の候補をプルダウンで並べる。過去データ流用には「完了を表示しない」の切替があるが初期値は非表示になっていない。カレンダー簡易入力は検索欄と候補30件の常設一覧を持ち、候補APIは担当・最近・検索結果を返すが、完了案件を一律に隠さない。100件以上を扱う人には「案件を探す」モーダルか入力補完、本人の関係案件優先、完了非表示の初期設定が適切。選択済み完了案件は編集時に見える必要がある。
4. **マイジョブとの関係:** `personal_work_entries` は `project_job_assignment_id` を持つが、カレンダーの簡易入力画面は本人のマイジョブを選ぶUIを持たない。日報で既存ジョブ予定を選んだ場合にはジョブと結び付く。手入力の簡易予定と同じジョブ予定を併用した場合、同一作業と確定するIDがないため、実例による二重計上確認が必要。
5. **公開範囲:** カレンダー簡易入力、部署の作業、日報取り込みは `PersonalWorkSchedule::available()` により情報出版の Super Admin に限定されている。全員向け公開は別の段階で権限・個人情報・旧日報との互換性を確認する。

## 推奨する次の順序

1. `work_record_trials` の追加改修とステップ4-2を止め、既存のマイジョブ・簡易予定・日報を少数の実例で同じ日に操作比較する。試用データは旧日報・評価に混ぜない。
2. 既存のマイジョブ登録画面の構造を保ったまま、案件を探すUIを共通化し、入力されない詳細項目を折りたたむ。依頼取り込み・過去流用・ファイル情報・続き・進行表のリンクを確認する。
3. 既存のカレンダー簡易入力を日々の作業記録の主導線にする。カレンダーで選んだ開始・終了を引き継ぎ、両方を必須・後から訂正可能にする。新たな作業時間欄は設けない。その日の予定を基本の活動記録として扱い、追加の実施確認を求めない。時刻の訂正が集計にも反映されるようにする。
4. 日報本文と当日のタイムテーブル表示は現状どおり維持する。日報作成時の既存の注意欄を、時間の大きな抜けなどを知らせる非強制の案内に改める。結果文を必須とする現行の Super Admin 用作業行と分析側の依存は、既存データへの影響を確かめてから変更する。新しい日報文章化ボタンは今は作らない。
5. その後に、同一ジョブの簡易記録とカレンダー予定の重複、上長の見たい実例、試験分析の対象条件を照合する。点数と全員公開はこの確認後に判断する。
