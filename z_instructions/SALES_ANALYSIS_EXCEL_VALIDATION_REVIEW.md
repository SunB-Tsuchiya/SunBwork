# SALES_ANALYSIS_EXCEL_VALIDATION_REVIEW.md — Excel取込バリデーション再設計レビュー依頼

## 1. 背景

売上分析機能（`z_instructions/SALES_ANALYSIS_PLAN1.md` / `SALES_ANALYSIS_MANAGER1.md`）の実装を進め、Phase 0〜6は完了・テストも通過していた。しかしユーザーが実際の（架空化されていない構造は同じ）帳票ファイルでアップロードを試したところ、以下の問題が続けて発覚し、設計時の想定と実運用の帳票データに乖離があることが判明した。ユーザーの指示により実装作業を一旦停止し、本ファイルでCodexにレビュー・再設計提案を依頼する。

**現時点までに判明した実運用の実態（設計時は未確認だった）:**

1. Excelタイトル行（1行目）の年月は、月次・年次・範囲（半期等）のいずれであっても**出力側（帳票ソフト）の設定により常に開始月固定**で表示される。半期(1-6月)ファイルでも年次ファイルでも「1月」としか出ない。→ この対応として、フォーム自動入力はファイル名から行い、タイトル年月とフォーム入力の一致検証は撤廃済み（行レベルのSB下版日照合のみで整合性を担保する方針に変更済み）。
2. 対象部署は当初「企画のみ」の想定だったが、企画・制作・オンデマンドの3部署すべてを取込可能にする方針に変更済み。
3. **今回新たに判明した問題（未対応）:**
   - 判型（I列 `format_size`）が空欄の行があり、現在は必須項目としてエラーになる。
   - 受注金額（N列 `order_amount_component`）が0の行があり、これ自体は既存ロジックでは許容しているはずだが、実際には「金額合計と受注金額合計の不一致」等でエラーになるケースがある。
   - ユーザーの要望: 「空データはエラーなしでとりあえず取り込み」たい。M列合計とN列合計の関係は「同一受注No内で複数行に分かれ、最後の行にまとめて合計金額が入る（途中行は0）」という、これまで何度も説明済みの仕様のはずだが、現在の実装がこれを正しく生かせていない可能性がある。

### 2.2 現在の必須項目チェック（`SalesImportValidator`）

```php
private const REQUIRED_TEXT_FIELDS = [
    'order_number' => '受注No',
    'client_name' => '得意先名',
    'product_name' => '品名',
    'category' => '分類',
    'item_name' => '項目',
    'format_size' => '判型',   // ← 実データで空欄あり。現状は必須扱いでエラーになる
];

private const REQUIRED_NUMBER_FIELDS = [
    'color_count' => '色数',
    'quantity' => '台数',
    'unit_price' => '単価',
    'line_amount' => '金額',
];
```

`validateRow()` はこれらが `null`（空欄）ならエラーメッセージを積む。1つでもエラーがある行はその行ごと「受注グルーピング」から除外され（`groupRows()`）、結果的にファイル全体が `valid: false` になる。

### 2.3 受注金額（N列）の扱い

```php
// order_amount_component（受注金額）は同一受注内の途中行で0が許容されるため必須値のみ検証
if ($row['order_amount_component'] === null) {
    $issues[] = '受注金額が数値として読み取れません。';
} elseif ($row['order_amount_component'] < 0) {
    $issues[] = '受注金額が負数です。';
}
```

→ 単体では0はエラーにならない設計のはずだが、`buildOrder()` 側で以下のチェックがある。

```php
$lineAmountSum = array_sum(array_column($rows, 'line_amount'));
$orderAmountSum = array_sum(array_column($rows, 'order_amount_component'));

// 浮動小数点の丸め差異（1円未満）を許容する
if (abs($lineAmountSum - $orderAmountSum) > 0.01) {
    $errors[] = "受注No {$orderNumber}: 金額合計（...）と受注金額合計（...）が一致しません。";
}
```

これは「同一受注Noの全行のM列合計とN列合計が一致すること」を検証している。PLAN上の合意（`SALES_ANALYSIS_PLAN1.md` 2.4節）は以下の通り:

> - 同一受注内では途中行の受注金額は0、最後の行に受注全体の金額が入る。
> - DB上の受注金額は、同一受注Noに属する全行の N 列合計として算出する。これにより記載位置に依存しない。
> - 同一受注NoのM列合計とN列合計が一致することを取込検証する。不一致なら自動確定せず、行番号・受注No・差額をプレビューへ警告またはエラーとして表示する。

**問題**: 「不一致なら**警告またはエラー**」とPLANに書かれているにもかかわらず、現在の実装は無条件で `errors`（＝確定不可のブロッキングエラー）にしている。かつ、この不一致が起きる具体的な原因（対象月の切り取り方でグループの一部行が範囲外になり除外される、等）を切り分けられていない。

### 2.4 行バリデーション失敗時の扱い

現在は、1行でも必須項目エラー等があると、その行を丸ごと受注グルーピングから除外し、かつファイル全体を `valid: false` にして**確定を一切ブロックする**設計（`SalesImportPreviewTest` 等で確認済みの現行仕様）。ユーザー要望は「空データはエラーなしでとりあえず取り込み」たいとのことで、これは以下のいずれかへの変更を意味すると考えられる。

- (a) 必須項目チェックの対象を絞り込む（判型等、実際には空欄があり得る項目を必須から外す）
- (b) 必須項目エラーを `errors`（ブロッキング）ではなく `warnings`（確定可能・注意喚起のみ）に格下げする
- (c) 問題のある行だけをスキップして残りの行で受注を構成し、スキップした内容を警告として提示する

いずれを採用すべきかはPLANの「値引き・返品・取消によるマイナス受注金額はない」「途中経過ファイルでも、掲載済み受注は受注金額まで確定している」という前提や、機密データを扱う都合上ユーザー以外がExcel実データを見られない制約とも合わせて検討が必要。

## 6. Codexレビュー結果（2026-09-03）

### 6.1 結論

現在の取込ロジックは、実帳票に合わせて再設計が必要である。

- 同一受注Noの途中行でN列（受注金額）が0になること自体は、現行コードでも許容されている。
- 現在の問題の中心は、空欄を持つ行を受注グループから丸ごと除外することと、M列合計・N列合計の不一致を無条件にブロッキングエラーにしていることである。
- 問題行だけをスキップして残りを保存してはいけない。一部明細が欠落すると、分類別・項目別・品名別の内訳が不正確になる。
- 売上総額はN列を正とし、説明項目やM列内訳に欠損・差異があっても、条件を満たせば警告付きで取込可能にする。
- M列合計とN列受注金額の差は隠さず「未配賦額」として集計・表示する。

### 6.2 重大度順の指摘

#### High-1: 空欄のある行を丸ごと除外している

対象:

- `app/Services/SalesAnalysis/SalesImportValidator.php` の `groupRows()`

現在は、`validateRow()` が一つでもissueを返すと、その行を`$ordersByNumber`へ追加せず`continue`している。このため、同一受注Noの一部明細だけが欠落し、M列合計とN列合計の不一致を二次的に発生させる。

修正方針:

- 行検証を`errors`と`warnings`へ分離する。
- 警告だけの行は除外せず、必ず受注グループへ含める。
- 重大エラーがある場合も「その行だけを捨てて残りを確定」せず、ファイル全体を確定不可にする。
- エラー表示にはExcel行番号を残す。

#### High-2: nullable化がValidatorとDBで一致していない

対象:

- `app/Services/SalesAnalysis/SalesImportValidator.php`
- `database/migrations/2026_09_02_100005_create_sales_order_details_table.php`
- `app/Models/Sales/SalesOrderDetail.php`
- `app/Services/SalesAnalysis/SalesImportService.php`

現在、判型等はValidatorで必須かつDBでもNOT NULLである。Validatorだけを緩和すると確定時にDBエラーになる。

推奨分類:

| 区分 | 列 | 扱い |
|---|---|---|
| 行の識別・売上帰属に必須 | 受注No、SB下版日 | 欠損・解析不能はブロッキングエラー |
| 受注単位で必須 | 受注金額 | 同一受注内で最終的な受注金額を確定できなければブロッキングエラー |
| 空欄を警告付きで許容 | 得意先名、品名、分類、項目、判型、色数、台数、単価、金額 | NULL保存。行は除外しない |
| 通常の空欄を許容 | 部品名、進行、備考 | NULL保存。原則警告不要 |

注意:

- 数値空欄を勝手に0へ変換して保存しない。`NULL`と0は意味が異なる。
- nullable対象は追加migrationで変更する。すでに適用済みのcreate migrationを書き換えるだけにしない。
- 得意先名等がNULLの場合、集計画面では`（得意先未設定）`、`（分類未設定）`等の明示ラベルでまとめる。
- `sales_orders`側の`client_name`、`product_name`等も、明細から受注代表値を決められない場合に備えてnullable化または明示的な未設定値方針を揃える。

#### High-3: N列の帳票規則を明示的に検証していない

対象:

- `app/Services/SalesAnalysis/SalesImportValidator.php` の `buildOrder()`

帳票規則:

- 同一受注Noが複数明細に分かれる。
- 途中行のN列は0になる。
- 受注の最後の行に受注全体の金額が入る。

推奨アルゴリズム:

1. 同一受注Noの全行を`source_row_number`順に並べる。
2. N列の途中行は0を許容する。
3. N列空欄については計算時のみ0相当として扱えるが、DB原値はNULLのまま保存する。
4. 0より大きいN列が原則1行だけ存在することを確認する。
5. その行が受注グループの最後の行であることを確認する。
6. その値を`order_amount`として採用する。
7. 全行のN列合計も監査用に計算し、採用値との一致を確認する。

判定:

- 途中N=0、最後N>0: 正常。
- 途中N=NULL、最後N>0: 警告付き正常。ユーザーが実帳票で空欄を0と同義にしていることを確認したうえで許容する。
- N>0が存在しない: ブロッキングエラー。
- N>0が複数行: ブロッキングエラー。
- N>0が最後の行ではない: 帳票規則違反として原則ブロッキングエラー。実データで正当例がある場合だけ仕様を再確認する。

#### High-4: 年次・範囲ファイルの再取込で旧月が残る

対象:

- `app/Services/SalesAnalysis/SalesImportService.php` の`confirm()`および`affectedMonths()`

現在は、新ファイルに実際に受注が存在する月だけ`SalesActiveMonth`を切り替えている。

例:

- 旧年次版には8月の受注がある。
- 修正版では8月の全受注が削除されている。
- 新版に8月行がないため、8月だけ旧版へのポインタが残る。

修正方針:

- active monthの切替対象は「データが存在する月」ではなく、取込指定範囲全体とする。
  - monthly: 指定月のみ。
  - range: 開始月〜終了月。
  - annual: 1月〜12月。
- 受注0件の月も、新版により0件となったことを表現できるようにする。
- 全対象月の切替を同一sales DB transactionで行う。

#### Medium-1: M列合計・N列金額の不一致を無条件エラーにしている

対象:

- `app/Services/SalesAnalysis/SalesImportValidator.php` の `buildOrder()`

推奨判定:

| 状態 | 結果 |
|---|---|
| N列から受注金額を確定でき、M列合計も一致 | 正常 |
| N列から受注金額を確定できるが、M列に空欄がある | 警告付き取込可能 |
| N列から受注金額を確定できるが、M列合計と不一致 | 警告付き取込可能 |
| N列から受注金額を確定できない | ブロッキングエラー |

売上総額、前月比、前年同月比、得意先別売上はN列由来の`order_amount`を使う。分類別・項目別内訳はM列由来の`line_amount`を使うため、次の値を必ず算出する。

```text
受注金額合計（N列基準）
明細内訳合計（M列の入力済み値）
未配賦額 = 受注金額合計 - 明細内訳合計
```

未配賦額はプレビュー、ダッシュボード、Excel出力で確認可能にし、差額を隠さない。

最終的に「M/N不一致でも警告付きで確定可能」とするかはユーザー確認が必要。Claude Codeは変更前に一問だけ確認すること。

#### Medium-2: 日付の実在性を検証していない

対象:

- `app/Services/SalesAnalysis/SalesWorkbookReader.php` の `normalizeDate()`

現在の正規表現では`2026/02/31`等も形式上通過する。`checkdate()`等で実在日を検証し、不正日はブロッキングエラーにする。

#### Medium-3: floatで金額を扱っている

対象:

- `SalesWorkbookReader::normalizeNumber()`
- `SalesImportValidator::buildOrder()`
- 差額計算箇所

現在は金額をfloatへ変換し、`array_sum()`と0.01許容で比較している。帳票が円単位整数だけなら直ちに誤差が出る可能性は低いが、DBはDECIMALなので、検証も文字列decimalまたは整数円へ統一する方が安全である。

初期修正では少なくとも、通貨列が円単位整数であることを検証して整数として比較する。小数金額が業務上あり得る場合はBCMath等を含め別途方針を決める。

### 6.3 「空欄でも取り込む」の安全な定義

採用推奨:

- 完全空行と合計行は従来どおり除外する。
- データ行は、説明項目が空でもスキップしない。
- 空欄は原則NULLで保存する。
- 説明項目や明細内訳の空欄は警告にする。
- 受注No、日付、受注金額を確定できない受注が一つでもあれば、ファイル全体を確定不可にする。
- 一部行または一部受注だけを黙って落とす部分取込は行わない。

この定義なら、ユーザー要望の「空データはエラーなしでとりあえず取り込み」を満たしつつ、売上総額や監査可能性を保てる。
