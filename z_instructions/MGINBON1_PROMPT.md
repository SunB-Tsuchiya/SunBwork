# MGinbon（銀本制作進行管理）再開プロンプト 1

## 目的

FileMakerの`N_DBSystem`で管理している毎年1月～6月の中学入試問題集制作を、
SBWorkの専用MGinbonモジュールへ移行する。既存NSystem／NDBは完成した入試問題の
検索・データベース機能であり、銀本制作進行管理とは名称・責務を分離する。

管理者にはFileMakerに近い統括表を残し、作業者には既存Coordinator進行表型の作業表を提供する。
両方は同じMGinbon正規データを参照し、作業者の登録を統括表へ自動反映する。
ProjectJobAssignment、Event、JobBox/MyJobBox、日報候補、作業レポートへ連携し、二重入力をなくす。

## 合意済み方針

- 銀本制作進行管理専用のMGinbonモジュールを作る。
- 管理画面は既存進行管理表の見た目に縛らず、FileMaker利用者の移行しやすさを優先する。
- FileMakerライクな管理台帳と、Coordinator進行表型の作業用進行表を切り分ける。
- 作業用進行表は必要なセルだけをジョブ化し、JobBox/MyJobBoxと統合する。
- 作業者の担当・完了・Event工数は管理台帳へ自動反映し、管理者に再入力させない。
- 現物を渡された作業者が全対象行・空き作業から該当セルを自分で選び、自己割当する。
- 自己割当とカレンダー作業登録は別操作とし、担当確保だけでは開始日を記録しない。
- 最初のカレンダーEvent作業日を対応する校正入り、完了にしたEventのJST作業日を校正UPへ
  自動反映する。複数日にまたがる場合は既存の続き作業（`source_assignment_id`）を利用する。
- 既存進行表↔Assignment↔Eventの往復連携を再利用する。MGinbon側はAssignment完了処理から
  作業パッケージ・対象工程タスク・管理台帳を明示同期し、`progress_cells`を正本にしない。
- 問題・解答は4科目一括を既定、α版の解説解答・傾向と対策等は科目別を既定とし、登録時の
  科目チェックでどちらにも変更できる。4科目一括は1つの作業パッケージ・Assignmentとして扱い、
  同じ担当や日付を4回入力させず、カレンダージョブも4件に増やさない。
- MGinbon専用の正規化テーブルを正規データとする。
- MGinbon正規データはSBWork本体DBへ混在させず、専用MySQL接続`mginbon`へ保存する。
- 専用DB内を年度プロジェクトで分け、年度ごとの物理DBは増やさない。
- 2026年FileMaker全件データは書込みなしのドライラン後、専用DBへ検証用仮移行する。
- WorkflowSheetのUI・連携パターンは再利用するが、`workflow_cells`へ全データを詰め込まない。
- 科目・工程を行データとして保持する。
- 最上位の進行単位は学校だけにせず、学校と冊子共通部品を扱う。
- 問題・解答が物理的に別冊子となるため、`mginbon_booklets`で冊子を区別する。
- `OP`はInDesign組版・修正オペレーター。各校はOPと校正の組で進み、内部実績は分ける。
- `出`はクライアントを含む共有サーバーへの出稿日。校正入り、校正UP、管理者集約後の
  OPへの戻りは別の節目として保存する。
- `初校校正=初_校正`は初校出稿後の文字突き合わせ、`校正①=再_校正1`は再校出稿前の
  スキャン図照合、`校正②=再_校正2`は再校出稿後の文字突き合わせ。
- 初期画面はFileMakerの段階別担当欄に沿い、同時複数校正者の入力欄を追加しない。
- 柔軟性は工程定義と内部参加者構造で確保する。
- 校正管理者の確認・集約は`戻り`に含み、個別ジョブ・工数は初期実装しない。
- `みくに戻りOP`は、三校時のクライアント現物確認後、戻った赤字を社内赤字と突き合わせて
  転記・修正する担当。タイミングには変動があるため固定順序でブロックしない。
- `初チェック`はOCR・組版後、初回出稿前に学校名、図版、大問、問題番号等を確認する
  体裁・構成チェック。文字突き合わせ校正とは別。
- 初校は原則OP→初チェック→出稿→校正入り→校正UP→戻り。クライアントの本格確認は三校時。
- 再校周辺は、スキャン画像反映→校正①（スキャン図照合）→再校出→校正②（文字校正）の順。
  再校修正=OP、その後の校正=赤字照合。
- 再校出・校正入り・校正UP・再校戻り・三校出は日付。赤字照合後に三校を出稿する。
- LISTの`原本scan納品日_国語`は国語専用でなく、4科目セット共通の代表スキャンUP日。
- 専門チームが初校後に原本の写真・細密グラフ等をスキャンし、画像を再校へ反映する。
- 原本スキャンは社内なら製版部門（個人不要）、社外なら既存`subcontractors`を選択する。
- 文字入力・作図・スキャンは個人より社内／外注先／前年流用と進行状態を重視する。
- scan／作図点数は入稿時に文字原稿から分けた図版の個数。図版を人がscan／drawingへ振り分け、
  さらに社内／外注へ分ける。科目別4区分の合計が図版総数。
- 図版点数の空欄と0は業務上同義。正規データと新規入力初期値は0、移行元値だけ保持する。
- 外注先別の点数・工数・将来の単価・外注費集計へ拡張可能な明細構造にする。
- OP・校正は個人Assignment・Eventから担当件数・作業時間を統計化する。
- 商品は書店向け印刷物と学校別α版デジタル販売を分ける。
- 書店向けは年度ごとに国語・算数・社会・理科の4商品があり、それぞれ問題冊子＋解答冊子で構成。
- α版対象校は毎年度のリスト取込で決定し、問題・解説解答・解答用紙・傾向と対策の
  実在媒体で学校別商品を構成する。学校マスターへ固定しない。
- 2026年度Excelは177掲載行、α対象63行。全177みくにコードがFileMakerと一致。
  α区分は①13、②16、③13、④17、関西4で、コード帯から推測せずExcel値を正とする。
- みくにコード帯100／200／300／500は年度版の共学／男子／女子／地方分類。
- 問題・解説解答・解答用紙は入試回単位。傾向と対策は年度×学校で1件で、第二回等の
  別掲載行には複製しない。2026年度の差分6件は欠落ではない。
- `解説解答`は解説＋解答、`解答のみ`は書店向け解答冊子用の学校別解答、媒体`解答`は
  解答冊子の表紙・目次・奥付等の共通データ。
- 全件ファイル末尾の冊子共通表紙1件は媒体`問題`が誤りで、正しくは`解答`。補正履歴を残す。
- FileMaker同様、担当者・外注先・媒体・科目・工程等は候補セレクターで入力する。
- 取込プレビューで元値と候補を並べ、人が選び直せるようにする。確定値・修正者・履歴を保持する。
- 初期実装の画面・項目・工程はFileMakerにある要素へ厳密に沿う。柔軟性は内部設定で確保し、
  FileMakerにない入力項目を推測で追加しない。
- Assignment→Event→作業実績→日報候補の流れを作る。
- MGinbon専用正規化データを正本とし、既存進行管理表はUIパターンを再利用する。
- 学校マスターを新設せず、既存NSystemの`n_schools / n_school_years / n_exam_series /
  n_exams / n_publication_entries`を共用する。MGinbon制作単位は原則`n_exams.id`へ接続する。
- Mコードは恒久学校属性ではなく、年度版`n_publication_entries`の属性として扱う。
- 担当作業は`project_job_assignments`、実績時間は`events`へ接続する。
- MGinbon進行表から学校・媒体・科目・工程を選んで既存形式の依頼ジョブを作り、作業者が
  JobBox／MyJobBoxからカレンダーへ作業時間を登録する。分数の直接入力は追加しない。
- `diaries`は自由記述を自動上書きせず、銀本実績から確認可能な日報候補を提示する。
- DDRの13値一覧は抽出済み。社員・外注先・状態語が同じ候補一覧に混在するため、旧値対応表で
  `users`、`subcontractors`、工程状態、実施区分へ分け、元値と確認履歴を保持する。
- FileMakerの合計・計算項目は原則再計算する。
- 元FileMakerレコードとの対応を保持する。
- 外注先は直接ログインせず、社内担当者が外注先・状態・日付・点数を入力する。
- SuperAdmin、Admin、Leader、Clerk、CoordinatorはMGinbonで同じ管理権限を持つ。Leaderを
  部署範囲へ限定しない。既存`CoordinatorMiddleware`の許可ロールを基礎にする。
- Proof Adminは全体閲覧を許可し、校正担当・校正入り・校正UP・校正状態等の校正関連項目だけを
  編集可能にする。API側でも更新可能フィールドを制限する。
- 原稿PDF、OCR、InDesign、校正PDF等の制作ファイルはMGinbonへ添付・移行せず、従来どおり
  共有サーバーで管理する。
- 管理台帳、共有進捗、出稿表、文字入力・作図・原本スキャン発注書は印刷専用HTMLを用意し、
  ブラウザーから印刷またはPDF保存できるようにする。Mac専用帳票は共通Web帳票へ統合する。
- 出稿作業票は紙原稿と一緒に回す。問題・解答のみは学校単位、解説解答等は科目単位で対象教科へ
  赤丸を付ける。工程行・順序・表示名・`突き合わせ→`等の補助文言・手書き欄をテンプレートで
  カスタマイズ可能にする。
- みくに出版には既存進行表の共有URLを基礎とした読み取り専用進捗ビューを提供する。
  公開項目はサーバー側allowlistで限定し、社員名・校正者名・外注先名・時間・社内メモ・費用を隠す。
- 本番進行表ID 5は531行、入力済みセル52、Assignment 51、Event接続50の疎な運用だった。
  この作業選択方式を継承するが、旧データのAssignment保存上の互換仕様は模倣しない。

## 重要な実装規則

- 新規ページは`AppLayout`を使い、重複する`main`、`py-12`、`max-w-7xl`を置かない。
- SPAルートは`routes/web.php`。
- Ziggy引数は名前付きオブジェクト。
- 日付castは`date:Y-m-d`。
- Vueでローカル日付に`toISOString()`を使わない。
- EventのUTC/JST混在は`CalculatesEventTime`を使用。
- CSVは`NormalizesCsvEncoding`でShift-JIS、CRLF、BOMに対応。
- `source_assignment_id`と`supersedes_assignment_id`を混同しない。
- 売上DBの本番レコードを参照しない。
- destructive DB操作をサブエージェントへ委任しない。
- `migrate:fresh`は対象DB確認と`--database=`必須。
- 既存変更を上書き・巻き戻ししない。
- Vue/JS変更後は`npm run build`。
- 完了時はChangelogSeeder、関連CONSOLIDATED文書、archive移動を行う。
