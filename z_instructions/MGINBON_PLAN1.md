# MGinbon（銀本制作進行管理）計画 1

作成日: 2026-09-17  
状態: Phase 1移行検証準備（実装未着手）

## 1. 目的

毎年1月から6月に実施する中学入試問題集制作について、FileMaker版
`N_DBSystem`の一覧性と業務知識を維持しながら、SunBWork（以下SBWork）の
ユーザー、案件、ジョブ割当、カレンダー、作業時間、日報へ統合する。

単純なFileMaker画面の移植ではなく、次を実現する専用モジュールとする。

- 進行管理者は学校・媒体・科目・工程をFileMakerに近い一覧で管理できる。
- 作業者は作業用進行表から担当可能な作業を選ぶか、割当済み作業を受け取り、
  JobBox／MyJobBoxとカレンダーで実績を登録できる。
- 作業者の開始・終了・完了操作を進行状況、作業時間、日報候補へ一度に反映する。
- 外注先別、学校別、媒体別、科目別、工程別、担当者別に集計できる。
- 将来、外注先別の工数・点数・単価・外注費を集計できる。
- 過去年度を検索・比較・複製し、翌年度の初期データへ流用できる。
- FileMakerの過去データを段階的かつ検証可能な形で移行する。

### 初期実装のスコープ原則

- 現行作業はFileMakerに存在する項目・工程・帳票要素に沿う。
- FileMakerにない作業項目や入力義務を、推測で初期実装へ追加しない。
- 柔軟性は、担当人数、工程定義、表示列、媒体・科目等を設定で変更できる内部構造で確保する。
- 将来用の構造を持つことと、現行画面へ未使用項目を表示することを分ける。
- 追加機能は現行移行後、利用者の明示要望に基づいて段階導入する。
- 原稿PDF、OCR、InDesign、校正PDF等の制作ファイルはMGinbonへ保存・移行せず、従来どおり
  共有サーバーで管理する。MGinbonは進行情報を正本とする。

## 3. 設計原則

### 3.1 ハイブリッドUI

- 同じMGinbon正規データから、用途の異なる二つの表を生成する。
- 管理台帳はFileMaker利用者が移行しやすい学校単位のまとまり、色分け、横長の表構造を維持し、
  日付、担当、点数、全工程を統括する。
- 作業用進行表は既存Coordinator進行表の操作を基礎にし、必要な作業セルだけをジョブ化する。
- データ・権限・ジョブ連携にはSBWorkの既存基盤を利用する。
- 作業者には役割・担当・未割当等で絞り込める簡潔な表を提供し、管理台帳の全項目入力を要求しない。
- 両方の表は別データを持たず、作業者による担当・完了・実績登録を管理台帳へ自動反映する。
- 実際の原稿・校正紙等を手渡された担当者が、作業用進行表で該当する学校・媒体・科目・工程を
  自分で選択して自己登録する。通常作業の登録を管理者の代理入力へ戻さない。

### 3.2 正規化

`初校出_国語`のようなフィールドを新DBの列として再現しない。

```text
年度 → 冊子（問題冊子／解答冊子等） → 制作単位（学校／冊子共通） → 媒体 → 科目（任意） → 工程 → 作業実績
```

科目や工程を行データとして保持し、新工程・新科目・新年度の追加でマイグレーションを
必要としない構造にする。

### 3.2a 専用データベース

MGinbonの正規データ、取込履歴、帳票設定、共有設定はSBWork本体DBへ置かず、専用MySQL
データベース接続`mginbon`へ保存する。年度ごとに物理DBを増やすのではなく、専用DB内の
`mginbon_projects.year`を年度境界とし、すべての業務データを年度プロジェクトへ帰属させる。

- 接続設定は`MGINBON_DB_*`環境変数で管理し、本体DB資格情報と分離する
- MGinbonモデルは明示的に`mginbon`接続を使用する
- MGinbon migrationは専用パスで管理し、実行時に接続先DB名を確認する
- 本体DBのusers、subcontractors、project jobs、assignments、eventsとの関連はIDを記録するが、
  DBをまたぐ物理外部キーは作らない。アプリケーション層で存在確認・権限確認を行う
- 年度をまたぐ照会は専用DB内で行い、年度別の絞り込み・比較・翌年度複製を提供する
- 2026年FileMakerデータは最初に書込みなしでドライランし、その後この専用DBへ検証用仮取込する
- 元ファイルと元値を保持し、再実行可能にする。本番確定は件数・点数・警告のレビュー後に行う

### 3.3 一回の入力を複数機能へ反映

```text
管理者または作業者が作業セルを選択
  → project_job_assignments作成
  → 作業者のJobBox/MyJobBoxへ表示
  → 作業開始時にeventsで作業時間の記録を開始し、工程の開始節目を自動記録
  → 作業終了・完了時に工程の終了節目を自動記録
  → MGinbon工程実績と管理台帳を更新
  → 日報候補・日別レポートへ集計
```

進行表と日報への二重入力を避ける。

### 3.4 履歴優先

現在値だけでなく、担当変更、日付変更、開始、終了、完了、差し戻しを履歴として残す。
FileMaker移行値には元レコード・元フィールドを追跡できる情報を保持する。

### 3.5 選択式入力と人による補正

- FileMakerのセレクター運用を引き継ぎ、担当者、外注先、媒体、科目、工程、状態等は
  原則としてマスター連動のドロップダウン／候補検索で入力する。
- 取込時の自動マッピング結果は確定扱いにせず、プレビューで人が選び直せるようにする。
- 元値、候補値、確定値、修正者、修正日時を保持する。
- 未一致値や曖昧一致を勝手に近い候補へ置換しない。
- 選択肢にない正当な値は、権限者がマスター追加してから選択できるようにする。
- 通常画面でも権限者は誤入力を選択式で修正でき、変更履歴を残す。

## 4. 用語と管理単位

| 用語 | 意味 |
| --- | --- |
| 年度プロジェクト | 例: 2026年中学入試。1月から6月の全体単位 |
| 商品／販売形態 | 書店向け印刷物、学校別デジタル販売（α版）等 |
| 冊子 | 印刷商品内で物理的に分かれる問題冊子、解答冊子等 |
| 制作単位 | 年度内の進行管理単位。学校、または表紙・目次・奥付等の冊子共通部分 |
| 入試回案件 | 制作単位の一種。年度別試験、日能研コード、みくにコード等を持つ |
| 学校共通コンテンツ | 傾向と対策等、同年度の複数入試回で共有する学校単位の制作物 |
| 冊子共通 | 表紙、扉・目次・奥付、ノンブル通し等。学校コード・科目を持たない場合がある |
| 媒体 | 問題、解説解答、解答用紙、傾向と対策、解答のみ等 |
| 科目 | 国語、算数、社会、理科。将来追加可能 |
| 工程 | 入稿、文字入力、作図、初校、再校、三校、四校、五校、校了等 |
| 工程作業 | 制作単位×媒体×科目（任意）×工程の実作業単位 |
| 作業実績 | 誰が、いつ、何分、何を行ったかという追記型記録 |

校正サイクルは、各校を単一作業として扱わず、次の職種を一組にする。

- OP: InDesignでデータを組み、指示に応じて修正する組版オペレーター
- 校正: 組版結果を一字一句突き合わせる校正担当者

現行FileMakerでは、`初校校正`、`校正①`、`校正②`は工程上の別段階である。
内部名は`初校校正=初_校正`、`校正①=再_校正1`、`校正②=再_校正2`である。
初校校正は初校出稿後の文字突き合わせ、校正①はスキャン図が正しく入ったかを再校出稿前に
照合する工程、校正②は再校出稿後に初校校正と同水準で行う文字突き合わせである。
初期画面に同時複数校正者の入力枠を追加しない。将来の変更可能性は工程定義で確保する。

画面上は「初校」「再校」「三校」等でまとめ、内部ではOP担当・各段階の校正担当・受け渡し日・
各作業実績を区別する。これにより、OPと校正それぞれの日報・工数・担当履歴を集計できる。

各校の主要な節目は次の意味で扱う。

| FileMaker表記 | 意味 | MGinbon上の扱い |
| --- | --- | --- |
| OP | InDesignで組版・修正する担当者 | operation担当・Assignment |
| 出 | 出稿。クライアントを含む共有サーバーへ原稿をアップした日 | published/shared milestone |
| 校正入り | その段階の校正担当へファイルを渡した日 | participant handed_at |
| 校正UP | その段階の校正担当が作業を終えた日 | participant completed_at |
| 戻り | 校正管理者等が結果を確認・集約し、修正OPへ渡した日 | returned_to_operation_at |

`出`は校正入りと同義ではなく、クライアント共有を含む独立した節目である。

初回はフォトコピー原稿をOCR・テキスト化して組版する。初校出稿前に、学校名、図版、
大問、問題番号等の欠落・取り違えを確認する`初チェック`を行う。これは一字一句を原稿と
突き合わせる文字校正とは別作業である。初校の順序は原則として、OP組版→初チェック→
出稿→校正入り→校正UP→戻りとなる。

クライアントは共有サーバー上の原稿を閲覧できるが、三校までは原則として本格チェックを
行わない。三校時に実際の印刷物を用いて本格確認する。

原本は学校から封筒で届く実際の試験問題一式で、4科目セットとして進行する。写真や数値の
細かいグラフ等は専門チームが原本からスキャンし、初校後に画像を反映して再校を出す。
LISTの`スキャンUP`は4科目共通の工程節目で、FileMaker内部名の`_国語`は代表セルを国語行へ
置いた画面上の都合である。MGinbonでは科目別日付と誤解せず、制作単位共通の日付として扱う。
原本スキャン担当は個人ではなく実施先を管理し、社内は製版部門、社外は既存`subcontractors`
と連動する。

入稿時に原稿を文字原稿と図版原稿へ分ける。図版原稿は三角形、グラフ等の個々の図版で、
人が内容に応じて作図または原本スキャンへ振り分ける。たとえば図版10点をスキャン3点、
作図7点とする。さらに各作業の実施先を社内／社外へ分けるため、科目ごとの図版総数は原則として
`社内scan + 外注scan + 社内作図 + 外注作図`で表せる。
点数欄の空欄と明示的な0には業務上の意味差がなく、入力者の習慣による。MGinbonでは双方を
数量0へ正規化し、新規入力の初期値も0とする。ただし移行監査用の元値は保持する。

文字入力・作図・スキャンは、個人名より実施元と進行状態を重視する。

- 実施元: 社内 / 外注先 / 前年度等から流用
- 進行状態: 未着手 / 作業中 / 完了
- 社内: 原則として個人を要求しない。必要な場合だけ部門を保持する。
- 社外: 既存`subcontractors`へ紐付ける。
- 流用: 元年度・元制作物を追跡可能にする。
- 科目別の点数・工数を保持し、将来の外注費集計へ利用できるようにする。

再校周辺では、FileMakerの各列を次のように区別する。

- 再校出、校正入り、校正UP、再校戻り、三校出: 日付の節目
- 校正①: スキャン図が正しく配置・反映されているかを再校出稿前に照合する担当
- 校正②: 再校出稿後の一字一句の文字校正担当（内部名`再_校正2`）
- 再校修正: 赤字を反映するInDesignオペレーター
- 校正: 赤字指示どおり修正されたかを確認する赤字照合担当

再校は、スキャン画像反映→校正①によるスキャン図照合→再校出稿→校正②による文字突き合わせ
の順で進む。赤字照合は文字校正やスキャン図照合とは別作業であり、再校修正後、三校を
クライアントへ出稿する前の品質確認として行う。

三校時にはクライアント「みくに」へ実際の印刷物を渡して確認を受ける。戻ってきた赤字を
社内赤字と突き合わせ、転記・修正するOPを`みくに戻りOP`として管理する。タイミングには
変動があるため、固定順序で工程進行をブロックしない。

FileMakerの1レコードは原則として制作単位×媒体。制作単位には学校と冊子共通部分がある。
同名・同媒体の複数レコードが存在するため、版・枝番等の識別方法は追加確認する。
移行ロジックでは推測せず、コード・媒体・重複状況を検査する。

## 5. 推奨データモデル（初稿）

以下のテーブルは専用`mginbon`接続に作成する。接頭辞は`mginbon_`を用い、汎用機能との境界を
明確にする。

### 5.1 `mginbon_projects`

- `id`
- `project_job_id`（SBWork案件。原則1年度につき1件）
- `year`
- `name`
- `starts_on`, `ends_on`（`date:Y-m-d`）
- `status`（draft / active / closed / archived）
- `created_by`
- timestamps

制約候補: `year`または`project_job_id`を一意とする。複数版運用の可能性を確認後に確定。

### 5.2 MGinbon年度別学校・試験情報とNSystem任意連携

MGinbonは専用DB内の年度制作単位を正本とし、FileMakerからみくにコード、日能研コード、年度学校名、
入試回表記を取り込む。既存NSystemの次のテーブルは、同年度データが存在して一致した場合だけ
任意リンクとして利用する。

- `n_schools`: 恒久学校。`n_code_prefix`と正式名称を保持
- `n_school_years`: 年度別学校名・属性
- `n_exam_series`: 学校内の入試回系列
- `n_exams`: 年度別Nコード付き試験
- `n_publication_editions`: 年度版書籍
- `n_publication_entries`: 年度版のMコード掲載行

FileMakerの日能研コードとみくにコードはMGinbon年度制作単位へ保存する。Mコードを恒久学校属性には
しない。NSystemに同年度の`n_exams`、`n_publication_entries`がある場合は照合し、`n_exam_id`等を
補助参照として保存できる。候補が複数または未一致でもMGinbonの取込を止めず、自動確定もしない。

2026年ローカル調査ではFileMakerの異なるNコード177件・みくにコード177件に対し、NSystem側の
2026年度一致件数はいずれも0件だった。このためNSystemリンクを必須FKまたは移行条件にしない。

### 5.3 `mginbon_booklets`

年度内で物理的に分かれる冊子を管理する。

- `id`
- `mginbon_project_id`
- `code`（problem / answer等）
- `name`（問題冊子 / 解答冊子等）
- `binding_note`（巻末糊付け等、必要な場合）
- `sort_order`
- timestamps

同じ「表紙」「ノンブル通し」でも冊子が異なれば別の制作単位として保持する。

### 5.4 `mginbon_product_types` / `mginbon_project_products`

同じ学校・媒体データから作られる販売形態を年度単位で管理する。

初期商品区分:

- `print_bookstore`: 教科別に問題冊子と解答冊子からなる書店向け印刷物
- `digital_alpha`: 対象校ごとのα版デジタル商品

書店向け印刷物は年度ごとに次の4商品を作る。

- 2026年度 国語
- 2026年度 算数
- 2026年度 社会
- 2026年度 理科

各教科商品は物理的な問題冊子と解答冊子で構成する。

`mginbon_project_products`候補項目:

- `id`
- `mginbon_project_id`
- `product_type_id`
- `mginbon_subject_id`（書店向け教科別商品の場合）
- `n_school_id`（学校別α版の場合。既存`n_schools.id`）
- `name`
- `status`
- `sort_order`
- timestamps

書店向け商品の一意候補は`mginbon_project_id + product_type_id + mginbon_subject_id`。
α版は年度・学校・商品区分で管理し、構成媒体を別明細にする。問題・解説解答・解答用紙は
入試回単位、傾向と対策は学校単位であり、1商品内で異なるスコープの媒体を組み合わせられるようにする。

α版対象校は学校マスターの固定属性にしない。毎年度の対象校リスト取込で
`mginbon_project_products`と構成媒体を生成・更新する。

2026年度ExcelのC列は①～④・関西のαグループを持ち、対象は63掲載行。177掲載行すべてが
FileMakerのみくにコードと一致したため、このExcelを年度制作対象の正本として取り込み、
FileMakerに実在する媒体と結合して商品構成を作る。α媒体が存在しない場合は空レコードを作らない。

### 5.5 `mginbon_production_units`

年度ごとの制作単位。入試回、学校共通コンテンツ、冊子共通ページを同じ進行基盤へ載せる。

- `id`
- `mginbon_project_id`
- `mginbon_booklet_id`（冊子共通では必須候補。学校では運用確認後に設定）
- `unit_type`（exam / school_content / book_component）
- `n_school_id`（exam / school_contentの場合。既存`n_schools.id`）
- `n_exam_id`（examの場合。既存`n_exams.id`）
- `display_name`
- `nichinoken_classification`
- `ginbon_included`
- `note`
- `sort_order`
- timestamps

入試回案件は`mginbon_project_id + n_exam_id`、学校共通コンテンツは
`mginbon_project_id + n_school_id + unit_type`を重複候補判定に使う。冊子共通は同名が複数存在し得るため、
表示名だけで一意制約を置かない。exam行の`n_school_id`は`n_exam_id`から得られる学校と一致させる。

### 5.6 `mginbon_media_types`

- `id`, `code`, `name`, `sort_order`, `active`
- 初期候補: problem / explanation / answer_sheet / trend / answer_only

媒体の意味:

- `解説解答`: 解説と解答を含む学校別データ。主にα版デジタル商品で使用。
- `解答のみ`: 解説を除き、解答だけにした学校別データ。書店向け解答冊子に掲載。
- `傾向と対策`: 入試回別ではなく年度×学校で1つの学校共通コンテンツ。第二回等へ複製しない。
- `解答`: 学校別の解答内容ではなく、解答冊子の表紙・目次・奥付等の冊子共通データを
  区別するFileMaker上の媒体値。

同じ「解答」という語でも、学校別コンテンツと冊子共通区分を混同しない。

### 5.7 `mginbon_subjects`

- `id`, `code`, `name`, `sort_order`, `active`
- 初期値: Japanese / Math / Social Studies / Science

画面表示は国語・算数・社会・理科とする。

### 5.8 `mginbon_items`

制作単位内の媒体単位。

- `id`
- `mginbon_production_unit_id`
- `mginbon_project_product_id`（商品構成へ属する場合）
- `mginbon_media_type_id`
- `legacy_filemaker_record_id`
- `version_label`（例: α版-4）
- `note`
- `sort_order`
- timestamps

一意制約は全件データ調査後に決める。同一制作単位・媒体の複数版を許容する可能性がある。
商品と媒体は別明細（product item pivot）でも接続し、学校別α商品が入試回媒体と学校共通媒体を
同時に参照できるようにする。

### 5.9 `mginbon_item_subjects`

媒体に存在する科目単位。

- `id`
- `mginbon_item_id`
- `mginbon_subject_id`
- `enabled`
- `sort_order`
- timestamps

一意制約: `mginbon_item_id + mginbon_subject_id`。

### 5.10 `mginbon_stage_definitions`

年度テンプレートとして使用できる工程定義。

- `id`
- `code`, `name`
- `group_code`（intake / input / drawing / proof / completion等）
- `round_number`（初校=1、再校=2、三校=3等。適用外はnullable）
- `activity_type`（operation / proofreading / handoff / completion等）
- `sequence`
- `uses_assignee`
- `uses_subcontractor`
- `uses_ordered_on`, `uses_delivered_on`, `uses_sent_on`, `uses_returned_on`
- `uses_quantity`
- `active`
- timestamps

初校・再校等を固定カラムにせず、順序を持つ定義にする。

### 5.11 `mginbon_stage_tasks`

制作単位×媒体×科目（任意）×工程の現在状態。

- `id`
- `mginbon_item_subject_id`
- `mginbon_stage_definition_id`
- `status`（not_started / assigned / in_progress / completed / blocked）
- `planned_on`, `original_scan_completed_on`, `published_on`, `proof_handed_on`, `proof_completed_on`,
  `returned_to_operation_on`, `completed_on`
- `deadline_on`
- `quantity`
- `note`
- `completed_at`
- timestamps

日付だけの業務日は`date`で持ち、Eloquentは`date:Y-m-d`を使用する。

### 5.12 `mginbon_stage_task_participants`

OP、校正者等を工程段階ごとに割り当てる。内部構造は将来の複数担当にも対応可能とするが、
初期画面と取込はFileMakerの担当枠に沿う。

- `id`
- `mginbon_stage_task_id`
- `role_type`（operation / proofreader等。初期値はFileMakerの役割に限定）
- `user_id`（社内担当者。外注の場合nullable）
- `department_id`（個人を特定しない社内部門担当の場合）
- `subcontractor_id`（外注先。社内の場合nullable）
- `project_job_assignment_id`（担当者ごとのSBWorkジョブ）
- `sequence`
- `status`（assigned / in_progress / completed / cancelled）
- `handed_on`
- `completed_on`
- `note`
- timestamps

制約・規則:

- 役割に応じ、`user_id`、`department_id`、`subcontractor_id`のいずれかを使用する。
- 原本スキャンは個人を管理せず、社内なら製版部門、社外なら外注先を指定する。
- 初期実装では1工程段階につきFileMaker上の担当枠を1つ表示する。
- 科目別作業は各参加者にAssignment、Event、作業実績を関連付ける。4科目一括作業は
  作業パッケージ側の1件を共有し、同じジョブを科目数分複製しない。
- 工程全体の完了条件は、FileMakerの段階に対応する担当作業の完了とする。
- 校正管理者の集約は`戻り`の日付へ反映するが、初期実装では個別Assignmentや工数を作らない。

### 5.12a `mginbon_work_packages` / `mginbon_work_package_tasks`

4科目を同じ担当者が一括して行う作業を、4回入力・4ジョブ化せず扱うための作業パッケージ。

`mginbon_work_packages`候補項目:

- `id`
- `mginbon_project_id`
- `project_job_assignment_id`（1パッケージにつき原則1件）
- `stage_definition_id`
- `user_id`または`subcontractor_id`
- `status`
- `started_on`, `completed_on`
- timestamps

`mginbon_work_package_tasks`は、1つのパッケージと複数の`mginbon_stage_tasks`を結ぶ。

- 問題・書店向け解答系は4科目選択を既定値にできる。
- α版の解説解答・傾向と対策等は、操作した科目だけを既定値にできる。
- 既定の選択範囲は商品・媒体設定として持ち、画面上で科目チェックを変更可能にする。
- 一括選択してもAssignmentとカレンダーEventを4件に複製しない。
- 担当、開始、完了、対応する入り／UP日を参加タスクへ一括反映する。
- パッケージ全体の作業時間を根拠なく科目へ等分しない。
- 進行開始後の分割は管理者操作と履歴を必要とする。

### 5.13 `mginbon_work_logs`

銀本工程と既存カレンダーイベントを結ぶ構造化作業実績。作業時間の正本は`events`とする。

- `id`
- `mginbon_stage_task_id`
- `mginbon_stage_task_participant_id`（担当者別実績の場合）
- `mginbon_work_package_id`（複数科目一括作業の場合）
- `user_id`
- `project_job_assignment_id`
- `event_id`（時間を伴う実績では必須）
- `worked_on`（`date:Y-m-d`）
- `quantity`
- `content`
- `source`（user / coordinator / import / system）
- timestamps

作業時間の正規データを`events`と二重に持たない。`event_id`参照で集計し、MGinbon側に
手入力分数を持たせない。数量・作業内容だけを補助情報として保持できる。

### 5.14 `mginbon_stage_task_histories`

- 対象タスク
- 操作者
- action
- before / after JSON
- occurred_at

監査と差し戻し調査に使用する。機密値を不要に複製しない。

### 5.15 `mginbon_legacy_mappings`または取込バッチテーブル

- 年度、元FileMakerレコード識別子
- 元フィールド名
- 移行先種別・ID
- 変換結果、警告、取込バッチID

再実行可能性と照合に使う。元の全行JSONを恒久保存するかは容量・機密性を考慮して決定する。

### 5.16 `mginbon_work_measurements`

文字入力・作図・スキャン等の数量・工数と実施元を保持する。FileMakerのscan／作図の「点数」は、
ページ数や時間ではなく個々の図版数である。初期実装ではこの図版数を扱い、単価・金額入力は
将来フェーズで有効化する。

- `id`
- `mginbon_stage_task_id`
- `mginbon_item_subject_id`（4科目共通の場合nullable）
- `work_type`（text_input / drawing / scan等）
- `execution_type`（internal / subcontracted / reused）
- `department_id`（社内部門。不要な場合nullable）
- `subcontractor_id`（社外の場合）
- `source_mginbon_item_id`（前年等から流用した場合）
- `status`（not_started / in_progress / completed）
- `quantity`
- `unit_code`（初期scan／drawingは`figure`。将来、頁・件等を追加可能）
- `minutes`（外注工数等を管理する場合。初期はnullable）
- `unit_rate_snapshot`（将来。適用時の単価を固定保存）
- `amount`（将来。明細金額）
- `billing_period`（将来。外注費集計月）
- timestamps

単価マスターを後から変更しても過去金額が変わらないよう、費用機能導入時は単価スナップショットを
明細へ保存する。金額は初期FileMaker移行の必須入力にしない。

### 5.17 `mginbon_share_links`

みくに出版が進捗を確認する読み取り専用共有URLを管理する。既存進行表の共有トークン方式を基礎に、
MGinbonでは公開項目をサーバー側allowlistで限定する。

- `mginbon_project_id`
- トークンハッシュ、表示名、公開設定
- 有効期限、失効日時、最終アクセス日時
- 発行者・監査情報

管理台帳全体や内部ID、社員・外注先、Event、社内メモ、費用情報を無条件に返さない。
詳細は`MGINBON_CLIENT_SHARE1.md`を参照する。

### 5.18 帳票テンプレート

出稿作業票は、問題・解答のみを学校単位、解説解答・傾向と対策等を科目単位で出力できるようにする。
科目単位帳票は対象科目へ赤丸を印字する。工程行の表示、順序、表示名、役割ラベル、工程間の補助文言、
手書き作業時間欄・メモ欄を年度／媒体別テンプレートで変更可能にする。

初期版は安全な構造化設定方式とし、自由HTML・任意スクリプト・完全自由配置は提供しない。
候補テーブルは`mginbon_report_templates`、`mginbon_report_template_rows`、
`mginbon_report_exports`。詳細は`MGINBON_REPORTS1.md`を参照する。

## 6. 既存SBWorkとの接続

### 6.1 ProjectJob

年度プロジェクトを既存`project_jobs`の1案件へ関連付ける。
案件の所有者・サブCoordinator・チームメンバー権限を基本として利用する。

### 6.2 ProjectJobAssignment

`mginbon_stage_task_participants.project_job_assignment_id`を既存ジョブ割当への接続点とする。

- Coordinatorが担当設定した場合は通常の依頼ジョブとして作成する。
- MGinbon進行表の学校・媒体・科目・工程セルから既存進行表と同じ操作で依頼項目を選び、
  `project_job_assignments`を作成できるようにする。
- 通常は、現物を受け取った作業者本人が該当セルを検索・選択し、自己割当としてAssignmentを作る。
- 自己割当は担当確保であり、カレンダーへの作業登録とは分ける。自己割当だけでは開始節目を記録しない。
- 4科目セットで動く作業は、選択した4科目の工程タスクを1つの作業パッケージとAssignmentへ
  結び、担当・開始・完了を一括反映する。科目別作業では1科目だけを選べる。
- 作業者はJobBox／MyJobBoxで銀本依頼を受け、そこから既存カレンダー登録へ進む。
- 作業者が自分で追加する必要がある運用は、既存の自己割当規則に従う。
- `source_assignment_id`（続きジョブ）と`supersedes_assignment_id`（置換）を混同しない。
- 完了・未完了・通知は既存サービスへ寄せ、MGinbon側に別実装を複製しない。

### 6.3 Events / 作業時間

`events.project_job_assignment_id`から実作業時間を集計する。

- 作業者は既存方式どおり、各自がカレンダーへ開始・終了時刻を登録する。
- MGinbon独自の「実績○分」直接入力欄は作らない。
- 時刻計算は`CalculatesEventTime`を使用する。
- 通常イベントとproofイベントのUTC/JST混在規則を守る。
- 日付境界はJST。
- カレンダー修正とAssignmentの同期規則を流用する。

工程定義には、最初のカレンダー作業登録と完了がどの管理台帳上の節目に対応するかを設定する。
たとえば校正工程は次のように自動同期する。

```text
校正担当者が自己登録
  → Assignment作成・担当者反映
最初のカレンダー作業登録
  → 校正入り = Eventの作業日（JST）
カレンダーで完了
  → 校正UP = 完了対象Eventの作業日（JST）
```

初校校正、校正①、校正②等の各工程は、それぞれ対応する入り／UP欄へ記録する。担当確保だけでは
実績日を確定せず、最初のカレンダー作業登録と既存の完了操作を契機にする。誤操作や後日入力に備え、
権限者による日付補正と変更履歴を保持する。複数日にまたがる場合は既存の「続き作業」を使い、
`source_assignment_id`で系列化する。開始日は系列最初のEvent作業日、UP日は完了対象Eventの
JST作業日とする。完了処理による祖先Assignmentの完了カスケードも既存仕様を利用する。

既存進行表は、セルとAssignmentを`progress_cell_id`／`assignment_id`で双方向接続し、Eventを
`project_job_assignment_id`で接続している。カレンダー完了時はAssignmentと続き系列の祖先を完了し、
進行表は`progress_cells.completed_at`または関連Assignmentの`completed`から完了表示する。
MGinbonもこの往復連携を流用するが、`progress_cells`を正本にはしない。Assignment完了処理から
MGinbon作業パッケージ・対象工程タスク・対応節目を明示的に同期し、フロント表示だけの推測にしない。

### 6.4 日報

現行`diaries`はユーザー・日付・自由記述が中心であり、Assignmentへの直接FKを持たない。
以下の段階構成とする。

1. 銀本依頼ジョブと紐付くイベントから日別作業サマリーを生成。
2. 日報画面に「銀本作業候補」として表示。
3. ユーザーが補足・修正して日報を確定。
4. 将来、他案件も同じ候補生成へ統合できるよう、MGinbon固有ロジックをサービスへ隔離。

日報本文へ自動追記する場合は、再保存時の重複を避ける識別方法を別途設計する。
初期版では「候補表示＋ユーザー確定」を推奨する。

### 6.5 既存WorkflowSheet

再利用するもの:

- 多段ヘッダー・縦積み表示の考え方
- 担当ユーザー／外注先選択
- Assignment登録・完了への導線
- 工数集計
- テンプレート設計の考え方

そのまま流用しないもの:

- `workflow_cells`をMGinbonの正規データにすること
- 汎用`column_config`だけで全MGinbon業務定義を表現すること
- 1セル1値へ担当・複数日付・点数を詰め込むこと

MGinbon専用テーブルを正規データとし、UIコンポーネントやサービスを必要に応じて共通化する。

本番の既存進行表`中学入試問題集_問題・解答`（進行表ID 5）は、531行に対して入力済みセル52、
Assignment 51という疎な運用であり、必要な作業だけをジョブ化する方式が実運用で成立している。
MGinbonの作業用進行表もこの方式を基礎とする。ただし既存表の旧データでは校正セルが
`assignment_id`へ入る等の旧仕様が残るため、その保存上の癖は継承せず、現行のworker／proof_v2
相当の役割とAssignment接続を明示的に実装する。詳細は`MGINBON_PROGRESS_SHEET5_PROFILE1.md`を参照。

## 7. 画面設計（初稿）

具体的な配置・状態遷移は`MGINBON_WIREFRAME1.md`を参照する。

全ページで`AppLayout`を使用し、ページ側で`main`、`py-12`、`max-w-7xl`を重複させない。
ただし大規模表はカード内で横スクロール・sticky列を使用し、FileMakerの一覧性を優先する。

### 7.1 MGinbonメニュー／ダッシュボード

- 年度切替
- 管理台帳（入稿チェック等の保存ビューを含む）
- 作業用進行表
- 自分の作業（JobBox／MyJobBox）
- 外注集計
- 作業レポート
- 学校検索
- データ取込（権限者のみ）
- 遅延、未割当、未入稿、期限接近の概要

### 7.2 管理台帳（FileMakerライク）

FileMakerのLIST／入稿チェックを一つの統括データの保存ビューとして扱う。

- 冊子・制作単位ごとに媒体カードを縦積み
- 学校と冊子共通（表紙・目次・奥付等）をセクションまたはフィルターで切替
- 科目を横4列（存在科目のみ）
- 入稿予定日／実入稿日
- 文字入力、作図、スキャン担当・点数
- 色分けと警告
- 学校、媒体、分類、担当者、状態で絞り込み
- 入稿チェック／全体／初校／再校／三校以降／校了／外注のビュー切替
- 担当者、日付、状態のインライン編集（権限者のみ）
- 作業用進行表で登録された担当、完了、実績時間を自動反映
- 管理者が全項目を再入力する運用にはしない

### 7.3 作業用進行表（Coordinator進行表型）

既存Coordinator進行表の実績ある操作を基礎にし、オペレーター・校正者等が自ら作業を
登録できる疎な表とする。FileMakerの全管理項目をそのまま並べず、ジョブ化する作業を中心にする。

- 初期列は既存表と同様に初校／再校／三校の段階と、組版／校正の役割を基準にする
- MGinbonの工程定義から列を構成し、将来は工程・担当人数を設定変更できる
- 各セルから担当者または自分を選び、既存形式の依頼ジョブを作成する
- 現物を渡された作業者は全対象行・空き作業を検索でき、該当セルを自分で選択する
- 対象科目をチェックで複数選択でき、「4科目に反映」で国語・算数・社会・理科を一括選択できる
- 問題・解答は4科目を、α版の解説解答・傾向と対策等は選択科目だけを既定値とする
- 自己登録時はログインユーザーを担当者の初期値とし、別人への代理割当は権限で分ける
- 必要な作業だけセルを作成し、全531行×全工程を事前入力しない
- 制作単位・媒体を左側sticky列
- 学校、媒体、科目、役割、担当、未割当、状態で絞り込む
- 作成したAssignmentはJobBox／MyJobBoxとカレンダーへ接続する
- 完了・作業時間は同じMGinbon工程作業へ戻し、管理台帳にも即時反映する
- 通常ユーザーは全対象行・空き作業を閲覧・検索できるが、自分の担当登録と実績入力を基本とする
- 同じ現物への重複自己登録は一意制約または競合確認で防止する

### 7.4 JobBox／MyJobBox・自分の作業

- 今日／今週／期限超過
- 学校、媒体、科目、工程、期限、指示
- 作業開始、作業終了、完了、続きを登録
- 作業内容と点数
- 自分の実績一覧

作業用進行表から作成したジョブを既存JobBox/MyJobBoxへ表示し、MGinbonバッジと学校・媒体・
科目・工程の文脈を加える。必要ならMGinbon専用「自分の作業」フィルターを併用するが、
正規のAssignmentは共通なので二重ジョブは作らない。

初期版では制作ファイルのアップロード、版管理、プレビューを行わない。

### 7.5 日別作業レポート

- ユーザー別、日付別

- 既存進行表と同様に、共有URLの発行、コピー、印刷、無効化を提供する
- みくに出版はログインせず、読み取り専用で最新進捗を確認する
- 公開用の学校・媒体・科目・工程状態・対象日付だけを返す
- 社員名、外注先名、作業時間、社内メモ、費用、内部IDは初期値として非公開
- 共有URLから編集API、JobBox、カレンダーへ到達させない

### 7.9 印刷・PDF

- 管理台帳、クライアント共有進捗、出稿表、文字入力・作図・原本スキャン発注書に印刷専用表示を作る
- ブラウザーの印刷機能で紙印刷またはPDF保存できるようにする
- FileMakerのMac専用レイアウトはWeb版で分けず、共通印刷レイアウトへ統合する
- 社内帳票とクライアント共有帳票で公開項目を分ける
- 詳細は`MGINBON_REPORTS1.md`を参照する
- 問題・解答のみは学校単位、解説解答・傾向と対策等は科目単位を既定とし、対象科目へ赤丸を付ける
- 紙原稿と一緒に回すため、担当者・日付を印字し、作業時間・メモ等の手書き欄を残す
- `突き合わせ→`等の補助文言、工程行の表示・順序・名称を帳票テンプレートで変更可能にする

## 8. 権限案

| 操作 | 権限候補 |
| --- | --- |
| 年度設定・取込 | SuperAdmin / Admin / Leader / Clerk / Coordinator |
| 学校・媒体・工程編集 | SuperAdmin / Admin / Leader / Clerk / Coordinator |
| 担当設定・外注設定 | SuperAdmin / Admin / Leader / Clerk / Coordinator |
| 校正担当・校正入り・校正UP・校正状態の編集 | 管理権限グループ / Proof Admin |
| 作業セルからの自己登録 | 案件参加User（全対象行・空き作業から選択） |
| 自分の作業実績登録 | Assignment担当者 |
| 全体閲覧 | 管理権限グループ、案件参加Userは作業用進行表 |
| 集計閲覧 | SuperAdmin / Admin / Leader / Clerk / Coordinator |
| クライアント共有URLの発行・失効 | SuperAdmin / Admin / Leader / Clerk / Coordinator |
| クライアント共有URLの閲覧 | 有効トークンを持つ者（読み取り専用） |

MGinbonの管理権限グループはSBWorkのサイトルールに従い、`SuperAdmin / Admin / Leader / Clerk /
Coordinator`を同権限とする。既存`CoordinatorMiddleware`はこれら5ロールを許可するため、原則として
同じアクセス規則を利用する。MGinbon内でLeaderを部署範囲へ限定したり、Clerkを下位扱いしたりしない。
Proof Admin（実装上の`proof_coordinator`）は全体を閲覧できるが、編集は校正担当、校正入り、
校正UP、校正状態等の校正関連項目に限定する。一般Userは自分の担当登録・実績入力を行う。

## 9. FileMaker移行設計

### 9.1 必要データ

設計確定前に、535件全件のヘッダー付きMergeまたはCSVを取得する。
CP932、CRLF、BOMを許容し、`NormalizesCsvEncoding`を使用する。

### 9.2 変換規則

- `_国語`, `_算数`, `_社会`, `_理科`を科目へ分解。
- `初校出`, `初校戻り`, `再校OP`等を工程定義と日付種別へマッピング。
- 担当者名を`users`へマッピング。完全一致だけで自動確定し、曖昧一致は確認対象。
- 外注先名を`subcontractors`へマッピング。
- 合計・小計・集計フィールドは原則取り込まず、明細から再計算。
- 空欄と0を区別する。0が実績ゼロか未入力かを項目ごとに定義。
- 確認済みの元データ誤りは取込補正ルールとして明示し、警告・補正履歴を残す。
- 元コードと元レコード識別子を保持。
- 書店向け印刷物とα版デジタル商品を別の商品構成として生成する。
- α版対象は年度別リストを正規データとし、学校マスターへ固定しない。
- α区分①～④・関西は年度Excelの値を正とし、みくにコード帯や学校属性から推測しない。
- みくにコード100／200／300／500番台は、共学／男子／女子／地方という年度版掲載分類として
  既存`n_publication_entries.publication_section`で扱い、恒久学校属性へ転用しない。
- α版対象校だけ、問題・解説解答・解答用紙・傾向と対策の存在媒体を生成する。
- 傾向と対策は年度×学校で1件とし、第二回等の入試回制作単位へ複製しない。
- 日付はJSTの日付として`Y-m-d`へ変換し、`toISOString()`を使わない。

### 9.3 取込方式

1. ファイル検証
2. プレビュー（新規／更新／警告／エラー）
   - 担当者、外注先、媒体、科目、工程等をドロップダウンで補正可能
   - 元のFileMaker値と補正後の値を併記
   - 未一致・重複・誤分類を行単位で保留可能
3. ドライラン集計
4. 明示確認後にトランザクション取込
5. 取込結果・対応表を保存
6. 再実行時は一意なlegacy keyで重複防止

本番FileMakerデータを破壊・更新しない。取込元は読み取り専用エクスポートとする。

既知の表紙媒体誤入力も、行番号依存の自動修正ではなく、取込プレビューで`問題`から`解答`へ
選び直せるようにする。確定した補正は同一legacy keyの再取込時に再利用できる。

### 9.4 照合

- 全体件数
- 学校別・媒体別件数
- 科目別の非空件数
- 工程日付件数
- 担当者別件数
- 外注先別点数
- 社内／外注合計
- 任意抽出した学校の画面目視

## 12. セキュリティ・運用

- 物理削除より履歴・論理状態を優先する。
- 変更操作は操作者を保存する。
- Sakura配備前にマイグレーション、キャッシュクリア、ビルドを実施する。
- 本番SSHは正確なコマンドを提示し、事前承認を得る。

## 13. 残る確認事項

確定済み:

- 年度プロジェクトは1年単位の大規模プロジェクトとして扱う。
- 確認済み誤入力は取込プレビューの候補セレクターで補正し、履歴を保存する。
- 主要168項目の分類と工程上の意味は`MGINBON_FIELD_MAPPING1.md`へ記録済み。
- 日報本文を自動上書きせず、作業実績から選択可能な候補を提示する。
- 作業時間は既存カレンダーへ各自が登録し、`events`から集計する。直接分数入力は追加しない。
- 現物を受け取った作業者が全対象行・空き作業から該当工程を選び、自分でAssignmentを登録する。
- 工程開始・完了を対応する管理日付へ自動反映する。校正は開始で校正入り、工程完了で校正UPとする。
- 担当登録とカレンダー作業登録は分離し、最初のEvent作業日を校正入りとする。
- 作業が次回へ続く場合は既存の続き作業を利用し、完了にしたEventの作業日を校正UPとする。
- 4科目セットと科目別作業の両方を選択できる。4科目一括でも同じAssignmentを4件作らない。
- 外注作業は外注先が直接入力せず、社内担当者が入力する。
- みくに出版には、既存進行表の共有URLを基礎にした読み取り専用進捗ビューを提供する。
- クライアント共有画面には社員名、校正者名、外注先名を表示しない。
- SuperAdmin、Admin、Leader、Clerk、CoordinatorはMGinbonで同じ管理権限を持つ。
- Proof Adminは全体を閲覧でき、校正関連項目だけを編集できる。
- 制作ファイルはMGinbonへ添付・移行せず、従来の共有サーバーで管理する。
- 管理台帳、共有進捗表、出稿表、文字入力・作図・原本スキャン発注書は印刷・PDF保存に対応する。
- 問題・解答のみの作業票は学校単位、解説解答等は科目単位で対象科目へ赤丸を付ける。
- 帳票の工程行、表示名、補助文言、手書き欄を安全な設定方式でカスタマイズできる。
