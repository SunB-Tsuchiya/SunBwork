- 帰りの実績時間は朝の予定枠から仮表示し、本人が確認・修正して保存することをユーザーが承認した。予定時間と確認済み実績時間を別に持ち、分析は確認済みの実績時間だけを使う。設計は PLAN に記載、実装は未着手。
- 作業種類: 進行管理へ「原稿チェック」を追加、校正は「修正校正（重）」「修正校正（軽）」を分ける。事務と営業にも少数の候補を追加した（PLAN の表）。`INFO` の担当マスターには事務専用コードがないため、作業の大区分として事務を増やす案で相談中。
- 事務は独立大区分にすることでユーザーが承認。`clerk` は権限で、オペレーター・校正などを兼務できる。入力可能な作業種類を権限や担当で固定しない。事務は伝票チェック、書類作成・処理を中心に候補化。Clerk の専用カレンダーと User タブの個人カレンダーは別画面なので、簡易入力への導線を確認する。
- 2026-10-09、ユーザーが実装を許可。`activity_type` と `actual_minutes` の追加 migration、日報入力・保存・表示、部署の日・週・月分析をローカル実装中。本番未展開。詳細は MANAGER の作業ログと `CONSOLIDATED_05` を確認する。

- 案件・ジョブの既存フローは残す。
- 個人の予定と実績を簡単に記録し、相手が何をしているか・忙しさの目安を見られるようにする。
- 案件名の厳密な統制より、「今日、組版を100ページやった」等が分かることを重視する。
- 最新方針は進行管理・営業・組版/DTP・制作・校正・その他を一つの粗い大区分で扱う。最初の入力対象は情報出版部署（`INFO`）の全担当。
- 朝の予定は大区分と予定枠を中心に短く登録する。予定は午前・午後・終日を基本に、希望者は1時間単位で指定できる。
- 実績は短い「今日の進み・結果」を基本にする。ページ数・件数など数量は任意で、組版のページ数はその日に作業したページ数。朝に予定を作成し、帰りに日報作成を開いた時点で予定を反映するか本人が選ぶ。
- 作業名は任意。朝の予定では既存案件選択・案件名自由入力が可能だが、案件未定でも登録できる案。帰りに予定を日報へ反映した場合、各予定の結果文と任意の実績数量・単位を日報画面で入力する。
- 朝の入力と部署内の予定確認は単一の「今日の作業」画面にまとめる。
- 午前・午後の境界は各人の対象日の勤務時間・昼休憩に合わせる。
- 部署一覧では予定枠の埋まり具合を段階表示し、未登録は不明とする。実績は人別・大区分別の記録日数と、入力された場合のみ単位別の数量を表示。順位・総合スコアは初期範囲外。
- 閲覧範囲は最新回答で**同じ部署内のみ**に変更された。グループ会社と他部署は閲覧不可。予定・案件・作業名があれば作業名・実績数量を表示する。
- 作業記録の一覧・集計は部署内限定だが、日報権限は現状どおり。本人が日報専用欄へ反映・保存した内容は、既存 `DiaryPolicy` により同じ会社の管理系ロールが閲覧できる。反映選択時に案内する。
- 評価査定は、まず記録と傾向を見てから基準を決める。任意記録の件数だけで職種を横断して比較しない。
- 設計図・管理ファイル・再開用プロンプトを作り、細部を相談しながら方針を決める。

## 現時点の設計仮説

- 予定と実績を同じ `personal_work_entries` に記録する案。案件・依頼ジョブへのリンクは任意。
- 大区分は進行管理・営業・組版/DTP/制作・校正・その他。既存の細かな `work_item_types` は必須にしない。
- 休憩設定がない日・夜勤の扱い、段階表示のしきい値は未確定。
- 現行作業量分析はジョブ数量・見積時間を使うため、新記録の評価指標にそのまま使わない。
- 欠入力を「暇」と表示せず、異なる単位や仕事を無条件にランキングしない。
- 朝は大区分と予定枠だけで保存できる。帰りに日報へ取り込む予定ごとの「今日の進み・結果」は必須。ユーザー確認済み。
- 本番の利用状況は、AGENTS.md に従い正確な SSH コマンドを提示・承認取得後、情報出版の各人の直近90日の自己割当・依頼割当・日報記入日数だけを集計済み。日報が48～56日あって自己割当0件の人が4人いた。自己割当件数は仕事量の代理指標にしない。案件名、本文、売上には触れていない。
- ユーザーは次に、日報より既存のユーザースケジュールの記入状況を優先分析するよう指示した。承認済み SSH で直近90日の `events` を確認。INFO 37人のうち、ジョブ非連動の個人予定があるのは4人（うち2人は1日だけ）、ジョブ連動の予定日があるのは20人、多くは46～60日。共有予定を多数作成する進行管理・営業もいる。校正用 proof の UTC/JST 混在を除いたジョブ連動予定4,489件の作成時刻は、前日以前7件、当日午前1,297件、当日午後3,142件、翌日以降43件。本人による入力か他者・自動作成かは区別していない。休暇・勤務日分母も未確認。タイトルや本文は取得していない。
- 次の設計論点は、既存ジョブ連動予定や共有予定がすでにある人に二重入力させないことと、案件に載らない進行管理・営業の予定を短く入れること。新記録を既存 `events` と同じ画面にどう見せるかを確定する。
- ユーザーは、本人の「今日の作業」に既存ジョブ予定を表示し、朝は足りない部分だけ大区分＋予定枠で追加する方針を承認済み。既存イベントは自動複製しない。本人には既存予定の詳細を見せ、部署一覧では `EventPolicy` が個人予定を原則本人等に限るため、当面は占有時間と粗い種別だけを使う案。重複時間は和集合で計算する。
- 最新回答: 部署一覧に、公開可の既存ジョブ予定の件名・案件名を表示する。極秘案件は案件単位で非公開を選択可能にする。既存ジョブ予定は本人が必要な行だけ日報へ取り込めるようにする（全件自動取り込みはしない）。
- 最新回答で、非公開設定は皆が見られる予定表だけに限定。既存の案件・JobBox・個人カレンダーの権限は変えない。派遣社員等に極秘案件の情報を見せたくない。既存案件の約9割は公開可能なので、案件は表示可を初期値にし極秘だけ非表示へ切り替える。新タブを全員に開く前に、稼働中の極秘案件の設定を確認する。案件に専用の表示可否を追加し、非公開時は件名・案件名・顧客名・ジョブ番号などを出さず時間枠だけ表示する案。自由入力の案件名にも行単位の公開設定を設ける案。
- ヘッダーの「予定表」は全ロール共通の `schedule.index` にリンクする。既存の共有予定表はグループ会社オーバーレイも扱うため、新たに「部署の作業」タブと部署限定 API を追加する設計案。既存 `schedule.events.range` へ新作業記録を混ぜない。公開可の案件名は派遣を含む同部署へ表示し、非公開案件は関係者本人以外の同部署メンバーには詳細を返さない。
- 最新の範囲指定では、案件の非公開設定は**新しい部署の作業予定表だけ**に作用する。既存の日報・案件・JobBox・個人カレンダー画面の表示や権限を変えない。自由入力の案件名は部署公開を初期値とし、必要時に入力者が非公開を選ぶ案。日報へ取り込む際は既存の日報閲覧範囲を案内する。
