# 簡易マイジョブの詳細入力・旧機能受渡し設計案

2026-11-05 JST。調査基準9b1565aa0（アプリ本番最終証拠a2f031c0e）。**設計案であり、方式/項目/新DBを確定・実装した資料ではない。** 利用者の依頼は同じ仕事のまま従来の詳細入力・添付等へ渡す方法の整理。一般公開は未承認。

## 調査結果と判断

- PersonalWorkEntryは予定時刻/実績数量/結果/分類/完了/続き元の正本。UnifiedMyJobBox.rowsは独立entryとPJAを別行にする。PJAとEventを追加したままentryを残すと、同じ仕事が複数行になり得る。
- User/ProjectJobAssignmentController.storeはProjectJobを経路引数に要求し、PJAと対応Eventを作る。簡易は大まかな分類・仮案件名のみでも保存できるため、旧フォームの新規保存へ直結すると不要な具体案件選択や別仕事作成を強いる。
- 旧updateもPJA向けで、対象割当と対応予定を更新する。簡易entryを対象とした既存更新APIではない。編集モードで旧画面を開くだけで同一仕事が保証されるとは扱わない。
- AssignmentForm.vueの「作業ファイル情報」はuseFileAnalyzerによる解析結果file_infoをJSONで保存し、MyJobBox/Show.vueのFileInfoDisplayで表示。調査したこのジョブ入力経路にはファイル本体の永続アップロード/ダウンロードを確認していない。日報のAttachment/pivot/uploadとは別機能。
- 旧フォームではファイル解析後にamounts/amounts_unit/size_idを自動設定する。簡易のactual_quantityは実績なので、この自動設定をそのまま移すと実績が変わる。ファイル総ページ数と実績数量を区別する必要がある。
- source_event_idは予定の結果補足、source_assignment/source_personal_work_entryは続き、supersedesは依頼置換。同一仕事の詳細化を表すために流用しない。

## 第一候補: 同じentryの詳細項目を拡張する（提案）

利用者に見える動きは「マイジョブ詳細 → 詳細入力（ファイル情報など） → 保存 → 同じ詳細」。簡易入力と詳細入力は入力項目の多さを変える。同じ仕事のままなので、別のマイジョブ/予定を作らない。旧PJAの新規作成画面へ移動する方式ではなく、既存の詳細項目・部品を簡易の同じIDでも使えるようにする案。

| 対象 | 保存先/扱い案 |
| --- | --- |
| 作業名/日付/開始終了/数量/単位/結果/完了/公開範囲/続き元 | 現在のPersonalWorkEntryが正本。詳細入力から別の値を重複保存しない |
| 作業の説明 | 任意の詳細メモ。進み・結果result_noteと分け、日報本文を生成しない |
| 作業ファイル情報 | file_info形式を再利用。ファイル名・種類・ページ数・サイズ等。ファイル本体とは別 |
| 旧固有の難易度/作業種別/サイズ等 | 詳細画面で本当に必要な項目を確認して段階追加。作業区分activity_typeと旧work_item_type_idを無断で一対一変換しない。分析の係数/評価を自動変更しない |
| 添付ファイル本体 | 利用者に別途確認中。必要なら認可付きアップロード/明示的entryへの紐付け/配信/削除を別工程で設計 |

保存案はpersonal_work_entry_details（仮名）のentry_id UNIQUEな1対1拡張。detail_noteとfile_info、更新競合用version等を候補にする。詳細メタデータだけを保持し、日付・時間・数量・完了・会社部署の別正本を作らない。初回migrationで既存entryを一括コピー/バックフィルしない。実装時は既存カラム追加との比較も行い、新テーブル採用を未承認のまま固定しない。

- 保存は既存entryを本人/会社部署/contextで再認可し行lock、拡張は一件だけ作成・更新。任意user_id/source/complete/statusは受理しない。戻る/キャンセルではDBを変更しない。
- 二重送信で拡張が増えないUNIQUE制約。編集中の他操作との競合はversion確認又はupdated_atチェックで明示し、単なる最終保存勝ちにしない。
- ファイル情報は構造/件数/文字列長/ページ数/合計値をサーバ検証。任意HTML/保存パス/URLを信用しない。合計値は可能な範囲で再算定。正本の実績数量は自動上書きしない。
- 詳細ファイル情報を消しても仕事/予定/数量/結果/系列は消さない。仕事本体の削除は既存の子/日報/同期待ち保護を維持し、拡張の後始末は同じtransactionで定義する。
- 公開範囲はentryに従う。新詳細データを部署一覧/分析/履歴検索へ自動追加しない。privateのファイル名やメモを他人propsへ漏らさない。本人INFO SuperAdmin試用に限定。
- 旧フォームは当初維持。共通FileInfoDisplay/useFileAnalyzerを再利用し、旧巨大フォーム全体を簡易保存先へ流用しない。新画面/部品はCONSOLIDATED_01に合わせる。

## 他の操作との区別

1. **同じ仕事の詳細入力（M11）**: entryのIDは同じ。BOX1行/カレンダー1予定/系列1ノード、時間・件数・数量は不変。仕事作成や完了通知は出さない。
2. **次の作業を旧詳細形式で作成（M09逆方向）**: 新しいPJAでよいが、元entryを明示した「続き」。別の日・時刻・新数量を入力する別仕事。この設計とは別の残工程。
3. **受信依頼からマイジョブ登録**: 承認済みの従来登録経路を維持。supersedesの置換/校正/通知の扱いを使う。既存entryの詳細化で再度登録しない。
4. **自分の仕事を他人へ依頼**: 所有者・依頼先・通知・実績の意味が変わるため、自動的に単純変換しない。利用者が必要とする具体操作を別確認する。今回の詳細化で依頼作成を実装済みにしない。

代替案はentryをPJAへ明示的に変換する方式。ただしBOX/カレンダー/日報/分析/継続元子孫/履歴/旧URL/完了/数量を全て別正本へ原子的に切替え、戻り・再送・同時編集を定義する必要がある。既存保存元保持の設計に比べ影響が大きいので、ファイル情報と詳細説明のためだけには第一候補にしない。利用者が従来の全機能を同じ旧画面で使うことを必須とする場合は、この比較を再検討する。
