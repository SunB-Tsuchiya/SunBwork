# PERSONAL_WORK_PLAN1 — 全職種共通の作業予定・日報記録 設計図

作成日: 2026-10-08  
状態: 承認済みの初期版をローカル実装中。本番未展開。

## 2026-10-08 入力導線の更新（最新決定）

- 朝の入力は User の個人カレンダーを起点にする。日付や時間帯をドラッグした操作メニューで「簡単な作業予定を追加」を選ぶと、選択した時刻を引き継ぐ。既存の「会議などの予定を追加」等の詳細入力も同じメニューに残す。
- 簡単入力は大区分と予定枠のみで保存可能。案件選択・案件名自由入力・作業名・公開範囲は任意。ドラッグした時刻は15分単位の時間指定として保存し、簡易予定を個人カレンダーへ再表示する。
- ヘッダー「予定表」の「部署の作業」は閲覧専用の日別タイムライン。入力フォームは置かず、個人カレンダーへのリンクを出す。以下の古い「今日の作業」単一画面・部署一覧内入力案より、この節を優先する。
- 案件欄は候補検索にし、Coordinator が本人をチームメンバーにした案件を先頭、簡易予定や過去のマイジョブで使った案件を次に表示する。案件名・番号・取引先名から同社の過去案件も検索でき、完了案件を選んでも既存案件への参照を保持する。極秘案件は関係者以外の検索候補に出さない。候補にない場合は従来の案件名自由入力を使う。固定のお気に入り登録は初期版では設けず、最近使った案件を候補にする。

## 2026-10-09 作業実績と新しい分析の方向（ローカル実装済み）

- 朝の予定では作業種類を任意入力とし、帰りに日報の作業結果を記録する行では必須にする。大区分とは別の少数の候補を、選択した仕事の大区分に応じて表示する。別の仕事をした日は大区分を切り替えられ、現在の `users.assignment_id` や `user_role` だけで入力できる種類を制限しない。以下を初期候補として実装し、名称と境界は試用で調整する。

| 大区分 | 帰りに選ぶ作業種類の候補 | 入力を迷わせないための目安 |
| --- | --- | --- |
| 組版・DTP・制作 | 新規作成／修正／データ整備／納品チェック | デザイン制作を別表示するかは試用時に確認 |
| 校正 | 初校校正／修正校正（重）／修正校正（軽）／原稿チェック | 重・軽はページ数ではなく赤字の密度と確認に要した手間で選ぶ。境界は下記確認待ち |
| 進行管理 | 進行調整／原稿チェック／入稿・納品チェック／連絡・打合せ／事務作業 | 顧客・社内調整、原稿整理、納品前の確認を分ける |
| 事務 | 伝票チェック／書類作成／書類処理／受発注・請求対応／その他事務 | `INFO` の担当マスターに独立した事務コードはない。UI の大区分として追加する |
| 営業 | 訪問・商談／見積・提案／受注・納期調整／顧客連絡 | 連絡件数は任意数量とし、メール1通を自動的に1作業へ分割しない |
| 共通 | その他 | 短い結果文で内容を残す |

- 「修正校正（重）」は赤字が多く、広範囲の再確認が必要な場合、「軽」は少数の赤字・限定箇所の確認を想定する。自己申告の重・軽を即座に評価係数へ使わず、実績時間と一緒に分布を見て目安を調整する。
- **決定済み:** 事務は進行管理から独立した作業の大区分にする。ユーザーがいう `clerk` は `user_role`（権限）であり、`INFO` の `assignment`（担当）には独立した事務コードがない。Clerk 権限者がオペレーター・校正等を兼務するため、権限や担当で作業種類を固定しない。直近に本人が使った大区分を初期候補にする案とし、毎回ほかの大区分へ変更可能にする。現状の `clerk.calendar` は事務・会社共有カレンダー、簡易作業予定の入口は共通の `calendar.index`（User タブ）であるため、Clerk からの導線は実装時に確認する。
- 部署内の分析は同一の実績行から日・週・月の期間を切り替える。作業種類ごとの**実績時間**を主軸にし、ページ数・件数などの数量と単位は任意で併記する。**決定済み:** 帰りの各作業行に朝の予定枠から仮の時間を表示し、本人が確認・修正して保存する。確認後の値を `actual_minutes` として予定時間とは別に保持し、日・週・月の集計には `actual_minutes` のみを使う。日報未反映や未記入はゼロ作業とみなさない。
- 仮の時間は、時間指定なら開始から終了まで、午前・午後・終日なら本人の対象日の勤務枠と休憩設定から算出する。予定が重なっても行ごとに時間を単純加算して正しい実働時間とみなさず、日報上で合計を見せて修正できるようにする。既存ジョブ予定を取り込む場合も、同じ作業の簡易予定を重複選択しないよう注意を出す。確認済み実績がまだない行は集計対象外にする。
- 日別は対象日の確認済み実績、週別は月曜始まりの日別合計、月別は暦月の日別合計とする案。数量は同じ作業種類かつ同じ単位の中でのみ合算し、ページ・件・ファイルなどを混ぜない。部署・会社境界と極秘案件の表示制御は既存の部署作業予定表に合わせる。
- 将来は簡易実績とマイジョブを折衷する。簡易実績を「その日に本人が行ったことと時間」、マイジョブを「案件・工程・数量・依頼の文脈」とし、同じ作業を二重加算しない。明示的に紐付く `project_job_assignment_id` があれば照合し、案件IDだけが一致しても別作業を自動的に同一視しない。マイジョブのみの月は別出典の参考値として表示し、実績時間へ換算しない。
- ページ数の意味は工程で異なる。納品チェックでは一度に数千ページを扱うことがあり、数量だけで異常値・高負荷とは判定しない。同じ単位でも「新規組版」と「納品チェック」を単一のページ係数で混ぜない。職種横断の単一評価点・順位は記録方法と分布の検証後に検討する。
- 現行 `WorkloadAnalyzerController` は自己割当を全割当に含めた後、自己割当を再集計してページ系生スコアへ加える経路がある。現行ランキングを新実績に接続する前に重複集計の修正と旧スコアの再検証が必要。既存ランキングの値と新しい日・週・月分析を同じ意味の指標として並べない。
- 承認済みの本番読み取り専用集計（直近90日、情報出版部署、氏名・案件名・本文・売上なし）では、進行管理と営業に作業種別未設定の自己登録が多い。進行管理の「データ制作」56件で合計97,652ページは、納品チェック等の大量ページを扱う業務があり得るため、入力誤りとは断定しない。

## 1. 目的と対象

- 最初に入力する人は**情報出版部署（`INFO`）の全担当**。進行管理・営業・組版／DTP・制作・校正・その他に共通の短い入口を作る。閲覧は情報出版部署内に限定する。
- 各人が**朝にその日の作業予定**を短時間で記録し、所属部署内で「何をしているか」「予定がどの程度埋まっているか」を見られるようにする。
- **帰りに日報を作成**し、当日の予定を反映するか本人が選ぶ。各行へ短い「今日の進み・結果」を残し、ページ数・件数などの数量は記録できる仕事だけ任意で入力する。組版で数量を入れる場合は、その日に作業したページ数とする。
- 一日の途中で仕事が変わることを許し、予定の修正や予定外作業の追加を簡単にする。毎日の入力を強制せず、未登録は「不明」と扱う。
- 初期版は記録と傾向の把握を目的とし、評価査定の点数・順位は付けない。運用を見て職種別の評価基準を後で相談する。
- 既存の Coordinator 案件作成、JobBox、MyJobBox、日報、勤怠用 `work_records` は維持する。個人作業記録の作成に案件登録やジョブ依頼を必須としない。
- 2026-10-08 の承認済み本番集計では、情報出版の直近90日に日報記入が48～56日ありながら自己割当が0件の人が4人いた。自己割当がある人でも件数に大きな差がある。自己割当件数を作業量の代理指標にしない。集計は名前・件数のみで、案件名・本文・売上は取得していない。なお集計上の自己割当は校正用の自動スロットを含み得るため、MyJobBox画面上の件数とは一致しない可能性がある。
- 同日の追加集計では、情報出版の直近90日について、個人予定のうちジョブ非連動の手入力があるのは37人中4人（うち2人は1日だけ）。一方、ジョブ連動の予定日があるのは20人で、多くは46～60日。ジョブ非連動で44日・46日分を記録した人も各1人いる。進行管理・営業には共有予定を多数作成した人もいる。共有予定の作成件数は本人の作業予定や参加日数ではない。休暇・勤務日の分母を調整していないため、未登録率や怠慢の指標にしない。
- 作成時刻の承認済み追加集計（同じ直近90日、校正用 `job_type=proof` は UTC/JST 混在のため除外）では、ジョブ連動予定4,489件のうち前日以前の作成は7件、当日午前1,297件、当日午後3,142件、翌日以降43件。大半が当日登録で、午前より午後が多い。`created_at` は初回作成時刻であり、更新時刻や本人が実際に作業した時刻とは異なる。共有予定やジョブ連動予定には他者作成・自動作成があり得るため、個人の記入努力や評価には用いない。

## 3. 初期画面の体験案

### 朝: 本人が予定を入力

1. 単一の「今日の作業」画面で、自分の既存予定・不足分の簡単な予定入力・部署内の予定確認を行う。日付は JST の今日を初期値にする。既存ジョブ連動予定を読み、同じ予定を再入力させない案を優先する。
2. 大区分を「進行管理／営業／組版・DTP・制作／校正／その他」から選ぶ。担当に応じた初期値を出すが変更可能にする。案件は既存案件の選択または自由入力、作業名も任意とし、案件が決まらない進行管理や営業でも**大区分と予定枠だけで保存できる**。これはユーザー確認済み。
3. 予定枠は「午前・午後・終日」を基本にする。希望者は開始・終了を1時間単位で指定できる。午前・午後は各人の対象日の勤務時間と昼休憩を基準に区切る。
4. 1日複数行を許す。既存案件とのリンクがあっても、依頼ジョブの完了状態は自動変更しない。依頼ジョブとのリンクは必要なら後から追加する補助項目とする。

### 既存予定を使う導線（今回の合意）

- 本人の「今日の作業」には、既存の個人カレンダー予定を読み取り専用で表示する。ジョブ連動予定を再入力させず、共有予定のうち本人が作成したものと参加を承諾したものも、本人の時間枠として確認できるようにする。辞退した参加予定は含めず、参加未確定は「仮予定」として別表示する案。
- 部署一覧では、公開を許可した案件に結び付く予定の**件名・案件名**を表示する。極秘案件は案件単位で「非公開」を選べるようにし、非公開案件の予定は時間枠だけを忙しさへ算入して、件名・案件名・顧客名・ジョブ番号・自由メモを返さない。個人予定の詳細公開範囲は既存 `EventPolicy` と異なるため、新機能専用の明示的な認可判定をサーバ側に置く。
- 公開先は、ヘッダーの「予定表」（`schedule.index`）に追加する**「部署の作業」タブ**を推奨する。既存の共有予定表は全ロール共通でグループ会社オーバーレイも扱うため、既存 `schedule.events.range` へ作業記録を混ぜない。新タブは別 API で同じ会社・同じ部署だけを返す。ヘッダーのリンク先は `schedule.index` のままにし、タブ選択または `?tab=work` で直接開ける案。
- 既存予定を見て足りない時間帯・案件未定の仕事だけ、大区分＋予定枠で簡易予定を追加する。前日の簡易予定を複製する近道は試用時の候補とする。既存 `events` を `personal_work_entries` に自動複製しない。
- 新しい簡易予定と既存予定が重なっても、本人画面では両方の出所が分かるようにし、部署一覧の埋まり具合は勤務枠内の時間の和集合で計算して二重加算しない。実績数量も既存ジョブ数量と自動合算しない。
- 既存ジョブ予定は当日午後の作成が多かったため、朝の一覧では「予定未登録／簡易予定あり／既存予定あり」をその時点のデータで判断する。後で追加されたジョブ予定により、朝の登録実績があったかのように扱わない。入力促進の分析には作成時刻と予定日を分けて使う。
- 予定日またぎや校正ジョブの UTC 保存を考慮し、既存イベントの JST 時刻解決には `CalculatesEventTime` の規則を用いる。休暇・勤務日が不明な日は登録率の分母から安易に数えない。

### 帰り: 本人が日報を作成

1. 「日報作成」を選んで当日の画面を開いた時点で、「朝の予定を反映する／反映しない」を選べるようにする。
2. 反映する場合は当日の予定を下書きとして読み込む。朝の予定そのものと既存の日報本文は上書きしない。反映しない場合は通常の日報入力画面を開く。
   - 選択時には、日報本文に反映・保存した文面は既存の日報権限を持つ同じ会社の管理者等にも見えることを短く案内する。
3. 反映した各予定の行に、短い**必須の「今日の進み・結果」**を入力する。数量・単位は任意とし、組版なら例として「100ページ」、進行管理なら「校了待ち3件を整理」などを残せる。実績入力は**日報画面内**で完結する。
4. 朝の予定と異なる作業、予定外の割り込みも日報時点で追加できるようにする。進行状態の追加操作は初期案に含めない。
5. 作業一覧は日報の**専用欄**に表示し、本文と一緒に保存する。片方だけ保存される状態を避けるため、同一トランザクションで保存する。
6. 再度日報画面を開いても、下書き反映で同じ実績を重複生成しない。反映は予定行の参照と画面上の下書き生成であり、確認操作だけでは DB を書き換えない。
7. 既存ジョブ予定も本人が必要な行だけ選んで日報の作業欄へ取り込めるようにする。選択した行の「今日の進み・結果」は必須、数量は任意。全件を自動選択しない。同じイベントを同じ日報へ二重に取り込めないようにする。

### 一覧と見せ方

- 「今日の作業」画面は、最初に自分の予定入力、続いて同じ部署の人別予定一覧を配置する案。スマートフォンでも当日の予定が見やすい構成にする。
- 本人: 今日・今週の予定と実績を同じ一覧で確認し、訂正できる。
- **同じ会社の同じ部署内だけ:** 情報出版の全担当を人×日付の一覧に並べ、大区分、任意の案件・作業名、予定枠、短い結果、任意の実績数量を表示する。グループ会社や他部署には表示しない。非公開メモを設ける場合は本人だけに表示する。
- 既存の個人予定は原則本人用で、`EventPolicy::view` は所有者等に限る。新しい「部署の作業」タブでは**同部署で公開可とした案件のジョブ予定**に限って件名・案件名を見せる。非公開案件、ジョブに紐づかない個人予定は、詳細を返さず粗い状態と時間枠だけを見せる。従来のカレンダー・案件・JobBox の閲覧権限は変えない。
- 「予定あり」「予定未登録」「休暇等」は区別する。未登録を「暇」と判定しない。
- 部署一覧の忙しさは、予定枠の埋まり具合を段階表示する。日別勤務形態 → 既定勤務形態で勤務時間を解決し、日別休憩 → 既定休憩を差し引いた勤務枠を分母にする。午前・午後は解決した休憩の前後、終日は勤務枠全体とする。重複予定は二重加算しない。表示文言・しきい値は試用時に調整できるようにする。
- 実績は、**人別・大区分別**の記録日数、短い結果と、入力された場合だけ単位別の数量を表示する。複数日に同じページを作業した場合はそれぞれの日の作業量として数える。異なる単位は合算せず、未入力を0件・0ページと見なさない。初期版では個人順位や総合スコアを表示しない。
- 休憩設定がない日・夜勤の区切りは実装前に例を確認する。勤務枠を解決できない人は埋まり具合を数値化せず「予定あり／未登録」にとどめる。

### 「予定表」内の配置・取得契約

1. ヘッダーの既存「予定表」リンクを開くと、`Schedule/Index.vue` に「部署の作業」「共有予定」の切替を置く。初期試用対象の `INFO` 利用者は「部署の作業」を初期表示する案とし、従来の共有予定にも1回の切替で移動できる。他部署では従来の共有予定を初期表示する。既存の共有予定は現在の `ScheduleCalendar` を使い、他部署やグループ会社に新タブのデータを配信しない。
2. 「部署の作業」上段に日付切替、自分の既存予定、簡易予定の追加ボタンを置く。簡易予定の初回入力は大区分と予定枠だけ。案件リンク・自由入力名・細かな時間は後から追加できる。
3. 下段は同部署の人別一覧。公開可の案件は件名・案件名・時間を表示し、極秘案件は関係者以外には「非公開の予定」と時間だけを表示する。未登録は「不明」とし、予定が重なる時間は一度だけ数える。
4. 新しい取得 API はログイン者の `company_id` と `department_id` をサーバ側で固定し、リクエストの部署 ID で範囲を広げない。既存の `schedule.events.range` とは独立させ、秘密案件のタイトルを JSON に含める前に認可判定する。
5. 案件の作成・編集画面に「部署の作業予定表に案件名を表示する」切替を置く。初期値は表示可。極秘案件は非表示に切り替え、担当者が稼働中の極秘案件を確認してから新タブを全員に開く。

## 4. データ設計案（確定前）

`personal_work_entries` を新設し、予定と実績を同じ行で管理する案。カラム名と型は相談後に確定する。

| カラム案 | 型案 | 用途・制約 |
| --- | --- | --- |
| `id` | bigint PK | 記録 ID |
| `user_id` | FK users | 所有者。編集・削除は本人のみを原則とする |
| `company_id`, `department_id` | FK nullable | 記録時の所属をサーバ側で保存する案。異動後に過去の公開範囲が変わらないようにする |
| `work_date` | date | JST の作業日。モデル cast は `date:Y-m-d` |
| `work_category` | varchar(30) | 大区分。進行管理・営業・組版/DTP/制作・校正・その他。担当に応じた初期値を変更可 |
| `title` | varchar(255) nullable | 任意の短い作業名。案件が分かる表示を優先する |
| `project_name_text` | varchar(255) nullable | 既存案件が候補にない場合の自由入力。案件名の表記揺れを許容 |
| `plan_slot` | varchar(20) nullable | 午前・午後・終日・1時間単位指定。午前・午後の実時間は対象日の勤務・休憩設定から解決する |
| `planned_start_time`, `planned_end_time` | time nullable | 1時間単位指定の場合に保存。JST の壁時計時刻 |
| `actual_quantity` | decimal(10,2) nullable | その日に作業した数量。予定だけの段階では未入力可。0 と未入力を区別 |
| `actual_unit` | varchar(30) nullable | `page`, `file` 等。許可値は職種別に定義 |
| `result_note` | text nullable | 短い「今日の進み・結果」。実績保存時の中心項目 |
| `memo` | text nullable | 本人用の補足。初期版に必要か試用で確認 |
| `diary_id` | nullable FK diaries | 日報の専用欄に取り込んだ行との関連。日報削除時も作業記録は残す案 |
| `project_job_id` | nullable FK project_jobs | 任意の案件リンク。削除時の扱いは要確認 |
| `project_job_assignment_id` | nullable FK project_job_assignments | 任意の依頼ジョブリンク。所有者整合を検証 |
| `source_event_id` | nullable FK events | 本人が既存ジョブ予定を日報へ選択して取り込んだ場合の参照。削除時も実績行は残す案 |
| `entry_visibility` | varchar(20) | 「部署の作業」タブでの自由入力名の表示範囲。`private` / `department` 案。案件リンクがある場合は案件の非公開設定を優先 |
| `created_at`, `updated_at` | timestamp | 編集履歴の基本情報 |

- `user_id, work_date` と `company_id, department_id, work_date` の複合インデックスを置く。1日複数件のため unique にはしない。
- 案件・作業名はいずれも任意。既存案件を選んだ場合の表示名は案件から取得する。案件なしでも大区分と予定枠で朝の登録を完了できる。
- 数量は非負とし、実績を入力する場合のみ単位を必須にする。入力上限・小数許容は要確認。
- 「予定のみ」「実績入力済み」は結果文の有無から判定する。日報に反映・保存する行では結果文を必須とし、数量だけで実績扱いにしない。余分な状態入力は初期版に設けない。
- 自由入力の名称は表示時にエスケープし、HTML として保存・表示しない。
- 進行管理・営業・校正も同じ表を使い、組版専用カラムを増やさない。
- 案件の公開・非公開は `project_jobs` に**「部署の作業予定表で案件名を表示する」**専用の真偽値を追加する案。既存 `ProjectJob` には現状この設定がない。既存案件の約9割は公開可との回答を踏まえ、初期値は表示可とし、案件の作成・編集権限を持つ Coordinator 等が極秘案件を非表示に切り替える。新タブを全員へ開く前に、担当者が稼働中の極秘案件を確認して設定する。既存の案件・JobBox・個人カレンダーの権限は変えない。
- 自由入力の案件名は既存案件の公開設定を引けないため、作業記録側で部署公開／非公開を選べるようにする案。非公開案件とリンクした行は、行単位で公開を選んでも非公開を優先する。未リンクの自由入力は約9割が公開可という運用方針に合わせ、部署公開を初期値とし、入力者が極秘のとき非公開を選ぶ。
- `source_event_id` がある実績は対象日・所有者一致を検証し、同じ日報内で重複参照させない。「部署の作業」タブへ件名・案件名を出す際は、現在の案件公開設定を毎回判定する。非公開化後の古い作業予定が新タブから漏れないよう、保存済みのタイトル文字列を無条件に配信しない。日報と既存カレンダーの閲覧権限・表示は現状どおり。
- 初期版では既存 `events` や `project_job_assignments` へ自動複製しない。「今日の作業」画面で予定・実績を表示し、二重登録と二重計上を避ける。既存カレンダーへの表示は試用後に必要性を判断する。
- 2026-10-09 更新: 部署の作業一覧と作業実績の内訳は別ページに分ける。予定表タブから個人カレンダーへ移動できるようにする。内訳の日表示では結果未入力の予定を実績と分けて示し、実績時間には加えない。
- 2026-10-09 更新: 利用者の試用結果を受け、簡易予定は個人カレンダーの専用 API から既存イベントと並べて表示する。`events` への複製はせず、二重登録を防ぐ。大区分ごとに色を分け、月表示では簡易予定を優先する。勤務形態未設定者の午前・午後・終日は表示上のみ 09:00–18:00 を仮枠とし、日報の実績時間には流用しない。
- 試用前に、既存 `events` のジョブ連動予定・手入力予定・共有予定と新記録を同じ「今日の作業」でどう見せるかを確定する。既存予定を新記録へ複製して入力を増やさない。新記録から既存予定を参照して結果だけ足せる導線を優先候補にする。

## 5. 既存機能との境界

| 既存機能 | 初期案 |
| --- | --- |
| JobBox / MyJobBox | 依頼・進捗・完了の正規フローを維持。個人記録から任意で参照できる |
| 個人カレンダー / 共有予定表 | ヘッダーの「予定表」内に部署限定の「部署の作業」タブを設ける。本人の既存予定を読み取り専用で同タブに表示し、既存予定への書き込み・自動複製はしない。従来の共有予定表の全社・グループ会社オーバーレイとは別 API にする |
| 日報 | 帰りに日報作成を開いた時点で、当日の簡易予定を反映するか選ぶ。既存ジョブ予定も本人が行単位で任意選択できる。選択した作業行は専用欄に表示し、本文と一緒に保存する。既存本文は上書きせず、日報全体には従来の日報閲覧権限を適用。案件の予定表向け非公開設定は日報には作用させない。`work_records` は勤怠として維持 |
| 作業量分析 | 新しい記録日数・結果文・任意の数量を「今日の作業」内で人別・大区分別に表示。旧スコアとの合算や順位付けは行わない |

## 6. 権限と安全性の案

- 本人は自分の記録を作成・編集・削除可能。管理者の訂正権限が必要かは要確認。
- 閲覧対象は**同じ会社の同じ部署**に所属する利用者のみ。予定・案件・任意の作業名・実績数量を見せ、グループ会社と他部署からは隠す。役職による全社閲覧の例外は設けない初期案。サーバ側ポリシーとクエリの両方で `company_id` と `department_id` を照合する。
- 派遣・業務委託を含む同部署メンバーは、公開可の案件の件名・案件名を「部署の作業」タブで閲覧できる。極秘案件は**その案件の担当者・案件管理者等、業務上関係する本人**にだけ同タブでも詳細を表示し、その他の同部署メンバーには時間枠と「非公開の予定」だけを返す。雇用形態だけで担当者本人の作業画面を隠さない。この判定はタブ専用 API に適用し、日報・既存カレンダーの権限には作用させない。
- 初期版の作成・閲覧対象は `INFO` 部署の全担当。担当コードで作成権限を狭めない。
- この制限は新しい個人作業記録の一覧・取得・集計に適用する。日報の権限は変更しない。本人が日報専用欄へ反映して保存した作業内容は、既存の `DiaryPolicy` に従い同じ会社の Admin・Leader・Coordinator にも見える。
- 日報専用欄と本文には既存の日報閲覧権限を適用する。予定表向けの非公開設定で日報の文字列を伏せないため、極秘案件を日報に取り込む操作時には既存の日報閲覧範囲を短く案内する。
- 既存案件を選ぶ場合は、その利用者に参照権限がある案件に限定する。選べる案件がない場合は自由入力を許す。依頼ジョブへのリンクを実装する場合も所有者整合を検証する。
- 集計 API も一覧と同じ部署内の閲覧範囲を適用する。自由メモは本人以外へ返さない初期案。
- 作業日と予定時刻は JST として扱い、UTC 変換が必要なイベント連携では既存 `CalculatesEventTime` の規則を確認する。

## 8. 検証計画

- 予定だけ、実績だけ、複数作業、訂正、数量 0、日付境界を確認する。
- 他人の記録の作成・変更・閲覧を権限別に検証する。同一会社の他部署とグループ会社を含む会社境界を跨ぐ参照を防ぐ。
- 情報出版の進行管理・営業・組版/DTP・制作・校正・その他の担当は作成でき、他部署は作成・閲覧できないことを確認する。
- 日報作成時の反映／非反映、既存本文の保持、再表示時の重複防止、予定外作業の追加を確認する。
- 新しい作業記録は他部署から取得できず、日報へ本人が反映・保存した文面は既存 `DiaryPolicy` の範囲で閲覧できることを確認する。
- 日報保存と予定ごとの実績保存について、片方だけ成功した状態を残さないことを確認する。
- 同じ依頼ジョブへのリンクがあっても既存 JobBox の完了・分析値を二重変更しないことを確認する。
- 予定の重複、半日・夜勤・休憩、予定なし・未登録の表示と段階表示を確認する。
- 実績数量の集計は同じ大区分・同じ単位に限り、未入力を0にせず、会社・部署の閲覧境界を跨がないことを確認する。
- 公開案件は同部署の「部署の作業」タブに件名・案件名を表示し、非公開案件は関係者以外へ件名・案件名・顧客名・ジョブ番号・自由メモを専用 API から返さないことを確認する。公開から非公開への変更後も過去日のタブ表示から案件名が漏れないことを確認する。既存の日報・カレンダー表示が変わらないことも確認する。
- 既存ジョブ予定の本人による任意取り込み、同一イベントの二重取り込み防止、他人のイベント ID の不正指定防止、元イベント削除後の作業結果保持を確認する。
- Vue/JS 変更時は AGENTS.md のビルド手順に従う。DB の破壊的操作は行わない。本番調査は承認された読み取り専用集計に限定する。

## 9. ユーザーと決める事項

1. **最新の決定:** 初期入力は大区分と予定枠を中心にする。帰りの実績は短い「今日の進み・結果」を中心とし、数量・単位は任意。組版のページ数は入力した日の作業ページ数。
2. **決定済み:** 予定は午前・午後・終日を基本とし、希望者は1時間単位で指定できる。
3. **最新の決定:** 閲覧範囲は同じ部署内のみ。グループ会社・他部署からは閲覧不可。予定・案件・任意の作業名・実績数量を表示する。
4. **決定済み:** 1ページはその日に作業したページとして数える。同じページを複数日に作業した場合や同日複数人で作業した場合も、それぞれの作業記録として扱う案。細かな例は試用時に確認する。
5. **更新済み:** 作業名は任意。既存案件の選択・案件名の自由入力を用意するが、進行管理・営業など案件が決まらない作業も登録できるよう、案件は必須にしない。
6. **決定済み:** 朝に予定を入力し、帰りに日報を作る。日報作成を選んだ時点で予定の反映／非反映を選び、反映した予定ごとの結果文と任意の数量を日報画面で入力する。作業一覧は日報専用欄に保存する。
7. **決定済み:** 午前・午後は各人の勤務時間・昼休憩に合わせる。休憩設定がない日・夜勤時の扱いは実装前に確認する。
8. **決定済み:** 朝の入力と部署内一覧は単一の「今日の作業」画面にまとめる。
9. **決定済み:** 部署一覧は予定枠の埋まり具合を段階表示し、未登録は不明とする。実績は人別・大区分別の記録日数と任意の数量まで表示し、順位は初期版に含めない。
10. **最新の決定:** 情報出版の全担当で開始する。入力に要する時間、週あたりの記録率、上長が見たい情報を試用後に確認する。
11. **決定済み:** 個人作業記録そのものは部署内限定。日報の権限は現状どおりで、日報専用欄へ反映・保存した内容には既存の日報権限を適用する。
12. **最新の決定:** 評価査定は記録と傾向を見てから基準を決める。任意入力の件数や職種間の異なる単位だけで人を比較しない。
13. **決定済み:** 朝は大区分と予定枠だけで保存できる。
14. **決定済み:** 日報に取り込む予定ごとの「今日の進み・結果」は必須。数量・単位は任意。
15. **確認済み:** 本番の直近90日集計を読み取り専用 SSH で実施。自己割当の有無と日報記入にはずれがあり、自己割当件数だけでは日々の仕事を把握できない。
16. **決定済み:** 既存ジョブ連動予定を「今日の作業」に表示し、朝は予定が足りない部分だけ大区分＋予定枠で補う。既存予定を新記録へ自動複製せず、重複表示と二重計上を防ぐ。
17. **最新の決定:** 部署一覧でも公開可の既存ジョブ予定の件名・案件名を見せる。極秘案件は案件単位で非公開を選択可能にする。
18. **最新の決定:** 既存ジョブ予定を本人が選択して日報へ取り込めるようにする。取り込んだ行には決定済みの必須結果文を適用し、全件自動取り込みはしない。
19. **最新の決定:** 案件の公開・非公開は新しい「部署の作業」タブなど皆が見られる予定表での表示に限る。既存の案件・JobBox・個人カレンダーの閲覧権限は変えない。
20. **最新の決定:** 約9割の既存案件は公開可。既存案件を一律非公開にはせず、表示可を初期値にして極秘案件だけを非表示に切り替える。新タブの全員公開前に稼働中の極秘案件を担当者が確認する。
21. **配置案:** ヘッダーの「予定表」から開く `schedule.index` に「部署の作業」タブを追加し、同じ会社・同じ部署の利用者だけが閲覧する。既存の共有予定表はそのまま残す。
