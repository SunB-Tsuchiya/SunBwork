# 作業記録・予定表・評価見直しの管理台帳

更新: 2026-10-17（JST）。対象: 情報出版の Super Admin 試用から、入力の定着、上長照合、将来の公開判断まで。

## この台帳の使い方

このファイルを横断プロジェクトの現在位置と未決事項の入口にする。具体的な実装と確認結果は `JOB_INPUT_REVIEW_PLAN1.md` / `JOB_INPUT_REVIEW_MANAGER1.md` / `JOB_INPUT1_PROMPT.md`、分析は `WORKLOAD_REBUILD_PLAN1.md` / `WORKLOAD_REBUILD_PLAN2.md` / `WORKLOAD_REVIEW_PLAN3.md`、過去の経緯は `JOB_REDESIGN_FLOW_AUDIT1.md` と `JOB_SYSTEM_RETHINK_NOTES1.md` を参照する。`PERSONAL_WORK*` と `JOB_REDESIGN*` は先行試用の資料であり、現方針に反する箇所はそのまま実装しない。手元にない `JOB_REDESIGN*` 等の資料は、手元の `origin/main` に存在する場合、`git show origin/main:z_instructions/<ファイル名>` で参照する。

引継ぎ時は、まず `AGENTS.md` と本台帳を読み、次に作業対象の PLAN / MANAGER / PROMPT と実装、最新の利用者発言を照合する。作業ツリーが分岐していたら、ファイルの存在だけで最新と決めず `git status`、`git log`、`git show origin/main:<path>` で比較する。`origin/main` 自体も取得時点の参照なので、本番やリモートの最新状態と同一とは断定しない。`/tmp` の隔離作業ツリーが残るとは仮定しない。

**記録規則:** 新しい発言ごとに、以下の決定・提案台帳へ日付、状態、根拠、置き換えた旧方針、次の検証を記す。進捗は「コード作成」「ビルド・構文」「本番試用反映」「利用者の画面確認」「上長の実例照合」を分ける。利用者の「成功」「OK」は直前に依頼した確認項目すべてを確認した回答として扱う。一部だけの場合は利用者がその旨を明記する。依頼していない条件まで確認済みと拡張しない。複数項目など回答の意味が曖昧になり得る画面確認では、確認項目と「すべて問題なければ『成功』のみ、違いがあれば該当項目と結果」などの返答方法を先に明示する。公開や採点方式を確定する前に、未決・保留の行をすべて再点検する。

## 最初の理念と現在の境界

1. **記録を止めない。** 短期に大量の仕事を切り替える人、長期案件の人、進行管理・営業・事務・校正・制作の人が、細かな伝票や依頼の完成を待たずに記録できること。途中でも終業時でも同じ入口を使い、1日10件程度でも扱えること。
2. **既存の良い経路を守る。** `project_job_assignments` を使う依頼→マイジョブ転換、依頼元、続き、ファイル、進行表との関係は維持する。進行管理の日常の必須作業は本筋の案件とメンバー登録を基本とし、支流・伝票・依頼は必要時に扱う。本筋がまだなければ仮名でその日を記録する。名前の一致だけで支流へ自動紐付けしない。
3. **時刻と日報の役割を明確にする。** 簡易予定の作業時刻はカレンダーの開始・終了。独立した分数入力欄は設けない。予定はその日の活動記録として扱い、毎件の実施確認は求めない。日報本文は自由記述のまま、タイムテーブルに予定を示す。大きな時間不足は保存を妨げず案内する。
4. **評価は試用中。** 目的は仕事の見える化と人事評価の参考で、おおむね6:4という優先度を点数比率に変換しない。記録時間・件数・工程候補・数量・自動完了・暫定点を、そのまま勤勉さ、成果、品質と断定しない。現場実例と上長の見方を複数月で照合してから評価方法を決める。
5. **公開範囲を保つ。** 新入力・分析は情報出版 Super Admin 試用。部署外・グループ会社・非公開案件の情報を広げない。一般公開と旧方式の置換は別の決定とする。本番 sales DB の閲覧・複製、実名や個別の評価値の資料保存はしない。
